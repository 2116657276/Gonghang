# 行止微信小程序手动验收指南

> 适用阶段：D3.1 微信开发者工具与真机验证
> 前置状态：D1 后端与 D2 H5、管理端已完成集中验收；微信小程序构建已通过，但设备行为尚未验收
> 支付环境：本指南只使用 `simulation`，支付宝 Sandbox 在 D3.3 单独验收

## 1. 验收目标

本次以微信小程序为消费者主线，确认同一套服务端事实在微信运行时可以连续完成“资金与预算 → 需求与候选 → 本人确认 → 模拟支付 → 意外支出调整 → 取消退款 → 恢复查看”。商户处理和审核证据仍在管理端完成，但必须沿小程序产生的同一订单编号核对。

一次验收只使用新建的隔离场景，不复用已经付款、退款、撤回或报价过期的旧场景。任何步骤失败时先保存第一条错误、页面截图和业务编号，不删除数据、不手工改订单状态，也不重新 Seed 同一个场景。

## 2. 开始前准备

1. 确认 `xingzhi/.env` 中 `PAYMENT_MODE=simulation`，并已设置仅供本机使用的 `SEED_DEMO_PASSWORD`。文档和截图中不要记录密码。
2. 在仓库根目录启动完整环境。开发者工具在本机运行时使用默认 API 地址：

   ```zsh
   ./start-xingzhi.zsh --restart --no-browser
   ```

   Windows 使用：

   ```powershell
   .\start-xingzhi.ps1 -Restart -NoBrowser
   ```

3. 打开 `http://localhost:8877/api/health`，确认服务和数据库健康；确认终端中的微信监听构建已经成功，且 `xingzhi/apps/miniapp/dist/weapp/app.json` 存在。
4. 建立一条自动售后场景和一条商户审核场景。把命令中的序号改成未使用的值：

   ```zsh
   pnpm --filter @xingzhi/server db:seed:consumer-scenario weapp-auto-20260922-01 2026-09-22 complete automatic
   pnpm --filter @xingzhi/server db:seed:consumer-scenario weapp-manual-20260922-01 2026-09-22 complete merchant-review
   ```

5. 保存两次命令输出的消费者邮箱、预算周期、测试商户、审核者、商品和报价标识。登录密码取本机 `.env`，不得抄进验收记录。
6. 在微信开发者工具导入 `xingzhi/apps/miniapp`。项目配置会读取 `dist/weapp`，本地调试 API 为 `http://127.0.0.1:8877`；保持“不校验合法域名”仅用于本机开发者工具调试。登录后到“我的 → 应用设置 → 演示环境”核对页面显示的 API 地址，避免使用上一次构建残留的地址。
7. 同时打开管理端 `http://localhost:5174`，准备商户和审核者登录。管理端账号使用场景输出或基础账号，密码同样取本机 `.env`。

## 3. 开发者工具主线验收

先使用自动售后场景的消费者账号登录。每完成一个关键节点，记录页面显示的周期、意图、订单、支付操作和退款标识；页面没有展示某项标识时，可在管理端或审核导出中补录，不能自行编造。

| 步骤 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| 1 | 登录并进入首页、计划、账目、我的五个标签页 | 页面均可打开；账户属于当前消费者；未来收入、待到账退款和信用额度没有计入当前现金 |
| 2 | 打开当前预算周期和资金影响 | 基准数据可解释为可用现金 2000 元、必要支出 900 元、储蓄目标 500 元、可调支出 400 元，可支配金额 200 元 |
| 3 | 从已有计划项目进入候选，选择场景商品并核对报价 | 原估算 80 元被正式报价 99 元替换，可支配金额为 181 元；页面没有把 80 元和 99 元重复扣除 |
| 4 | 建立待确认购买意图 | 购买确认页显示商品、99 元报价、报价有效期和资金/预算/报价版本；此时还没有订单和支付 |
| 5 | 点击“确认建立订单”，随后立即再点或返回重复尝试 | 最终只有一笔订单；页面明确说明建单不等于支付 |
| 6 | 在订单详情选择“继续付款交接”并完成本地模拟付款 | 返回订单详情后会主动刷新；支付状态最终为已支付，环境显示本地模拟，退出详情再进入仍是同一订单 |
| 7 | 返回计划，记录 400 元临时必要支出并评估影响 | 原 181 元余量变为 219 元缺口；系统只给出调整方案，没有静默改动正式预算或订单 |
| 8 | 选择一个方案并在系统确认框中明确确认 | 进入调整结果页；计划变化、订单善后和退款状态分开显示，未被选中的方案没有执行 |
| 9 | 若第 8 步未取消已付订单，从订单详情提交取消退款 | 先展示费用与预计退款，再要求本人确认；提交后进入处理进度或退款详情，不把“已受理”直接写成“已到账” |
| 10 | 等待 Worker 处理后返回订单详情和退款详情 | 自动分支最终显示订单已取消、渠道处理完成和已核验到账金额；首页、账目和周期复盘使用同一事实 |
| 11 | 关闭并重新打开小程序，重新登录后进入订单列表 | 原订单、支付、退款与时间线可恢复；没有因为重登产生新订单或新退款 |

若场景商品或预算初值与表中数字不同，应停止本次验收并核对是否登录了错误账号或复用了旧场景，不用修改数据库把画面凑成预期结果。

## 4. 人工处理分支与跨角色核对

退出自动场景账号，使用商户审核场景的消费者账号重复第 3 节第 1—6 步，然后从订单详情提交取消退款。

1. 小程序应显示“等待商户处理”或等价的处理中状态，不能提前显示退款完成。
2. 用场景对应商户登录管理端。新订单列表必须出现该订单，详情中的消费者脱敏信息、商品、金额、本人确认版本、支付状态和业务编号应与小程序一致。
3. 在商户工作台批准取消，并按用户已确认范围创建固定退款批次。重复点击或刷新后不得产生第二个退款批次。
4. Worker 完成后回到小程序订单页。页面重新显示时应主动刷新，最终展示已取消和已到账退款；若仍显示旧状态，手动下拉/重新进入后应恢复，且不能生成新操作。
5. 用场景对应审核者登录管理端。只能看到明确分配的预算周期；沿同一订单编号检查资金版本、预算版本、确认、支付、商户操作和退款资金事件。
6. 分别生成 JSON 与 HTML 证据。页面与导出中的订单编号、金额、状态和时间线应一致；导出不得包含登录密码、支付密钥、完整账户号或模型私有推理。

## 5. 微信运行时与界面专项检查

以下检查只做一轮，每项选择一个代表页面，不需要把所有页面在所有尺寸重复遍历。

| 检查项 | 操作 | 通过标准 |
| --- | --- | --- |
| 冷启动与首屏 | 清除本次小程序缓存并重新编译，从登录页进入首页一次 | 没有持续白屏、明显卡死或图片长时间空缺；若开发者工具给出下载、解析或渲染告警，保存原始记录 |
| 360px 窄屏 | 选择接近 360px 宽的模拟设备，查看首页、购买确认、订单详情 | 金额、状态、按钮和长业务信息不横向溢出；主要按钮可点击 |
| 短屏 | 选择约 360×640 的模拟尺寸，打开五个标签页中的底部操作面板 | 面板主要操作按钮位于微信标签栏上方，不被遮挡；内容可滚动到末尾 |
| 大字号 | 将开发者工具或系统字体调大一级，检查订单详情和退款详情 | 文字可换行，金额与状态不重叠，确认按钮仍可见 |
| 返回刷新 | 从付款交接、处理进度或商户处理后返回订单详情 | 页面读取服务端最新事实，晚到的旧请求不会把新状态覆盖回去 |
| 断网恢复 | 在订单详情断开网络后点击重新加载，再恢复网络并重试 | 显示可读错误；恢复后读取原订单，不新建订单、支付或退款 |
| 会话恢复 | 清除登录态或等待会话失效后访问业务页 | 回到登录页；重新登录后可按业务编号恢复原事实 |
| 重复操作 | 对建单、取消和退款各做一次快速重复点击 | 按钮在处理中不可重复触发；服务端最终只有一个有效业务结果 |

开发者工具不能证明刘海、底部手势区、系统字体和真实网络行为。开发者工具通过后，至少选一台真机重复“登录 → 报价 → 建单 → 模拟付款 → 返回刷新 → 订单恢复”，并再次打开一个底部操作面板。真机必须使用手机可访问的 HTTPS API 和已配置的微信合法域名；不要把 `127.0.0.1` 填给手机。

准备好 HTTPS API 后，用下面的方式重启并重新编译微信产物。把示例域名替换为实际已备案、已加入微信 request 合法域名且手机可以访问的地址：

```zsh
TARO_APP_API_BASE=https://api.example.com ./start-xingzhi.zsh --restart --no-browser
```

Windows PowerShell 使用：

```powershell
$env:TARO_APP_API_BASE='https://api.example.com'
.\start-xingzhi.ps1 -Restart -NoBrowser
```

启动信息和小程序“演示环境”页都应显示同一个 HTTPS 地址。更换地址后必须等待微信监听构建完成并在开发者工具重新编译，不能继续使用旧的 `dist/weapp` 预览。

## 6. 通过标准与记录

- 开发者工具主线第 1—11 步通过；
- 商户人工处理和审核证据能够沿同一订单编号闭环；
- 冷启动和首页没有可复现的下载、解析或图片解码阻断；
- 窄屏、短屏、大字号、返回刷新、断网恢复、会话恢复和重复操作没有阻断问题；

## 7. 常见失败的处理顺序

1. 白屏时先确认 `dist/weapp/app.json` 存在、终端没有 Taro 编译错误，再清除开发者工具缓存并重新编译。
2. 所有接口失败时先检查 `/api/health`、小程序请求地址和开发者工具的域名校验设置；真机则检查 HTTPS、合法域名和局域网/公网可达性。
3. 只有一个页面失败时，保存网络面板中第一条失败请求及响应，不连续点击制造更多操作。
4. 状态与管理端不一致时，以订单编号查询服务端和审核证据，区分页面未刷新、Worker 尚未完成和真实数据错误。
5. 报价过期、场景已结算或账户已撤回时，新建唯一场景重新验收；不要改库恢复旧场景。
