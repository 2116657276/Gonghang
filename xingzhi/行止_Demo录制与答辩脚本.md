# 行止 Demo 录制与答辩脚本

> 用途：工行杯演示视频、现场答辩和最终交付检查
> 主线：微信小程序消费者端；管理网页仅承担商户处理和审核证据
> 状态：脚本已准备，微信设备和支付宝 Sandbox 通过后才能冻结录制

## 1. Demo 要证明什么

行止不是一个普通记账工具，也不只是商品推荐页面。演示需要证明银行微应用可以基于用户明确授权的账户事实，把消费决策前移到“能不能买、怎么买、变化后怎么办”，并在用户确认后形成可追溯的订单、支付和退款证据。

完整故事保持一条主线：用户本月原有 200 元可支配空间，为一个估算 80 元的需求选择 99 元正式报价后，可支配空间变为 181 元；随后新增 400 元必要支出，形成 219 元缺口；系统给出调整方案，由用户明确选择，再把涉及的订单取消退款并交由商户和审核者沿同一业务编号处理、查证。

## 2. 录制前冻结条件

以下条件没有全部满足时不开始正式录制：

- 当前 Git 提交、数据库场景名和构建时间已经记录；录制过程中不临时改代码或数据库。
- 微信开发者工具主线通过，至少一台真机完成规定的最小链路。
- 全新 Sandbox 场景完成同一订单的付款、主动查单、取消退款、退款查单和审核证据。
- 小程序“演示环境”页显示预期 API 地址、支付模式和 Worker 正常状态。
- 管理端商户和审核者账号可登录，并且只看到各自有权访问的订单或预算周期。
- 屏幕、浏览器自动填充、终端和导出文件中没有密码、私钥、完整账户号、付款凭据或无关个人信息。
- 录屏文件夹已准备好，消费者、商户和审核者的关键业务编号已记录在屏幕外的本地便笺中。

## 3. 建议时长与画面顺序

建议主视频控制在 5—7 分钟。不要在视频中等待编译、Seed、模型长响应或渠道轮询；这些准备动作在录制前完成，但不能预先修改交易结果。

| 0:30—1:10 | 预算周期和资金影响 | 2000 元确认现金减去 900 元必要支出、500 元保留目标和 400 元可调支出，得到 200 元可支配空间 |
| 1:10—1:50 | 需求、候选和购买确认 | 原估算 80 元由 99 元正式报价替换，只计算 19 元差额；展示报价、预算和资金版本，强调必须由本人确认 |

## 4. 微信消费者端操作台词

### 4.1 资金事实与预算

打开首页后先进入“我的 → 应用设置 → 演示环境”，快速展示前端形态、API、支付模式和 Worker 状态。随后返回首页和计划页。

建议讲解：

> 行止首先区分已经确认的现金、未来收入、信用额度和退款待到账。只有银行侧或受控 Demo 已确认的资金事实参与“现在能不能买”的判断。当前周期确认现金是 2000 元，扣除必要支出、储蓄目标和可调安排后，剩余 200 元。

### 4.2 候选、报价与本人确认

从已有需求进入候选，选择 99 元商品，停留在确认前核对页面，再创建购买意图并进入购买确认页。

建议讲解：

> 用户原来只是按 80 元估算。取得 99 元正式报价后，系统用正式报价替换估算，只增加 19 元占用，所以可支配金额从 200 元变成 181 元。商品、金额、报价版本和预算版本都需要用户确认，Agent 不能代替用户完成购买授权。

### 4.3 Sandbox 付款与主动查单

只在最终 Sandbox 验收已经通过的情况下录制这一段。点击付款交接，在新标签页打开支付宝沙箱收银台，由用户完成登录和支付；回到原行止页面点击“我已完成操作，主动查单”。

建议讲解：

> 打开收银台不会让本地订单直接变成已支付。行止按原业务号主动查单，并校验订单号、金额和卖家。只有取得明确匹配的渠道结果，订单才进入已支付；未知结果会保留占用并进入复核，不创建第二笔订单。

若 Sandbox 当天不可用，改用 Simulation 场景并在画面上明确说明“本地模拟付款”。不得把 Simulation 结果剪辑成 Sandbox 成功。

### 4.4 计划变化和售后

回到计划，记录 400 元临时必要支出，展示 219 元缺口和可选调整方案。选择会处理当前订单的方案并确认，或从订单详情提交取消退款。

建议讲解：

> 支付完成并不代表计划永远不变。新增必要支出后，系统重新计算出 219 元缺口，只提出可执行方案；用户确认后，涉及原订单的善后继续沿原订单、原退款号处理。退款申请、支付宝渠道成功和银行卡到账是三个不同事实。

## 5. 商户与审核端切换

切换窗口前先隐藏邮箱以外的登录信息，并确认浏览器没有打开密钥或 `.env`。

商户端只展示：新订单列表、订单详情、消费者脱敏标识、商品、金额、确认版本、付款状态、取消决定、退款批次、业务时间线和必要复核入口。不要展开与本次故事无关的旧计划历史。

审核端只展示：本次明确分配的预算周期、订单编号、资金/预算/报价版本、用户确认、支付与退款事件、执行主体和证据导出。优先现场生成 HTML 证据供观众查看，JSON 作为技术附件，不在镜头中滚动大段原始数据。

## 6. 必须保存的证据

录制结束后保存以下材料，但不要提交本地密码或密钥：

- Git 提交号、微信构建时间、开发者工具版本、基础库版本、真机型号与微信版本。
- 微信消费者场景名、预算周期、购买意图、订单、付款操作、取消申请、退款批次标识。
- Sandbox 的支付宝订单号和退款请求号；对外截图可以保留必要的后四至八位，其余部分遮挡。
- 商户订单详情截图、审核周期详情截图、脱敏 HTML/JSON 导出。
- Simulation、Sandbox、微信开发者工具和真机各自的通过/失败结论，不合并成一个模糊的“全链通过”。

## 7. 答辩常见问题口径

**商户数据从哪里来？** 首版只检索提前登记并完成基本规则配置的银行合作商户数据，不声称已经全网接入。竞赛 Demo 使用受控商户和商品样例验证消费者闭环。

**为什么银行要做商品推荐？** 行止把银行已掌握且经用户授权的资金事实用于消费前规划，并把本人确认、支付、退款和计划变化形成同一证据链。银行的角色从支付终点延伸到可解释的消费决策和风险提醒。

**AI 会不会擅自花钱？** AI 可以读取允许的事实、解释候选和生成草稿；商品选择、预算生效、建单、支付和退款都需要结构化本人确认。服务端还校验资金、预算、报价和授权版本。

**余额和流水是真的吗？** 当前竞赛版本使用明确标注的 Demo 银行数据；支付宝 Sandbox 是真实沙箱渠道事实。两者都不能表述为已经接入工行生产账户。

**退款成功为什么没有立刻增加余额？** 支付宝确认退款只代表渠道事实。真实银行卡到账需要银行侧流水或账户事实再次核验；Demo 如生成联动流水，也必须标为 `demo`，不能伪装为 `bank_api`。

**项目如何扩展？** 先扩展合作商户目录和银行适配器，再在相同的授权、版本、幂等和证据边界下接入更多消费场景。当前不为尚未发生的规模问题预建通用平台。
