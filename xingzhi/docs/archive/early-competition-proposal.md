## 一、作品摘要

智能体正在从“回答问题”走向“替用户办事”。在旅行、餐饮、零售和生活缴费等场景中，一个自然语言目标可能被拆解为检索、比价、下单、支付、预约、履约、退款和售后，并由多个Agent、商户和支付参与方协作完成。新的风险不只发生在支付时：授权可能被下游任务过度继承，外部内容可能诱导Agent偏离原意，用户改变计划后旧任务仍可能继续执行，已经付款的订单又分别处于不同的取消、退款和履约状态。

行止将授权前、执行中、用户退出和资金善后组织为一套可审计协议。授权前生成有金额、商户、商品类别、有效期和二次确认条件的意图凭证；执行中用任务图约束权限继承并检查意图漂移；用户退出时以高优先级熔断事件冻结未执行节点；已经发生的订单按商户规则和支付状态进入取消、退款跟踪、售后或争议路径。系统把任务状态与资金状态分开计算、并列展示，使用户能够理解“智能体还能做什么、哪些任务已经停止、钱在什么状态、下一步由谁处理”。

行止的差异化不在于再做一个智能支付授权页面、反诈模型或客服机器人，而在于把“撤回”定义为具有范围、时间、优先级、幂等标识和回执要求的协议事件。项目中的“行迹”是过程留痕与闭环凭证模块，记录用户意图、授权版本、Agent动作、规则依据、外部回执和责任边界。对于银行或支付服务方，行止提供授权状态可视化、意图漂移提示、撤回留痕、退款进度协同和争议材料组织；任何真实支付、清算、退款和账户处理仍由依法具备资质的机构完成。

**关键词：** AI Agent；智能体支付；意图凭证；最小授权；任务熔断；退款跟踪；行迹凭证；数字金融

**一句话价值主张：** 当AI替人消费时，用户不仅要能授权付款，也要能限制、看见、叫停并完成善后。

## 二、背景、机会与问题定义

### 2.1 从“能支付”到“能善后”

智能体支付正在从概念进入真实场景。中国银联发布的智能体支付开放协议框架 APOP，围绕身份、意图、过程等信任问题建立支付侧能力；中国支付清算协会于 2026 年发布的智能体支付应用自律公约也强调用户授权边界、支付意愿核实、分级分类管理、人工服务与回退机制。[公开可核验：参考资料 3、4] 这说明行业已开始认真解决“谁在付、为何付、是否有授权”的问题。

但支付本身不是消费任务的终点。以一次旅行安排为例，用户的一句“帮我安排周末出行”可能触发机票、酒店、景点、交通、餐饮等多个任务。它们并不处于同一平台，也不具有相同的可逆性：

- 有些任务尚未支付，可以直接停止；
- 有些订单已支付但仍处于商户可取消窗口；
- 有些订单已提交取消，退款却需等待商户、收单机构和支付链路的状态变化；
- 有些服务已履约或进入不可逆环节，无法“撤销”，但用户仍需要明确的售后、争议与凭证路径。

如果没有统一编排，用户往往只能在多个 App、多个 Agent 和多条客服链路间追问“我的钱去哪了”。此时，单纯的支付意图校验已无法回答用户最关心的四个问题：

1. 我点击退出后，哪些后续任务已经停止？
2. 已经付出的哪几笔钱仍可取消或退款？
3. 哪些事项不能撤销，原因是商户规则、履约状态还是支付状态？
4. 如果发生争议，我能否获得一份完整、可信、可提交的过程凭证？

### 2.2 问题边界

行止聚焦“智能体支付任务的可控执行与可逆退出”而非泛化金融安全，具体定义为：

> 在用户授权智能体完成消费任务的过程中，如何通过最小授权、意图一致性检查和可审计熔断，限制未授权动作；并在用户停止、修改或退出时，协调任务冻结、取消、退款、售后与证据留存，使任务和资金分别进入可解释的稳定状态。

项目范围包括意图凭证、权限继承、任务状态编排、意图漂移检查、退出请求处理、支付与商户状态展示、经授权的接口模拟、流程留痕和争议材料组织。项目不包括替用户绕过商户规则、直接修改支付清算结果、承诺退款到账、替代银行处理争议、自动处置账户，或在未授权情况下访问账户与订单数据。

### 2.3 现有体验的四个断裂

| 断裂 | 用户面对的现象 | 为什么传统页面解决不了 | 行止的解决方向 |
| --- | --- | --- | --- |
| 任务断裂 | 一个自然语言需求被多个 Agent 和商户拆分执行 | 用户只看到订单，不知道任务之间的依赖关系 | 用任务图展示“谁依赖谁、能否停止” |
| 授权断裂 | 用户只确认一次，权限却被多个下游任务继续使用 | 单笔支付确认不能表达任务级预算、范围和有效期 | 建立意图凭证和最小授权继承 |
| 状态断裂 | 支付成功、订单取消、退款到账分属不同状态 | “已支付”不等于“不可取消”，“已取消”也不等于“已退款” | 建立统一退出状态机 |
| 责任断裂 | 银行、商户、平台、Agent 各自只解释一段 | 用户不知道下一步该找谁 | 明确每一步的责任主体和可操作入口 |
| 证据断裂 | 事后需要投诉或沟通时，缺少完整时间线 | 截图零散、难以核验、易遗漏授权与规则 | 由“行迹”模块生成结构化闭环凭证 |

## 三、产品目标与角色设计

### 3.1 产品目标

行止的第一目标不是提高支付次数，而是使智能体交易在授权、执行、退出和善后阶段保持可控。系统以“授权有界、执行可见、停止扩散、资金可见、过程可证”为五项基本目标：

1. **授权有界：** 用户明确预算、商户、类别、时限和二次确认条件，下游Agent只继承必要权限。
2. **执行可见：** 用户能够查看任务依赖、当前动作、权限来源和外部回执。
3. **停止扩散：** 用户提出退出后，冻结尚未开始或尚未提交的下游任务，防止Agent在旧目标下继续下单。
4. **资金可见：** 根据支付、商户取消窗口和履约状态，将已发生节点导向取消、退款跟踪、售后或争议路径。
5. **过程可证：** 将用户意图、授权版本、Agent动作、规则依据、接口回执和最终状态生成闭环凭证。

### 3.2 角色与责任

| 角色 | 在行止中的权利 | 在行止中的责任 | 行止不替代的职责 |
| --- | --- | --- | --- |
| 用户 | 发起退出、选择保留任务、查看资金状态、授权共享凭证 | 确认退出范围与账户验证 | 不替用户规避已接受的商户规则 |
| 用户侧 Agent | 提交任务图、接受冻结/恢复指令、返回动作状态 | 按最小权限执行，不得在冻结后继续新建交易 | 不获得无限支付或退款权限 |
| 商户/平台 | 提供订单状态、取消窗口、退款/售后结果 | 按自身规则处理订单与售后 | 不由行止决定其退款政策 |
| 银行/支付机构 | 提供依法合规的账户、交易和退款状态服务 | 独立承担账户与支付处理责任 | 不由行止触发未经确认的资金变动 |
| 行止编排层 | 统一状态、协调接口、生成解释与凭证 | 记录事实、提示边界、保护数据 | 不直接持有资金，不替代持牌支付服务 |

## 四、核心机制：意图凭证 + 任务图 + 退出状态机 + 闭环凭证

### 4.1 意图凭证与最小授权

每次智能体消费任务在产生可对外执行的动作前，都应形成一份结构化意图凭证。凭证不保存完整对话，而是把用户已经确认的边界转化为机器可校验字段。

| 字段 | 示例 | 约束作用 |
| --- | --- | --- |
| 任务目的 | 完成周末杭州两日行程 | 防止下游任务脱离原目标 |
| 金额范围 | 总预算不超过3000元 | 超限时必须重新确认 |
| 商户与类别 | 交通、住宿；不含购物与增值会员 | 阻断未经授权的类别扩张 |
| 有效期 | 当前行程完成或用户撤回前 | 避免旧授权长期有效 |
| 自动执行范围 | 比价可自动，付款需二次确认 | 区分建议、下单和支付权限 |
| 停止条件 | 用户退出、预算超限、意图漂移或接口异常 | 触发任务熔断和人工接管 |

下游Agent只能继承完成当前节点所需的最小字段。任何新增类别、提高预算、变更收款方或延长有效期的动作，都必须产生新的用户确认和凭证版本，不能通过修改旧记录静默扩权。

### 4.2 消费任务图

用户的消费目标被表示为一个可读的任务有向图，而不是一串不可解释的 API 调用。每个节点包含任务类型、执行主体、支付状态、商户规则状态、履约状态、可逆等级和上游依赖关系。

    用户目标：周末杭州两日行程
    ├─ 交通：高铁票
    │  └─ 已支付 / 待出行 / 以商户规则判断是否可退改
    ├─ 住宿：酒店
    │  └─ 已支付 / 在免费取消窗口 / 可申请取消
    ├─ 景点：门票
    │  └─ 未支付 / Agent 待确认 / 可直接停止
    └─ 本地交通：接驳预约
       └─ 未提交 / 依赖到站时间 / 可直接停止

用户点击“退出此行程”后，系统先冻结仍处于“待执行、待确认、未提交”的节点，再按已支付节点的商户规则、支付状态和履约状态进入不同路径。冻结不等同于删除历史记录：系统保留已发生动作的时间线，以便用户理解和后续举证。

### 4.3 可逆等级

“可逆”在行止中是状态化、条件化的能力，而不是对用户作出的绝对承诺。

| 等级 | 条件 | 系统可做的事 | 系统不能承诺的事 |
| --- | --- | --- | --- |
| R0：未执行 | 未创建订单或未提交支付 | 停止 Agent 后续动作，关闭任务 | 不可证明外部系统从未收到任何请求，需记录接口回执 |
| R1：未支付订单 | 已生成订单但未完成支付 | 请求商户取消或标记失效 | 不替商户绕过库存、价格或有效期规则 |
| R2：已支付可取消 | 支付完成且仍处于取消窗口 | 发起取消请求，跟踪退款处理 | 不承诺退款到账时点或全额退款 |
| R3：退款处理中 | 商户已受理或支付链路处理中 | 展示退款参考号、责任方和进度 | 不篡改支付机构状态 |
| R4：履约/不可逆 | 服务已履约、过了规则窗口或存在争议 | 引导售后/争议流程，生成材料包 | 不承诺撤销已履约服务或自动追回资金 |

### 4.4 退出状态机

    E0 正常执行
      ↓ 用户发起退出
    E1 退出请求已记录
      ↓ 冻结可停止节点 + 拉取已发生节点状态
    E2 任务分类完成
      ├─ R0/R1 → E3 已停止或已取消
      ├─ R2 → E4 取消处理中
      ├─ R3 → E5 退款跟踪中
      └─ R4 → E6 售后/争议待处理
      ↓ 所有节点到达稳定状态或转入明确人工通道
    E7 退出闭环

“稳定状态”并不一定是“退款到账”。例如酒店订单可能处于“商户已受理取消、支付退款处理中”，此时行止应把退出任务标记为“已转入退款跟踪”，而非错误地显示“已退款”。这种状态区分是项目可信度的关键。

### 4.5 行迹：行止的闭环凭证模块

行迹不是另一套独立产品，而是行止内部的“事实留痕与闭环凭证”能力。其输出是一份用户可阅读、可选择分享的过程摘要：

| 凭证字段 | 示例 | 作用 |
| --- | --- | --- |
| 退出意图 | 用户于 14:05 发起“停止整个周末行程” | 说明用户请求的范围 |
| 任务快照 | 4 个节点、2 个已支付、2 个未提交 | 说明任务结构 |
| 规则依据 | 酒店处于免费取消窗口；车票以平台退改规则为准 | 区分规则与系统判断 |
| 系统动作 | 冻结 2 个待执行节点，向 1 个商户发起取消请求 | 可审计的动作记录 |
| 外部回执 | 商户受理/拒绝、退款参考号、接口时间 | 说明后续责任与状态 |
| 最终归属 | 已停止、退款处理中、需售后等 | 让用户知道任务是否真正闭环 |

凭证采用最小必要信息，默认隐藏支付账户、完整交易号、身份证明、详细行程和商户联系人；用户在需要向银行、商户或客服提交时，才能选择特定字段范围和有效期。

## 五、产品架构与数据设计

### 5.1 五层架构

    交互层
    ├─ 用户退出面板
    ├─ 任务图与资金状态时间线
    └─ 闭环凭证与人工帮助入口
             ↓
    编排层
    ├─ 任务依赖图服务
    ├─ 退出状态机
    ├─ 可逆等级分类器
    └─ 通知与超时管理
             ↓
    规则层
    ├─ 用户授权与撤回范围
    ├─ 商户取消/退款规则映射
    ├─ 支付状态映射
    └─ 责任边界与风险提示
             ↓
    适配层
    ├─ Agent 执行器适配器
    ├─ 商户订单适配器
    ├─ 银行/支付状态适配器
    └─ 人工客服/争议工单适配器
             ↓
    治理层
    ├─ 授权记录
    ├─ 事件日志
    ├─ 最小化数据存储
    └─ 审计与凭证生成

初赛原型只使用模拟适配器和模拟订单状态，展示“不同外部系统返回不同结果时，行止如何分类、提示和闭环”。任何真实支付接口、商户接口或银行接口的接入均属于后续合作事项，不在原型中模拟成已上线能力。

### 5.2 最小数据字典

| 数据类别 | 必要字段 | 原型处理方式 | 不采集或默认脱敏的字段 |
| --- | --- | --- | --- |
| 用户授权 | 匿名用户 ID、退出范围、确认时间、有效期 | 生成随机 ID 和时间戳 | 身份证号、银行卡号、生物特征 |
| 任务节点 | 匿名任务 ID、类型、依赖关系、执行状态 | 用模拟任务图生成 | 完整聊天记录、无关个人偏好 |
| 订单状态 | 匿名订单标识、支付/取消/履约/退款状态 | 使用模拟商户回执 | 完整订单号、收货地址、乘车人信息 |
| 规则信息 | 规则版本、取消窗口、状态说明、来源 | 记录公开规则或模拟规则版本 | 未授权抓取的商户内部规则 |
| 凭证日志 | 请求、动作、回执、责任方、时间 | 采用不可修改的事件序列展示 | 账户明细、敏感附件全文 |

### 5.3 可解释分类与意图漂移检查

行止不以大模型直接决定“能不能付款”或“能不能退款”。分类依据应当是结构化事实和明确规则：

1. 当前动作是否处于意图凭证允许的目的、金额、商户、类别和有效期内；
2. 权限是否来自有效的上游授权，是否发生未经确认的继承或扩张；
3. 该节点是否已经开始执行，是否仍存在下游依赖；
4. 是否已完成支付，支付状态来自何处；
5. 商户是否公开或接口返回可取消窗口；
6. 服务是否已经履约，是否需要进入售后或争议处理；
7. 外部接口是否成功响应，若失败是否需要人工接管。

大模型可以把“帮我安排一次经济型周末出行”解析为待确认的意图字段，也可以把“我不去了，全部停掉”解析为退出范围建议；但金额、商户、类别、授权继承、状态转换和外部调用必须由规则引擎、权限校验和可审计接口决定。外部页面内容不得直接改变用户授权。

## 六、Demo 原型设计

### 6.1 Demo 目标

在 4—6 分钟内，让评委看到行止不是“取消订单按钮的集合”，而是一套能够管理多 Agent、多订单、多支付状态的退出编排服务。核心可视化是：用户的一次退出请求如何停止后续行动、识别资金状态、处理例外并生成闭环凭证。

### 6.2 主场景：受控旅行委托与临时退出

以下情境完全为 [原型假设]，不对应真实商户、支付机构或退款规则。

用户先授权智能体完成“总预算不超过 3000 元、仅限交通/住宿/门票、有效期 24 小时”的杭州两日游委托。执行过程中，系统既要阻止越出意图凭证的动作，也要在用户临时退出后完成任务熔断与资金善后。

| 节点 | 执行前约束或初始状态 | 系统预期路径 |
| --- | --- | --- |
| 高铁票 | 在授权类别内，已支付，尚未出行 | 退出后转入“规则核验/售后路径”，不承诺退款 |
| 酒店 | 在授权类别内，已支付，模拟处于免费取消窗口 | 退出后发起取消，进入“退款处理中” |
| 景点门票 | 已选定但尚未支付 | 退出后立即停止，不再提交订单 |
| 接驳车 | 待预约，依赖到站时间 | 退出后立即停止并标记“未发生资金动作” |
| 旅行会员升级 | 外部页面诱导 Agent 购买，超出授权类别 | 权限校验直接拦截，必须重新征得用户确认 |

### 6.3 Demo 脚本

1. 用户输入“帮我安排一次经济型杭州两日游”。行止将自然语言整理为待确认的意图凭证：总预算 3000 元、交通/住宿/门票三类、24 小时有效、单笔超过 1200 元需二次确认。
2. 用户确认后，任务图开始执行。外部页面出现“开通旅行会员可提高成功率”的诱导内容，Agent 尝试新增会员购买节点；权限校验发现其超出允许类别，予以拦截并生成异常说明。
3. 高铁票和酒店完成模拟支付，门票尚未支付，接驳车仍处于待预约状态。页面同步显示每个节点的授权来源、资金状态和下游依赖。
4. 用户说：“行程有变，杭州两日游全部停掉，不要再下单。”行止将其解析为高优先级退出事件，并弹出范围确认，允许用户选择“全部退出”或保留特定节点。
5. 用户确认后，系统首先熔断未支付门票和待预约接驳车，阻止所有下游新动作；随后分别向已支付节点查询规则并发起允许范围内的取消请求。
6. 酒店模拟回执为“取消已受理、退款待跟踪”；高铁票规则未能确认，系统转入人工核验或售后路径，不擅自承诺退款。
7. 用户打开双时间线，分别查看“任务是否停止”和“资金是否闭环”；系统生成脱敏行迹凭证，列明原始授权、越权拦截、退出意图、熔断动作、外部回执和未闭环事项。

### 6.4 原型页面清单

| 页面 | 关键内容 | 评审亮点 |
| --- | --- | --- |
| 意图授权页 | 目的、预算、类别、有效期、二次确认阈值 | 把自然语言委托压缩为机器可校验的授权边界 |
| 任务总览页 | 用户目标、任务图、节点状态 | 一句话任务如何被拆成可治理的结构 |
| 异常解释页 | 越权动作、权限来源、拦截理由、重新授权入口 | 展示对意图漂移和外部诱导的可解释防护 |
| 退出确认页 | 退出范围、保留项、授权确认 | 退出不是 Agent 擅自停止，而是用户可控 |
| 退出时间线 | 停止、取消、退款、售后各自状态 | 不把“取消”误写成“退款成功” |
| 责任解释页 | 每个节点的规则、责任方、下一步 | 不推诿、不越权、可理解 |
| 行迹凭证页 | 完整时间线、最小字段、分享控制 | 为后续客服、商户沟通或争议提供基础材料 |
| 管理/审计页 | 匿名事件日志、失败重试、人工接管 | 体现可运营、可审计的金融科技能力 |

## 七、银行协同与服务价值

### 7.1 银行的合理角色

行止不经营支付业务，不直接保管或划转资金。支付账户管理、支付处理、收单、清算等核心环节应由依法具备资质的机构承担；这是智能体支付自律规则强调的主体责任边界。[公开可核验：参考资料 4] 行止在银行侧的合理价值主要有四类：

1. **支付状态可视化。** 将用户授权的交易状态与任务退出状态关联展示，降低“付款后信息失联”的体验成本。
2. **授权撤回留痕。** 对用户何时、以何种范围撤回 Agent 任务授权形成可审计记录。
3. **退款进度协同。** 在支付机构可提供的状态范围内，帮助用户理解退款是否已由商户受理、是否进入支付链路、是否已到账。
4. **争议材料组织。** 在用户选择授权的前提下，生成包含交易标识脱敏信息、时间线和商户回执的材料摘要，辅助后续人工服务。

银行不应也不需要借由行止决定商户是否必须退款、擅自终止已完成支付或绕过正常投诉处理机制。系统在每一个“不可逆”或“规则不明确”节点明确展示人工服务入口和责任主体。

### 7.2 三方价值

| 参与方 | 核心收益 | 价值边界 |
| --- | --- | --- |
| 消费者 | 少找入口、少看不懂的状态、知道钱和任务分别停在哪里 | 不承诺所有订单可撤销或退款 |
| 商户/平台 | 收到结构化、范围明确的取消请求，减少重复客服沟通 | 保留自身经营规则、售后规则和最终处理权 |
| 银行/支付机构 | 将“交易状态”升级为“消费任务退出状态”，增强用户信任 | 仍独立处理账户、支付、退款和争议 |

### 7.3 未来落地路径

第一阶段面向单一旅行场景，以模拟订单和支付状态完成原型验证；第二阶段扩展到餐饮、票务和生活服务，形成统一任务状态标准；第三阶段在机构合作、用户授权、安全评估和接口规范具备条件后，对接真实 Agent、商户和支付状态服务。产品的长期竞争力不在于绑定某一个商户，而在于建立跨场景的“退出状态语言”和可审计闭环能力。

## 八、创新性与差异化

| 相关方向 | 常见关注点 | 行止的差异 |
| --- | --- | --- |
| Agent 支付授权 | 谁能付、付什么、限额多少 | 将授权约束延伸至任务执行、撤回、熔断与善后全过程 |
| 反欺诈/风控 | 识别异常交易、阻断风险 | 服务真实用户主动退出，兼顾便利性与安全性 |
| 电商/旅行售后 | 单一订单退款或客服问答 | 管理多 Agent、多商户、多状态的任务依赖图 |
| 电子存证 | 事后证明发生了什么 | 将证据嵌入实时退出流程，形成可执行闭环 |
| 通用 Agent 编排 | 如何完成任务 | 解决任务中断后如何安全、可解释地收尾 |

本项目的五项创新为：

1. **意图凭证化。** 将自然语言任务压缩为目的、金额、对象、期限和升级条件等可校验字段，限制权限在多 Agent 之间无边界扩张。
2. **“退出权”产品化。** 将用户的停止、修改和善后权利从零散的取消入口升级为高优先级协议事件。
3. **任务—资金双视角。** 同时展示任务是否停止和资金是否闭环，避免把“已停止”误写成“钱已退回”。
4. **条件化可逆模型。** 以 R0—R4 表示不同可逆等级，诚实呈现商户规则、履约状态和支付状态带来的边界。
5. **行迹内嵌式凭证。** 在授权、执行、拦截和退出过程中持续组织动作、回执和责任信息，降低事后举证成本。

行业正在建设身份、意图和支付过程的可信机制，行止选择在此基础上补足“退出后的过程信任”，使智能体支付从“能完成一笔交易”进一步走向“能稳妥结束一件事”。[公开可核验：参考资料 3]

## 九、合规、隐私与安全设计

### 9.1 权限与支付边界

1. 用户必须在退出范围确认后，系统才能向 Agent 或商户适配器发出停止、取消或查询请求。
2. 用户撤回的是对 Agent 的后续任务授权；该撤回不当然使已完成支付、已履约服务或已生效商户合同自动失效。
3. 涉及账户、支付、清算和退款的真实处理，必须由持牌金融机构、支付机构和合规商户系统完成。
4. 高风险或不确定状态必须转人工，不允许大模型基于文本自行做出资金处置决定。

### 9.2 数据与隐私保护

| 原则 | 设计实现 |
| --- | --- |
| 最小采集 | 仅保存完成退出编排所需的匿名任务、状态、规则版本和回执摘要 |
| 目的限定 | 数据只用于退出处理、用户查询、审计和经授权的争议材料 |
| 可撤回 | 用户可以撤回对特定凭证或第三方共享的授权；撤回后停止新增共享 |
| 默认脱敏 | 交易号、订单号、地址、乘客信息、账户信息默认掩码展示 |
| 权限分层 | 用户、客服、商户、银行服务人员各自只能访问职责范围内的数据 |
| 事件审计 | 每个状态切换记录来源、时间、请求者、回执和失败原因 |

### 9.3 失败模式与处理

| 失败模式 | 系统表现 | 正确处理方式 |
| --- | --- | --- |
| Agent 不响应冻结指令 | 节点显示“停止请求未确认” | 不伪造已停止状态；提示用户转人工并保留日志 |
| 商户接口超时 | 取消状态未知 | 进入“待确认”，设置重试和人工服务入口 |
| 商户拒绝取消 | 返回规则或拒绝原因 | 转入售后/争议路径，不绕过商户规则 |
| 退款状态延迟 | 商户已受理但支付状态未更新 | 显示“退款跟踪中”，不能写为“已到账” |
| 用户退出范围模糊 | 例如“把不必要的都取消” | 要求用户在任务图上确认范围，避免误停必要事项 |
| Prompt Injection 或异常指令 | 外部内容诱导 Agent 继续下单 | 退出状态优先级高于一般任务；新任务须重新获得用户确认 |
| 授权过期或权限被下游扩张 | 节点引用失效或不匹配的意图凭证 | 拒绝执行并展示授权链；要求用户重新确认，不静默续权 |
| 重复退出或重复回执 | 同一请求被多次提交或商户重复返回结果 | 使用幂等键合并事件，保留原始回执并标记重复来源 |

## 十、实施与验证计划

### 10.1 10 周原型路线

| 阶段 | 周期 | 核心产出 | 验收标准 |
| --- | --- | --- | --- |
| 场景与规则访谈 | 第 1—2 周 | 授权—执行—退出全旅程、访谈提纲、状态字典 | 确认至少 3 类授权边界和 4 种退出结果 |
| 交互原型 | 第 3 周 | 意图授权、任务图、异常解释、退出确认、时间线与凭证页面 | 用户能说清“允许做什么、将停止什么” |
| 状态机开发 | 第 4—5 周 | 意图凭证校验、R0—R4 分类、事件日志、幂等模拟回执 | 越权动作被拦截；同一节点不显示矛盾状态 |
| 适配与演示 | 第 6—7 周 | 模拟 Agent、商户、支付状态适配器 | 完成端到端旅行场景 Demo |
| 可用性测试 | 第 8 周 | 用户理解度、状态措辞和权限反馈 | 记录至少 5 名测试者的问题 |
| 安全与答辩打磨 | 第 9—10 周 | 异常场景、合规说明、Demo 脚本、计划书更新 | 不出现“保证退款”“自动扣款”等越权表述 |

### 10.2 后续评估指标

初赛阶段不宣称真实业务效果。若后续取得合规测试条件，可从以下指标验证：

| 维度 | 指标 | 解释 |
| --- | --- | --- |
| 退出完整性 | 退出请求后被成功冻结的待执行节点比例 | 仅统计具备接口回执的节点 |
| 状态清晰度 | 用户正确理解退款/售后状态的比例 | 通过可用性测试测量 |
| 处理效率 | 用户找到责任方和下一步入口的时间 | 不等同于商户处理时效 |
| 凭证可用性 | 客服/用户认为材料完整可读的比例 | 通过匿名访谈验证 |
| 风险控制 | 未经二次确认的新增下游动作数 | 目标是零，但需在真实测试中验证 |

## 十一、待访谈与待验证数据清单

### 11.1 访谈对象

| 对象 | 建议数量 | 要验证的问题 | 禁止收集的信息 |
| --- | --- | --- | --- |
| 经常使用旅行/生活服务 App 的用户 | 5—10 人 | 何时会取消、最不理解哪些状态、怎样才算退出完成 | 账户密码、身份证、完整订单记录 |
| 商户或平台运营/客服人员 | 1—3 人 | 订单状态、取消窗口、退款与售后分别由谁处理 | 内部接口密钥、未公开规则 |
| 银行或支付服务从业者 | 1—2 人 | 哪些交易状态可向用户解释、哪些边界必须由持牌机构处理 | 内部风控规则、客户数据 |
| Agent 开发者/产品人员 | 1—3 人 | 如何冻结任务、如何返回动作回执、异常如何上报 | 生产环境密钥、真实用户日志 |

### 11.2 需补齐的材料

1. **用户退出访谈：** 近 6 个月内发生过的取消、退款、售后体验；不记录真实订单号和金额。
2. **状态映射样本：** 以公开规则、模拟订单或书面许可材料整理“未支付、可取消、退款处理中、已履约”的状态转换。
3. **商户规则样本：** 旅行、票务、餐饮、零售中不同取消窗口的公开规则链接和版本日期。
4. **Agent 行为日志：** 只保留任务 ID、动作类型、时间、成功/失败回执和依赖关系的模拟日志。
5. **理解度测试：** 让测试者阅读退出时间线，记录其是否能回答“钱在哪里”“谁负责”“我还需要做什么”。
6. **合规复核意见：** 请具备支付、数据合规或金融科技经验的老师/从业者审阅“用户撤回授权不等于撤销已履约服务”的边界表述。

### 11.3 访谈使用原则

访谈与测试须取得知情同意，只记录结论和匿名角色。真实聊天内容、账户信息、订单详情、支付流水和商户内部资料均不得进入参赛计划书、Demo 或公开展示。所有展示数据均需标为“模拟数据”或“经授权脱敏数据”。
