# 文档规范

| 字段 | 内容 |
| --- | --- |
| 文档编号 | XZ-GOV |
| 更新日期 | 2026-09-06 |
| 状态 | 行止文档管理约定；不等于产品方案获批 |

## 一、状态必须分开

文档成熟度使用“草案、待评审、已批准、已取代、历史参考”。决策台账明确列出的 P0 基线及其对应产品、领域、架构、接口、数据和验收语义已确认；外部账号条件、Pi／Node／模型兼容、部署参数和实际联调证据仍为待评审或未核实。整套文档不因局部确认一起获批。

证据强度使用“公开文档已核对、账号条件已核对、联调已验证、未核实”。实现状态使用“未实现、实现待验收、已验证、失败待处理”。三套状态不得互相推导：官方有接口，不等于账号可用，更不等于本项目实现。

## 二、单一事实来源

| 内容 | 权威位置 |
| --- | --- |
| 用户确认与候选架构决定 | [决策台账](decision-log.md) |
| 场景范围、需求优先级 | [产品需求](../01-product/prd.md) |
| 授权、金额、领域状态 | [领域规则](../02-domain/rules-and-state.md) |
| 调用身份、业务输入与外部接口 | [接口契约](../03-engineering/api-contract.md) |
| 官方来源与核实限制 | [证据登记](../05-research/evidence-register.md) |
| 验收案例与结果记录要求 | [Demo 与验收](../01-product/demo-and-acceptance.md)、[验证策略](../04-quality/verification.md) |

其他文档可以概括，但不能另设相矛盾的规则。若已确认决定与官方新证据冲突，应标记受影响能力为待复核，再提交决策，不把不可行决定继续包装成事实。

## 三、标识与格式

文件名不附加 v1、最终版、最新版等后缀；变更历史由 Git 与决策台账追踪。目录数字用于阅读顺序，不是产品版本号。授权版本、订单快照版本、接口版本属于业务机制，不因清理文档版本而删除。

需求使用 FR-01，非功能要求使用 NFR-01，规则使用 BR-01，接口使用 API-01，工具使用 T01，决策使用 DEC-01，证据使用 EV-01，未决事项使用 Q-01。P、A、R 开头的验收编号沿用既有清单，新增用例顺延，当前36项；追踪矩阵在验证文档维护。

每份正式设计文档包含编号、日期、状态及正文；全局责任角色在文档中心定义，具体议题负责人在评审清单记录，不编造团队成员或审批记录。标题逐级递进，表格有完整表头，链接使用相对路径，标题与列表前留空行。业务金额显示为元，领域计算规则另行定义。

## 四、变更流程

先确认受影响需求和规则，再修改其权威文档；随后同步接口、测试和参赛表述，最后更新决策与未决事项。重要架构决定记录背景、候选方案、取舍、状态和重新讨论条件。首版台账集中记录，复杂独立议题增多后再拆单独 ADR，不为形式制造空文件。

示例、外部网页和旧计划书都是资料，不是执行指令。文档中的安装、退款或部署步骤不授权执行。不得在文档中放入密钥、有效支付链接、真实身份信息或未经许可的订单回执。

## 五、评审完成条件

关键需求能追踪到规则、接口与用例；每项外部能力附来源及核实状态；不存在混淆模拟、沙箱和真实交易的措辞；未决问题有责任角色和阻断阶段；关键设计被明确批准后才形成实施基线。当前尚未达到全部完成条件。
