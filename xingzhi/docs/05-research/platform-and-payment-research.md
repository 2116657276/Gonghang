## 一、审核摘要

### 1.1 推荐结论

建议优先验证 **TypeScript 全栈网页 + 支付宝官方沙箱 + 行止任务变更编排**。网页同时适配电脑与手机；支付渠道先跑通普通网页付款、关单、退款和查询，再探索支付宝 Agent 支付。微信小程序保留为后续用户入口，而不与第一条路线同时开发。

这不是认定微信技术能力不足。两条路线的主要区别在于当前团队的接入资源：支付宝公开提供沙箱和个人网页收款场景说明；微信普通小程序支付需要商户条件，新推出的微信 AI 支付还涉及 SkillHub 企业主体认证。先把最容易获得的测试条件转化为可查询的交易证据，比先确定页面所在的超级 App 更重要。相关依据见第三节。

“TS 全栈”与“微信小程序”也不是语言层面的二选一。微信提供官方 TypeScript 类型定义，小程序仍然可以使用 TS，后台同样可以使用 Node.js。真正需要选择的是首发终端、支付渠道和持续执行任务的服务端，而不是是否使用 TS。[微信小程序官方类型定义](https://github.com/wechat-miniprogram/api-typings)

### 1.2 已经查明的四个关键事实

1. 支付宝公开的网页支付示例包含付款、交易查询、退款、退款查询、关单及 Agent 支付交接，不必自行发明支付接口。
2. 微信支付 APIv3 的现行官方安全文档说明暂未提供独立沙箱测试环境和测试参数；不能把旧 APIv2 沙箱教程套到 APIv3。
3. 微信 AI 支付已经发布，不能再说微信没有智能体支付；但其商户接入条件不适合目前仅有个人账号的默认资源。
4. ACT 协议已经包含意图凭证、授权暂停、吊销和存证。行止应以场景化协同与工程验证体现贡献，而非宣称这些基础概念由本项目首次提出。

### 1.3 行止目前最值得深化的定位

**工作定位建议：面向智能体消费的计划变更与交易善后协同服务。** 旅行是第一验证场景；授权撤回、停止新购买、部分保留、退款跟踪和过程凭证是核心能力。

用户改变旅行目的后，行止应能判断“哪些订单保留、哪些购买停止、哪些事项需要确认、哪些退款仍在处理中”。它首先是接入受控 Agent 和合作商户的服务模块，通过独立网页展示，不是能够接管用户手机上全部旅行 App 的万能助手。

## 二、成熟技术的采用与项目差异

### 2.1 本轮采用的创新判断标准

采用成熟技术、现有协议和公开组件，不会自动失去竞赛价值。评估重点是场景是否成立、自主完成的部分是否清楚、组合后的效果是否可验证。同主题或同技术曾获奖，只用于识别直接重复，不作为自动淘汰条件；同时保留来源与许可，不把借鉴内容写成自研首创。

大赛公开要求强调原创、可行性和真实需求，未在本轮查阅页面中要求每个技术组件都必须为全球首次提出。是否符合具体知识产权与参赛条款，仍以组委会现行规则为准。[大赛介绍与参赛要求](https://www.gonghangbei.com/dsjs.html)

### 2.2 已有能力与行止的工作空间

| 参照对象 | 已有能力或方法 | 行止可以吸收什么 | 不应宣称什么 |
| --- | --- | --- | --- |
| 支付宝网页收款 | 付款、查单、退款、退款查询、关单 | 官方交易链路、渠道凭证和结果校验 | 自研了支付通道 |
| 支付宝 Agent 支付 | 用户授权下的智能体购买与支付交接 | 将受控购买动作接入 Agent 支付体验 | 一次任务授权自动获得无限扣款权限 |
| ACT | 意图结构化、授权凭证及生命周期、交易和信任事件 | 统一授权语义和证据关联思路 | 首次提出授权暂停、撤销与存证 |
| AP2 | 用户确认、受约束的委托及动作授权、回执 | 将用户确认与具体交易内容绑定 | AP2 凭证天然被中国支付渠道接受 |
| A2A | Agent 任务通信与取消请求 | 记录取消请求、接收处理结果 | 取消任务一定成功或等于退款 |
| UCP | 订单、履约、调整项及事件通知 | 分离履约和财务调整，追踪外部订单变化 | 获取订单能力即获得所有售后操作权限 |
| 补偿事务模式 | 长流程失败后的业务补偿和人工选择 | 按业务规则收尾、处理可保留的已完成事项 | 首次提出旅行订单部分取消 |

参照来源：[ACT 委托授权域](https://www.act-protocol.com/documentation/delegation.md)、[AP2 授权框架](https://ap2-protocol.org/ap2/agent_authorization/)、[A2A 规范](https://a2a-protocol.org/latest/specification/)、[UCP 订单能力](https://ucp.dev/specification/shopping/order/)、[微软补偿事务模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)。这些是各自规范或产品的描述，不代表它们已经普遍接入所有商户。

本阶段仅借鉴协议的概念与约束，不宣称行止已通过 ACT 等协议认证，也不宣称已完成协议兼容或跨平台互操作验证。

### 2.3 建议保留的三项自主贡献

**第一，变更影响解释。** 将“出差取消但仍保留探亲行程”等复合意图转成逐项处理清单，解释取消酒店是否影响接驳、保留交通是否仍有未完成事项。模型提出候选，规则与用户确认约束执行。

**第二，任务与交易一致性。** 接到停止新购买的指令后，受控服务端不再准入新的购买动作；已生成收银台、已提交支付和状态未知的交易单独核对，避免界面已停止而旧付款链接仍被误当作失效。

**第三，善后结果可核验。** 商户取消、支付退款和用户下一步分别展示。退款查询无明确成功证据时不显示成功；预期退款不计为已回收金额；重复回执不重复累计。

这三项是拟验证的应用贡献，不是已经证明的行业空白。即便其他产品存在相近功能，只要我们明确自己的边界、改造和测试，仍可继续推进。

## 三、平台与接入条件核实

### 3.1 支付宝网页收款：推荐先验证

**官方事实。** AI 网页应用收款页面明确支持个人收款场景，覆盖电脑和手机网页；接入索引提供下单、查询、退款、退款查询和关闭交易接口。沙箱使用测试账号和测试资金，与正式交易分离。[产品介绍](https://aipay.alipay.com/products/ai-web-app.md)、[接入索引](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/llms.txt)、[沙箱说明](https://aipay.alipay.com/llms.txt)

**研究判断。** 在尚无经营主体的情况下，这是优先级最高的支付验证入口。首个可运行闭环先使用电脑网页收银台，手机端付款体验作为同阶段兼容性验证，不能仅因宣传覆盖 PC/H5 就假设所有手机环境完全一致。

**待实测。** 个人账号是否能够取得当前沙箱应用和测试账户、目标支付产品是否可用、客户端如何完成测试支付、正式业务类目与网站材料是否满足要求。本轮没有登录账号核验，不承诺审批通过，也不承诺申请耗时或费用。

### 3.2 支付宝 Agent 支付：有衔接路径，但不能混同于普通收款

官方“传统供给 Skill”接入指南说明，可以保留已有电脑网站支付服务，在其上增加商家下单能力，并把支付环节交给支付宝支付处理能力。官方示例已经包含 Node.js 服务与相应交接说明。[接入指南](https://aipay.alipay.com/docs/skillpay.md)、[官方示例](https://github.com/alipay/ai/tree/main/code_example/page-pay-demo-with-agentpay)

**研究判断。** 行止可先完成普通网页交易，再让 Agent 通过受控业务接口请求下单，复用同一订单账本和支付适配器。不需要为了接入 Agent 支付而另建一套订单系统。

**待实测。** 普通网页沙箱可用，不等于买家侧 Agent 支付工具支持同一沙箱链路。本轮未确认 Agent 工具的沙箱支持范围、自建网页 Agent 的嵌入方式、用户间授权隔离和退款回传能力。该能力暂定为增强验证项，不作为首个闭环的前置条件。

买家侧支付开通与卖家侧收款签约是不同环节。自己的个人支付宝能够付款，不表示自己的服务已具备收款或退款权限。[Agent 支付说明](https://aipay.alipay.com/agentpay.md)

### 3.3 微信小程序＋普通微信支付：可作为第二入口

官方接入准备要求小程序账号认证、商户支付权限和 AppID 关联。支持主体包括个体工商户、企业等；交易类小程序还需遵循相关订单管理规范。[微信小程序支付接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015459512)

微信 APIv3 的现行官方说明指出，暂未提供独立沙箱和测试参数，生产环境不支持压测。因此，当前不把“注册个人小程序后直接接微信支付沙箱”列为可执行路线。具体合作测试条件若有变化，应以实际产品文档和商户后台为准。[微信支付安全实践·测试部分](https://pay.weixin.qq.com/doc/v3/merchant/4012073699.md)

**研究判断。** 微信小程序适合后续日常使用、分享和手机内确认；只有在取得匹配的商户条件，或明确只展示非支付原型时，才应提高其优先级。

### 3.4 微信 AI 支付：已发布，商户条件较明确

微信官方文档已经提供 AI 支付。用户使用与主账户隔离的 AI 专属卡，并在当前介绍的模式下逐笔确认。商户侧指南要求微信支付商户号，并通过 SkillHub 进行企业主体认证；不支持无营业执照的小微商户。接入还涉及传统 Native/JSAPI 下单与后续支付交接。[产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4035576700.md)、[接入准备](https://pay.weixin.qq.com/doc/v3/merchant/4035576711.md)、[开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4035576716.md)

**研究判断。** 值得保留兼容方向，但不能作为当前个人资源下的默认落地路径。微信 AI 支付、普通小程序支付、微信支付分是不同产品，不将其中一项的能力和准入规则推导到另一项。

### 3.5 两条容易误选的路线

**不能默认“网页套进个人小程序即可”。** 微信官方 web-view 组件说明，个人类型小程序暂不支持使用该容器。若后续选择个人小程序展示，应采用原生页面或合适的跨端方案，并核实类目和审核条件。[微信 web-view](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)

**不能依赖手机页面持续执行退款跟踪。** 微信小程序后台会挂起，浏览器页面也不是可靠的持续任务执行环境。取消、查询、退款重试与日志持久化应由服务端承担，用户关闭页面不应使已确认的善后流程丢失。[微信小程序运行机制](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/operating-mechanism.html)

## 四、技术路线建议：先固定边界，不锁死框架

### 4.1 推荐的第一条路线

| 层次 | 候选方案 | 当前建议 |
| --- | --- | --- |
| 用户与审核界面 | Vue 3 + TypeScript + Vite；React + TypeScript 同样可行 | 当前 P0 选择 Vue 3/Vite；不把界面框架设为业务前提 |
| 服务端 | Node.js + TypeScript，轻量 API 框架如 Fastify | 支付密钥、订单鉴权、状态转换全部留在服务端 |
| 持久化 | PostgreSQL | 保存订单、支付尝试、退款、授权版本与任务，不使用内存 Map 作为唯一记录 |
| 异步执行 | 持久化任务表和独立后台执行进程 | 首版不同时引入多套消息队列、工作流平台和微服务 |
| 支付接入 | 支付宝官方 Node.js SDK，封装独立适配器 | 优先验证当前网页支付文档对应接口，禁止混用沙箱与正式网关 |
| 模型能力 | 支持结构化输出或工具调用的模型接口 | 解析意图、生成解释；失败时保留表单操作，不取得商户私钥 |
| 测试方式 | 状态转换测试、接口契约测试、浏览器端到端测试 | 先验证关键状态与资金数字，再追求界面丰富度 |

支付宝官方 SDK 使用 TypeScript 实现并提供加签、验签等能力，说明 TS 服务端接入并不存在语言障碍。实施时选择仍受支持的 Node.js LTS，并在兼容性验证后锁定实际依赖；本轮不安装或固定完整依赖版本。[官方 SDK](https://github.com/alipay/alipay-sdk-nodejs-all)、[Node.js 发布计划](https://github.com/nodejs/Release)

Fastify 的接口校验可以帮助落实运行时字段约束，但 TypeScript 类型本身不能防止恶意请求。数据库事务可用于并发预算占用和任务领取，不能使外部支付变成可回滚的本地事务。[Fastify 校验说明](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)、[PostgreSQL 锁机制](https://www.postgresql.org/docs/17/explicit-locking.html)

### 4.2 如果审核后决定先做微信小程序

保留同一服务端、授权规则和交易账本，将用户界面换成微信原生 TS 页面。支付侧改为经正式资质核实的微信支付；若暂时没有资质，小程序只验证交互和本地模拟，不宣称已实现微信官方支付测试闭环。

Taro 支持 React/Vue 与多个小程序、H5 终端，但跨端框架不会代办商户资格，也不会消除支付接口与组件限制。只有确实需要同时交付网页与小程序、并验证支付体验后，才把它升级为主方案。[Taro 官方介绍](https://docs.taro.zone/docs/)

### 4.3 本轮不建议加入的内容

暂不建设自有钱包、用户资金托管、跨商户代收分账、自动垫付、真实票务库存、区块链上链、复杂多 Agent 集群或全协议兼容层。它们不是不可研究，而是会扩大首个交易闭环的接入与验证成本。

同样不以安装某个通用 Agent 或自动化操控付款页面替代支付接入。用户核身、付款确认应由官方界面完成，不让模型读取密码、验证码或复用用户支付会话。

## 五、付款退款闭环的实际边界

### 5.1 三种环境必须分开

| 环境 | 商户与行程 | 支付渠道 | 可证明的事情 |
| --- | --- | --- | --- |
| 本地模拟 | 虚构商户、规则与订单 | 模拟适配器 | 业务逻辑、故障处理和界面展示 |
| 官方沙箱 | 自建测试商户业务；不产生真实旅行预订 | 支付宝官方测试网关与测试账号 | 官方测试交易、退款、关单及查询联调 |
| 小额真实验证 | 获批主体与获准业务场景 | 正式支付产品 | 特定交易的真实付款与退款，不代表真实旅行服务全部接入 |

第一阶段可以使用一个沙箱卖家账户承接多个逻辑服务订单，但必须表述为“一个测试卖家下的多订单协同”。不能仅因界面写了酒店和车票，就称已接入两家独立真实商户。

真实验证应在产品获批、资金上限和用户确认明确后，按平台允许方式开展。本轮不使用亲属典当业务主体代替旅行业务资质，不制造虚假经营材料，也不为了演示另行收钱再转账伪装成原路退款。

### 5.2 要分别验证五种结果

1. **订单创建：** 行止业务订单与支付渠道交易号正确关联；生成支付表单并不等于渠道已经形成可查询的已付款订单。
2. **付款确认：** 使用验签后的通知或查询结果，核对应用、卖家、订单、金额和状态。
3. **未支付关单：** 关闭请求获得渠道结果；若与付款发生竞争，转入在途交易核对，不直接显示未发生支出。
4. **退款执行：** 用户提出退款诉求，商户按规则作出处理，由有权限的商户服务端调用渠道接口。
5. **退款确认：** 取得退款结果并核对原单、退款单和金额；渠道确认成功与用户银行卡可用余额的证明层级分开。

以上五种结果及通知校验均有支付宝公开接口依据，但能否在本账号的沙箱完整运行仍需逐项实测。[网页支付接入指南](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/ai-web-app-payment-integration-guide.html)

### 5.3 退款结果不能套用统一的“成功字符串”

支付宝退款接口中的 `code=10000` 不是单独充分的退款成功证据；`fund_change=Y` 可用于其文档规定的成功判断，其他情况需进一步查询。退款查询以 `refund_status=REFUND_SUCCESS` 为明确成功证据，不能仅凭返回退款金额认定成功。查询建议与退款请求间隔至少 10 秒。[退款接口](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/api-list/alipay-trade-refund.md)、[退款查询](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.md)

支付宝 `TRADE_CLOSED` 既可能表示未付款关闭，也可能表示支付后全额退款。必须结合历史付款记录和退款结果解释，不把它统一翻译为“从未付款”。`TRADE_FINISHED` 表示交易结束、不可退款，也不能作为“可申请退款”的依据。[交易查询](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/api-list/alipay-trade-query.md)

微信退款具有 `PROCESSING`、`SUCCESS`、`CLOSED`、`ABNORMAL` 等状态。其查询节奏与支付宝不同；不能用每秒刷新的前端页面反复请求支付渠道。各适配器应遵守对应平台的查询与限频建议。[微信退款查询](https://pay.weixin.qq.com/doc/v3/merchant/4013071041.md)、[微信退款最佳实践](https://pay.weixin.qq.com/doc/v3/merchant/4014959631.md)

## 六、不能直接照搬官方示例的部分

本轮仅作公开示例的实现对照阅读，不是对第三方仓库的完整安全审计。核对时的支付宝示例仓库提交为 `c72c1d605e498827f788c69022babd9216003f5a`，可据此复查，避免后续代码更新造成证据漂移。

| 观察到的示例写法 | 行止不能直接沿用的原因 | 拟采用的处理 |
| --- | --- | --- |
| 订单保存在内存 Map | 重启后不能持续解释订单与付款的关联 | 持久化记录，再调用外部渠道 |
| 回调处保留订单更新和幂等 TODO | 注释要求不等于实现完成 | 通知验签、业务字段核对和原子去重全部纳入验收 |
| 每次进入退款入口生成新退款号 | 用户重复提交可能被当作新的部分退款请求 | 同一业务退款固定请求号，金额和原单不变 |
| 无退款状态但有退款金额时展示成功 | 与当前退款查询文档的成功判据不一致 | 无明确成功状态时继续核对，不以金额字段兜底成功 |
| 普通演示路由直接接收订单号和金额 | 不足以证明操作人有权处理该订单 | 服务端核对用户归属、商户权限和剩余可退金额 |

来源：[固定提交的示例实现](https://github.com/alipay/ai/blob/c72c1d605e498827f788c69022babd9216003f5a/code_example/page-pay-demo-with-agentpay/app.js)、[退款查询文档](https://aipay.alipay.com/docs/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.md)。本轮未执行这份示例，未声称其已在本机跑通。

另一个接入细节是，官方 Node SDK 分别使用 `gateway` 和 `endpoint` 处理不同调用路径。若只修改其中一个就混合调用，可能把部分请求留在正式地址。首轮联调应检查所有实际请求目标，并拒绝沙箱任务访问正式网关。[SDK 实现](https://github.com/alipay/alipay-sdk-nodejs-all/blob/master/src/alipay.ts)

官方 SDK 已附 MIT 许可；本轮检查的 `alipay/ai` 示例仓库根目录和递归文件清单未发现独立许可证，示例的许可不能直接套用 SDK 的 MIT 许可。可以据接口文档自主实现；若要复制示例的大段代码，先核实其适用授权，并保留必要声明。[SDK 许可证](https://github.com/alipay/alipay-sdk-nodejs-all/blob/master/LICENSE.txt)、[示例仓库](https://github.com/alipay/ai)

## 七、行止需要补强的产品规则

### 7.1 “先暂停购买”与“确认取消订单”分开

用户明确点击“暂停新购买”时，服务端应先阻止新的购买准入，并记录暂停回执；不应等待大模型生成解释才暂停。是否取消已付款订单、是否接受费用损失，再通过变更预览逐项确认。

模糊表达如“算了”不能直接触发全部退款。对于“接站别订了”等明确范围，只暂停对应节点及必要的后续购买；对于“其他都先别买”，可以暂停任务整体的新增购买。暂停不改变既有订单履约事实。

### 7.2 已交给外部渠道的动作单独收尾

受控网关只能保证暂停生效后不再准入新的购买动作，不能保证此前已经发出的交易请求不再完成。进入外部发送阶段的动作按在途处理，保留占用并查清结果。已经交付的收银台链接也要关单验证，不能靠前端隐藏按钮撤销渠道能力。

上述保证以“范围内的所有新增购买均经过行止受控入口”为前提。如果外部 Agent 还持有可绕过该入口的独立支付工具，行止不能阻止其继续交易；首版必须明确排除这类旁路，不将内部暂停表述为支付账户冻结或全平台停付。

旧任务授权即使仍有有效签名，也必须通过服务端的当前状态和版本检查；签名不等于授权未被撤回。恢复或扩大购买范围需要新的确认，不因退款成功自动恢复购买。

### 7.3 新购买权限与善后权限分开

停止新购买后，允许在独立、明确的善后授权下继续查询原单、跟踪退款及处理用户已确认的取消请求。这些权限仅对应现有订单，不能用于新增购买或更换退款收款人。用户若进一步撤回查询权限，页面显示跟踪已停止及官方查询入口，不再静默访问。

### 7.4 预算不等于余额

界面至少区分累计已支付、待确认支付占用、已确认退款、预计退款和剩余授权空间。第一版以“累计购买上限”管理预算，退款不自动补回已使用的购买授权；需要再次花费时由用户确认新范围。

“预计可退 880 元”不能提前当作已收到 880 元，也不能视为银行账户可用余额。模型不能仅因预计退款足够，就创建替代酒店购买。配套 Demo 文档给出了可逐项核对的金额例子。

### 7.5 凭证可追溯不等于事实绝对真实

行迹保存用户确认、规则来源、业务动作和渠道回执之间的关联。哈希可用于发现特定记录变动，但不能证明原始输入真实，也不自动产生司法存证效力。第一版不使用“不可篡改”“法律认可”等未经独立机制支持的表述。

## 八、验证顺序与停留条件

| 阶段 | 要验证的问题 | 通过条件 | 不通过时保留什么 |
| --- | --- | --- | --- |
| A：账号与环境核实 | 个人账号能否取得正确沙箱与测试工具 | 明确应用、买卖家测试账号、可用接口与客户端；不公开密钥 | 文档、状态模型和本地模拟方案 |
| B：最短交易闭环 | 一笔测试付款能否按原单退款 | 可查询的支付与退款结果、金额一致、来源明确 | 不扩展 Agent，先解决渠道联调 |
| C：行止多订单闭环 | 部分保留、停止购买与退款能否协调 | 配套验收中的核心案例通过 | 已完成的单订单官方闭环 |
| D：Agent 支付增强 | 官方工具能否承接受控订单 | 订单与支付交接一致，用户按渠道要求确认，失败可核对 | 普通网页收银台，不伪造 Agent 接入 |
| E：小额真实验证 | 当前主体与业务能否正式接入 | 产品获批、限定真实金额、用户确认、真实支付退款证据 | 官方沙箱成果，明确未验证真实资金 |
| F：微信入口评估 | 是否具备商户条件和用户入口需求 | 主体条件、业务类目、支付体验及后台续跑验证完成 | 网页继续作为主入口 |

这些是后续开发的通过门槛，不是本轮已完成的测试。若本届报名窗口临近，先以可验证的现有材料参赛，具体截止日另查官方通知，不能把尚未实现的后续能力写成已完成成果。
