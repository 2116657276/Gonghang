## 一、验收目的和当前状态

本文件只验收新方案的一条消费者闭环：用户先从空状态说出生活目标、日期、消费上限、必须项和可调整项，形成需求草稿；选择主借记账户后查看轻量账目和未来 30 天安排，先取得可行性卡，再比较银行平台已登记的商品，确认后完成支付；随后新增一笔必要支出，重新规划并确认调整方案，最后核对订单、退款和资金影响。

历史项目已有 55 项后端定向检查通过，也已有支付宝沙箱付款、原单退款和待付款关单等核心子链记录。这些记录是可复用底座的历史证据，不能直接算作本方案的 N01—N12 通过；历史子链也不能替代新方案要求的同一运行连续链。新方案中的账户规划、记账与现金流分离、空状态自然语言需求、多候选比较和统一消费者流程均需要重新实现和验收。

当前交付仅文档；临时开始的数据实现已经撤回，开发暂停。因此 N01—N12 的状态统一为“未执行”；实际结果应在 M1—M3 集中验收时填写，并记录环境、时间、证据位置和未覆盖范围。

## 二、数据和状态口径

### 2.1 标准测试数据

| 数据项 | 标准值 | 说明 |
| --- | ---: | --- |
| 主借记账户当前可用余额 | 2,600 元 | 测试账户查询时的余额快照 |
| 未来 30 天必要支出及当期还款 | 1,500 元 | 可由多条资金安排组成，按日期展示 |
| 用户希望保留的金额 | 500 元 | 用户主动设置，不由模型替代决定 |
| 当前可规划空间 | 600 元 | 2,600 − 1,500 − 500 |
| 选定登记商品方案 | 480 元 | 由用户从候选中确认 |
| 选定后预计余量 | 120 元 | 600 − 480 |
| 新增必要支出 | 400 元 | 计划变化的触发事实 |
| 变化后的缺口 | 280 元 | 120 − 400，显示为缺口 280 元 |

表中的 600 元是主演示的初始静态样例，不替代正式的逐日期计算。M1 应识别基准余额、已入账流水和已经覆盖的现金流，不能重复扣除；付款后按实际账户事实与剩余未付安排计算，不能把已经反映在余额中的 480 元再次扣除，期末正余量也不能掩盖中途日期上的缺口。同一主账户下多个计划共享账户事实，账单中已含的分期安排只能计入一次。

预计收入和预计退款可以显示在时间线上或说明区，但尚未到账、渠道未核验或不可直接使用时，不加入当前可用余额和已确认可规划空间。信用额度始终不属于自有现金，也不加入可规划空间。只有实际账户事实才能更新主借记账户余额；支付宝沙箱退款成功只代表该沙箱交易的渠道结果，不能直接改写主借记账户余额或宣称银行已经入账。

### 2.2 消费统计与现金流安排

消费统计记录已经发生的消费，现金流安排记录未来某日期需要留出的金额。订单、支付回执、银行卡流水和退款记录应建立关联，但同一消费只能计入一次消费统计。信用卡消费和后续还款分别保存；账单中已经覆盖的分期安排不能再次计入。一个主账户下的多个消费计划共享账户事实，汇总时不能把同一笔流水分配给多个计划后重复计算。原付款在退款后仍保留，已确认退款另行累计。

建单占用、已确认支付、预计退款、已确认退款和账户流水的含义必须分别展示。支付已确认后不能再次占用或扣款；退款待核对时不能提前释放缺口或当作可用余额。付款后按实际账户事实和剩余未付安排计算，不把已反映在余额中的消费再次扣除。

### 2.3 可行性卡与决策信息

商品检索前先展示可行性卡。卡片结论只描述当前输入事实和规则结果，不使用“安全保证”等绝对表述，固定使用以下四类之一：

| 条件结论 | 卡片内容 |
| --- | --- |
| 符合当前约束 | 当前余额、必要安排、保留金额和日期为何支持继续确认 |
| 需调整 | 哪个金额、日期或项目超出约束，需要如何缩减、替换或延后 |
| 依赖预计收入或退款 | 依赖的资金和日期，以及当前为什么不能当作可用余额 |
| 信息不足 | 缺少哪项账户、流水、账单、日期、商品规则或用户意图 |

卡片同时展示影响日期、缺口或余量、项目预算拆分、必须保留项、可调整项和简短解释。它只支持用户决策，不代替确认，也不对未来资金作保证。

每次关键决策都保存轻量记录：输入事实版本、规则结果、简短理由、方案差异、用户确认和实际操作结果。记录不包含模型隐私思维链，也不用于自动学习或改变规则。计划完成后补充轻量复盘，列出计划金额、实际支付、已确认退款、净额和未决事项。

### 2.4 环境标签

所有账户、账目、商品、订单、回执和导出材料带有环境和来源标签：

| 标签 | 用途 | 说明 |
| --- | --- | --- |
| `simulation` | 日常开发和故障构造 | 本地业务结果，不是银行或支付渠道事实 |
| `sandbox` | M3 集中演示 | 支付宝官方沙箱渠道事实，商户和商品仍为测试资源 |
| `production` | 未来合作条件 | 本方案不启用，不作为当前 Demo 结果 |

订单、支付和退款按保存的交易环境隔离；账户事实按财务 source 标识，demo 流水可受控关联 sandbox 订单，关联不改变来源或环境。模拟支付不能冒充沙箱支付，沙箱支付也不能冒充银行余额变化。

## 三、主演示脚本

### 3.1 从空状态建立消费计划

1. 用户进入微应用的空状态，先输入生活目标、日期、消费上限、必须保留项和可调整项，例如：“周末和朋友出去玩，两个人，预算不要影响月底生活安排，晚饭必须保留，活动可以调整。”
2. 账户尚未选择时，Agent 只补问缺失条件并形成需求草稿；此时不输出已经验证可行的资金结论，不创建订单、支付或购买授权，也不建立长期目标。
3. 用户选择一张测试借记卡作为主账户。页面显示余额 2,600 元、查询时间、收支可见范围，并独立列出未来 30 天必要支出及当期账单／还款 1,500 元。
4. 用户确认保留 500 元。系统把消费统计和未来现金流安排分栏展示，先给出可行性卡：当前静态样例可规划空间 600 元，并说明影响日期、余量、缺口、预算拆分、必须保留项和可调整项。
5. 标准测试目录准备至少两个合格候选时，系统只从银行平台已登记的测试目录中提供两套符合当前约束的方案，例如“省预算”和“偏体验”，分别展示项目预算拆分、价格、时间、适用条件、推荐原因、必须保留项和可调整项，用户选择一项总价 480 元的方案。若目录不足两个合格候选，系统如实提示无足够可比较结果或展示现有候选，不虚构商品和价格；该情形单独记录，不用来伪造主演示的比较证据。

### 3.2 用户确认并完成支付

1. 确认卡片列出商品、商户、金额、计划范围、有效期、环境和将执行的动作，并关联当前可行性卡和方案差异。
2. 用户明确确认后，服务端重新核对报价、账户归属、授权、计划版本和购买空间，再创建订单。
3. 日常验收使用本地模拟支付；M3 录制时以 sandbox 环境新建一条代表性订单（不修改已有订单环境）。付款已确认后，刷新页面、重复点击或 Agent 再次运行都必须读取原支付事实，不得新建订单或再次扣款。
4. 订单与账目关联清楚：480 元作为已确认消费及相应现金流事实只记录一次；如果采用沙箱，渠道记录显示 sandbox；主链可由受控联动生成明确标为 demo 的测试账户流水并关联原订单，不能称银行已扣款。未生成关联流水时保留待账户核对的消费安排，余量仍为 120 元。

### 3.3 新增必要支出并调整

1. 用户补充：“临时多了一笔 400 元的必要支出。”系统将这笔支出按日期加入同一计划。
2. 系统展示变化前后：原余量 120 元，新增支出 400 元，形成 280 元缺口，并列出预计收入、预计退款等尚未成为可用资金的项目。工资延后等变化同样由用户更新或已接入事实触发按需重算，不由常驻模型等待。
3. 系统根据订单状态提出选项：保留重点项目、替换更便宜的登记商品、延后尚未付款的项目，或取消符合规则的已付款订单。
4. 用户确认调整范围和可接受费用后才执行。已建单未付款的项目可按渠道状态申请关单；已付款项目按登记商户规则提交取消或退款；尚未创建的计划项不生成虚假订单。
5. 页面区分“预计退款”“商户已受理”“渠道已确认退款”“主账户已入账”四种含义。沙箱退款确认成功时，只更新沙箱订单和渠道证据；没有关联账户流水时，主账户余额不变；演示若启用受控 demo 流水联动，则明确展示“测试账户模拟入账”，同时保留独立 sandbox 回执，不能写成真实银行到账。

### 3.4 展示结束状态

演示最后回到同一计划，显示保留、替换、延后和取消的结果，注明仍待核对的订单或退款，并给出证据来源和时间。计划完成后展示轻量复盘：计划金额、实际支付、已确认退款、净额和未决事项。每次关键决策保留输入事实版本、规则结果、简短理由、方案差异、用户确认和操作结果，不展示模型隐私思维链，也不依据行为自动学习。演示人员不得用预先改好的余额、手工改状态或不同订单片段拼接出一条不存在的连续链；如使用录屏回放，应标注回放时间和环境。

## 五、专项验证与非阻断项

以下内容保留其价值，但不阻断首版 P0 的放行，也不作为 N01—N12 之外的隐性要求：

- 同一次取消确认内分批退款、取消费用和退款总额核对。
- 商户拒绝、长期退款延迟和人工责任交接的额外场景；渠道未知的基础保留与恢复属于 N11，不能从必验范围移除。
- 多张银行卡、全量账户聚合、复杂贷款合同和自动分类。
- 多商户独立接入、真实库存、真实商品履约和银行正式接口。
- 支付宝 Agent 支付、小程序或其他支付渠道适配。

首版沿用当前消费计划和需求草稿，不建立长期目标系统；变化由用户更新或已接入事实触发按需重算，不安排常驻模型或自动交易。

专项验证仍须遵守原有资金、用户确认、权限、固定业务号、环境隔离和数据完整性要求。专项结果不能反向降低 P0 的必要约束，也不能把测试商户的人工操作写成银行正式能力。

## 六、阶段验收安排

M1、M2、M3 是唯一主 DEV 顺序，具体范围以[分阶段开发计划](../03-engineering/development-plan.md)为准。现有订单、确认、支付、取消和退款能力继续在主开发链路中复用，不因新方案后移到 P2；本节只说明本验收与三个阶段的对应关系。

| 阶段 | 工作范围 | 验收重点 |
| --- | --- | --- |
| M1 新后端 | 账户与账目逻辑、当期还款、30 天规划、登记商品、多候选、空状态需求、变化调整；在已应用 001—012 的基础上使用增量迁移和新种子数据，旧迁移不改写 | N01—N11 的服务端事实、金额口径、权限、幂等和模拟主链 |
| M2 统一前端 | 从空状态到规划、候选、确认、支付、变化和退款的一体化消费者工作区 | 在 `simulation` 环境完整走通 N01—N11 的主场景 |
| M3 沙箱与用户证据 | 在同一运行中使用支付宝官方沙箱完成付款、变化确认、原单取消退款与查询，集中完成用户访谈和任务观察；未付款关单需要展示时另行补充 | 完成 N12，并复核沙箱来源与银行余额边界 |

大阶段结束后集中验收和记录结果。已通过的窄范围检查在代码和环境未改变时直接引用；只有受到新改动影响或发现具体缺口时才定向复测。P0 的完整 Demo 只有在 N01—N12 全部通过时才能放行；任一必验项阻塞时，只能交付部分开发版本并列明阻塞原因和未交付范围，不能标记为完整 P0 通过。

## 七、结果记录格式

每项结果至少记录：执行日期、执行人、环境标签、业务计划／订单的脱敏关联、输入摘要、实际状态、金额和日期、证据位置、是否使用回放，以及失败或阻塞原因。记录只保存必要脱敏信息，不写入账号密码、支付密钥或完整敏感回执。

验证结果应区分四类事实：已实现并通过、已有历史底座证据、当前未执行、依赖银行或商户合作的待验证能力。历史 55 项后端检查与既有支付宝沙箱核心链只能放在第二类，不能替代新方案验收。
