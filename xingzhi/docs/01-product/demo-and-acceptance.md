## 一、Demo 要证明什么

第一版必须从用户提出购买需求开始，由自定义 Pi 单 Agent 查询商品、提出购买方案，经用户确认后创建测试商户订单，并完成官方沙箱付款；随后在同一组订单上处理计划变更、部分保留、取消、退款与结果核验。不能只展示预置已付款状态，也不要求真实旅行预订。详细需求见[PRD](prd.md)。

展示的金融价值是**购买授权、在途支出和退款事实能够保持一致**，而不只是旅行推荐更聪明。以下四件事必须分别成立：用户确认的变化能够落到具体任务；新购买确实被受控服务端阻止；支付与退款结果来自对应渠道；关闭页面或收到重复通知不会破坏状态。

## 二、首版范围

### 2.1 必做与不做

| 分类 | 内容 |
| --- | --- |
| 必做 | 一位测试用户、一份旅行任务、四个任务节点、一个测试卖家；按订单分别完成付款、关单或退款处理 |
| 必做 | 一次明确暂停、一次变更预览、一次确认、可恢复的任务执行和查询 |
| 必做 | 支付与退款来源标识、金额核对、重复请求处理、在途结果待确认 |
| 必做 | 取消费用预览及接受后的部分退款、多次部分退款、商户拒绝／延迟与明确失败展示 |
| 增强项 | 支付宝 Agent 支付交接、小程序和独立合作商户适配 |
| 暂不做 | 真实铁路出票、真实酒店库存、跨商户资金归集或分账、钱包余额托管、自动垫付 |
| 暂不做 | 微信与支付宝两套支付同时落地、多 Agent 自主协商、通用跨 App 自动操作 |

多个业务节点在首轮可以共用一个沙箱卖家，但必须说明是“一个测试卖家下的多笔测试交易”。后续增加独立合作商户时，再验证商户权限、取消规则和外部接口差异；不能用界面上的多个品牌名称代替真实接入。

### 2.2 三种数据标签

每笔订单、每个回执和每份导出材料都应有环境与来源。建议使用“本地模拟”“支付宝沙箱”“正式交易”三个互不混淆的环境标签，并另外注明“测试商户规则”或“渠道查询结果”。

沙箱中的测试交易是调用官方测试接口产生的记录，不发生真实资金转移，也不产生真实旅行服务。沙箱故障不得自动切换正式通道；本地模拟只能用于解释和故障构造，不能替代沙箱闭环验收，未完成的沙箱订单继续标记待核对。

## 三、主演示：出差取消，但保留探亲

### 3.1 初始任务与授权

用户希望安排杭州出行，授权总购买上限为 3000 元，仅限交通、住宿、门票和接驳，授权有效期为 24 小时。这里的预算是行止对购买动作的上限，不是用户向行止充值，也不是支付宝授予的免确认扣款额度。付款仍按渠道要求由用户确认。

先由 Agent 查询测试目录并生成购买方案，再由用户确认、创建订单并完成 A、B 的付款，得到下表的变更前状态。D 仅为计划项。所有商户规则均为测试规则；3000 元与24小时是固定的 P0 测试参数，不是固定产品阈值。

| 节点 | 测试金额 | 初始任务状态 | 初始支付状态 | 备注 |
| --- | ---: | --- | --- | --- |
| A：去程交通服务 | 420 元 | 已预订，待使用 | 官方沙箱已付款 | 不表示真实出票 |
| B：住宿服务 | 880 元 | 已预订，待入住 | 官方沙箱已付款 | 基础脚本允许全额取消退款 |
| C：景点服务 | 180 元 | 订单已创建，待用户付款 | 渠道已查得待付款 | 用于展示关单和旧链接处理 |
| D：到站接驳 | 120 元 | 尚未创建订单 | 无支付尝试 | 依赖去程到站安排 |

A、B 的已付款状态必须由实际沙箱付款得到。C 只有在渠道查询确认待付款后，才能作为“渠道待付款订单”展示；仅生成 HTML 支付表单，不足以证明渠道已创建该交易。

### 3.2 用户的变更指令

“出差取消了，但我还要去杭州看家人。去程保留，酒店和景点不要了，接站先别订，其他新支出也暂停。”

系统先记录“暂停新购买”的明确指令，再生成影响预览。预览应显示 A 保留、B 申请取消退款、C 关闭未付款交易、D 不再下单。不能因为 D 依赖 A，就反向把用户明确要求保留的 A 一并取消。

界面同时提供独立的“暂停新购买”按钮，点击后不依赖模型解析。自然语言入口仍需识别指令及其范围；只有识别为明确暂停请求后，才先执行暂停、后生成详细解释，不能承诺未经识别的任意文本都会即时生效。

### 3.3 四至六分钟展示脚本

| 步骤 | 展示内容 | 应当观察到的结果 |
| ---: | --- | --- |
| 1 | 展示从选购到付款的过程及变更前订单 | Agent 查询与用户确认可追溯；A、B 有实际沙箱支付证据；C 待付款；D 未产生交易 |
| 2 | 用户发出变更指令 | 服务端确认暂停新增购买；明确显示这是行止内部购买权限的暂停 |
| 3 | 展示影响预览 | A 保留；B 预计退 880 元；C 待关单；D 停止；费用和规则来源清楚 |
| 4 | 用户确认逐项处理 | 记录计划版本、订单范围和费用接受情况；旧预览过期则重新确认 |
| 5 | 执行并核对 | D 停止；C 向支付渠道请求关单；B 由测试商户按规则发起退款；A 不变 |
| 6 | 展示中间状态 | “商户已同意”“渠道已处理”“结果待核对”等含义分开，预计退款不写成已退 |
| 7 | 展示最终证据 | 可查得 B 的退款结果、C 的关单结果；行迹材料保留原始支付与后续变化 |
| 8 | 展示一个异常回放 | 重复点击退款或迟到支付回执不能造成二次退款或错误余额 |

完整验收必须在同一次可追溯运行中完成需求、选购、创建订单、付款及后续善后。短时答辩可在说明准备时间的前提下压缩付款展示，但必须另有完整连续验收记录；不同订单的独立付款和退款片段不能拼接冒充同一闭环，预录内容明确标记回放。

## 四、金额解释与核对样例

### 4.1 第一版的金额口径

| 字段 | 含义 | 不包含什么 |
| --- | --- | --- |
| 累计已支付 | 本次授权范围内已确认成功付款的累计金额 | 不因退款而抹去原始付款事实 |
| 支付占用 | 待支付或已提交但结果尚未确定的购买金额 | 尚未创建订单的纯计划报价 |
| 已确认退款 | 按唯一退款请求累计的渠道确认金额 | 预计退款、商户口头承诺 |
| 预计退款 | 根据当前测试规则形成的可退金额估计 | 未确认到账的真实账户可用资金 |
| 当前净支出 | 累计已支付减已确认退款 | 不代表未来最终成本，也不包括尚未成功付款的占用 |
| 剩余授权空间 | 3000 元减累计已支付减支付占用 | 退款不自动重新增加此空间 |
| 当前可执行购买额度 | 在授权有效、未暂停且满足其他约束时，才允许使用的空间 | 暂停时为 0；不是银行或支付宝钱包余额 |

内部金额采用整数分，对接以元计价的接口时使用固定两位小数字符串。第一版不引入优惠券、积分、分期或多币种，避免把订单总额、用户实付和实际退款混为一谈。

### 4.2 基础脚本的预期数字

| 时点 | 累计已支付 | 支付占用 | 已确认退款 | 当前净支出 | 剩余授权空间 | 当前可执行购买额度 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A、B 已付款，C 待付款 | 1300 | 180 | 0 | 1300 | 1520 | 1520 |
| 用户暂停新购买 | 1300 | 180 | 0 | 1300 | 1520 | 0 |
| C 确认关闭，B 退款待核对 | 1300 | 0 | 0 | 1300 | 1700 | 0 |
| B 确认全额退款 880 元 | 1300 | 0 | 880 | 420 | 1700 | 0 |

金额单位均为元。第三行即使显示“预计退 880 元”，也不能把当前净支出提前改为 420 元。第四行退款成功后仍处于暂停状态，不能自动购买替代酒店。后续用户可以重新确认购买范围和上限，但应保留旧授权及原始付款记录，不通过新版本重置账本逃避上限。

### 4.3 部分退款变体

P0 的部分退款用例把住宿取消规则设为“退 800 元、保留 80 元取消费用”。必须在确认前向用户展示并取得接受；同一原单可在独立用例中按不同固定退款号验证多次部分退款。规则不是平台通用标准，也不是现实酒店政策。

确认退款后，累计已支付仍是 1300 元，已确认退款为 800 元，当前净支出为 500 元，其中交通 420 元、取消费用 80 元。原订单金额不能被改写成 80 元，累计退款与本次退款不能重复相加。

## 五、状态和权限的最小设计

### 5.1 分开保存，不压成一个“完成”状态

| 对象 | 首版需要区分的情况 |
| --- | --- |
| 购买授权 | 待确认、有效、暂停、撤销、过期 |
| 任务节点 | 待执行、等待确认、执行中、保留、停止、结束、待人工处理 |
| 商户订单 | 未创建、已创建、取消待处理、取消同意、取消拒绝、已履约 |
| 支付尝试 | 未发起、等待用户付款、在途或未知、已付款、确认未付款关闭 |
| 退款请求 | 未申请、申请待提交、已提交待核对、渠道确认成功、明确失败、待人工处理 |
| 整体善后 | 未启动、处理中、仍有待跟踪事项、已安排人工责任、全部事项结束 |

行止内部枚举不是支付渠道枚举；适配器保存原始渠道状态和映射依据。历史付款仍成立时，即使渠道后续返回关闭，也不得删除已付款事实。人工接管表示有人继续负责，不表示资金已经退回。

### 5.2 三组权限

1. **购买权限：** 创建新订单、生成支付交接信息。暂停或撤销后，受控入口拒绝新的动作准入。
2. **善后权限：** 查询现有订单、提交用户已确认的取消诉求、查询对应退款。仅对明确订单和期限有效。
3. **商户执行权限：** 测试商户审核取消规则并发起渠道退款。不能由买家界面直接持有或自行生成。

用户只拥有 A 订单时，即使知道 B 的渠道交易号，也不能查阅或退款 B。模型可以选择已授权的业务工具，但不能任意指定外部网址、商户身份、退款账号或支付密钥。

### 5.3 并发暂停与在途支付

服务端领取购买动作时，原子检查最新授权、版本和预算，并记录动作及占用。暂停操作在同一授权记录上生效后，不得准入新的购买动作；已进入外部发送阶段的动作单独标为在途。

演示范围内的购买必须全部经过这一入口；外部 Agent 自带且可绕行的支付工具不属于暂停保证范围。验收前应检查工具权限与调用路径，不仅检查网页按钮是否禁用。

数据库提交与支付网络受理不是同一事务，不能承诺“用户点击暂停之后绝不会再发生付款”。正确承诺是“暂停生效后不再准入新的购买；此前在途交易逐笔核对”。对于已经生成的待付款交易，只有收到关单成功结果后，才能确认原付款入口不可继续使用。

后台进程崩溃后，先恢复未确定动作的查询与对账，不生成新订单号重新扣款。重复网络尝试可以有新的通信追踪号，但同一业务支付或退款的幂等标识不能因此改变。

## 六、界面与系统职责

### 6.1 三个演示视角

| 视角 | 展示内容 | 必须避免的误导 |
| --- | --- | --- |
| 用户端 | 任务目的、授权边界、订单状态、变更预览、退款进度 | 不展示成可控制任意第三方 App 的控制台 |
| 测试商户端 | 测试商品、取消规则、退款审批及执行记录 | 明确为自建测试商户，不冒用真实品牌 |
| 证据与审核端 | 请求、查询结果、去重记录、规则来源及脱敏导出 | 不用后台手工改状态伪装渠道回执 |

三个视角可以在同一套应用中实现，但权限要分离。审核视角只读；故障注入和重置入口限本地模拟或独立测试场景，不对正式交易开放。

### 6.2 与终端无关的能力契约

| 能力 | 输入边界 | 输出要求 |
| --- | --- | --- |
| 暂停新购买 | 已认证用户、任务范围、幂等标识 | 服务端生效记录、已暂停范围、在途清单 |
| 生成变更预览 | 当前任务快照、用户意图、订单和规则来源 | 保留与取消清单、预计金额、待确认问题、快照版本 |
| 确认变更 | 对指定预览的确认、可接受费用、幂等标识 | 接受结果或过期冲突，不静默扩大范围 |
| 请求付款 | 已确认的业务订单和有效购买授权 | 官方付款入口或明确失败；不是付款成功承诺 |
| 请求取消 | 用户已确认的订单和规则依据 | 商户受理、拒绝或待处理状态 |
| 执行退款 | 商户权限、原支付订单、固定退款请求和金额 | 渠道结果及后续查询任务 |
| 查询交易与退款 | 有权访问的已有对象 | 来源、查询时间、渠道状态与解释 |
| 导出行迹 | 用户选择的字段、分享范围 | 脱敏材料、未解决事项、证据来源与生成时间 |

第一版不固定具体 API 路径，以免在框架未选定前制造兼容负担；以上职责和授权边界应在网页、小程序或 Agent 接口中保持相同。

### 6.3 需要持久化的最少记录

保存任务及节点、授权及确认记录、商户订单、支付尝试、退款请求、待执行动作、渠道回执和审计事件。状态变化与待执行动作在同一数据库事务中落地；对外调用在事务外执行，结果回写并校验版本。

成功通知只有在完成必要的验签、字段核对和可靠落库后才确认接收。后台任务采用有限重试、递增等待和人工接管；支付结果未知时，不能用相同商品生成另一个新支付订单来“重试”。

## 七、验收清单

以下 36 项均为 P0 后续测试判据。每项完成后应记录日期、环境、证据位置和实际结果；当前不填“通过”。

### 7.1 官方交易闭环

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| P01 | 正常完成沙箱付款 | 订单、卖家、应用、金额与渠道付款状态一致 |
| P02 | 用户到达返回页但尚无成功证据 | 页面等待查询，不凭跳转显示付款成功 |
| P03 | 同一成功通知发送两次 | 只累计一次付款，不重复启动履约或善后 |
| P04 | 通知签名无效，或签名有效但金额、卖家不匹配 | 不更新支付状态，记录待排查事件 |
| P05 | 全额退款 | 同一原单和退款号可查得明确退款成功，金额正确 |
| P06 | 部分退款 | 保留原付款金额，仅记录实际退款和未退部分 |
| P07 | 退款查询返回成功调用码但无成功退款状态 | 不显示退款成功，不提前释放预计回款 |
| P08 | 多次部分退款或重复回执带累计退款金额 | 区分累计与本次金额，不重复加总，不超过可退金额 |
| P09 | 同一次退款重复点击或超时重试 | 使用同一退款号及金额，不能产生第二次业务退款 |
| P10 | 未付款订单关闭 | 以渠道关单结果为依据，并核对旧付款入口状态 |
| P11 | 已全额退款订单返回 TRADE_CLOSED | 保留历史付款和退款，不解释为从未付款 |
| P12 | 查询返回 TRADE_FINISHED | 识别交易已结束，不据此继续尝试普通退款 |
| P13 | 从购买需求连续运行至退款核验 | 同一可追溯业务运行（允许跨 Agent 会话恢复）具备商品依据、购买确认、创建订单、官方付款、取消确认、原单退款和结果关联 |

### 7.2 计划变更与授权

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| A01 | 用户点击暂停按钮，或自然语言已被识别为明确的整体暂停请求 | 按钮路径不依赖模型；明确请求不等待详细解释，服务端先记录暂停结果 |
| A02 | 暂停后 Agent 用旧授权创建新订单 | 受控入口拒绝准入，付款请求不进入新执行流程 |
| A03 | 明确保留 A、取消 B/C、停止 D | A 不被误取消；B/C/D 分别按自身状态处理 |
| A04 | 用户只说“算了”或“不必要的都取消” | 不自动退款，要求确认范围；没有把商户文本当作用户指令 |
| A05 | 预览后退款规则、金额或订单状态变化 | 原预览失效或明确提示变化，必要时重新确认 |
| A06 | 取消有 80 元费用 | 确认前展示，未接受前不执行带损失的取消 |
| A07 | 退款成功后授权仍暂停 | 不自动购买替代服务，不自动恢复购买额度使用 |
| A08 | 买家访问其他用户订单 | 即使提供真实订单号也拒绝访问 |
| A09 | 外部商品描述要求忽略授权或更换收款方 | 文本不获得权限；规则检查阻止超范围动作 |
| A10 | 用户撤回后续退款查询权限 | 停止新增查询并保留已知结果，提供官方处理入口 |
| A11 | Agent 提出商品、金额或授权确认 | 商品金额由业务服务校验；Agent 不能代用户产生确认或修改收款方 |

### 7.3 异常与恢复

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| R01 | 付款与关单几乎同时发生 | 不强行判为未付款；查清后进入相应保留或取消退款流程 |
| R02 | 请求已发出但返回超时 | 保留在途占用；先查单，不能再创建新支付绕过未知状态 |
| R03 | 退款查询过早尚未返回成功 | 按渠道建议等待再查，不直接判为永久失败 |
| R04 | 用户关闭网页或小程序进入后台 | 服务端继续已授权的善后；重新进入可恢复真实状态 |
| R05 | 后台在调用前或调用后崩溃 | 依据持久化记录恢复，核对外部结果，不重复扣款退款 |
| R06 | 两个执行者同时领取同一任务 | 同一动作仅有一个有效领取；重复调用受幂等规则约束 |
| R07 | 商户拒绝取消或退款余额不足 | 显示原因与责任方，不以用户同意代替商户或渠道成功 |
| R08 | 先收到退款成功，再收到旧付款通知 | 历史补齐但不让退款状态倒退，金额不重复累计 |
| R09 | 联网失败，切换本地模拟展示 | 环境标签明确，不伪造剩余沙箱步骤成功 |
| R10 | 沙箱任务误配置正式地址 | 在发出请求前拒绝执行，不能静默访问正式网关 |
| R11 | Pi 运行中断、重启或待确认期间用户离开 | 从业务记录重建上下文；未确认操作不执行，已受理操作先核对，不依赖模型持续循环 |
| R12 | 模型不可用或达到运行上限 | 明确提示能力受限；后台继续已授权任务，表单可查询与确认既有方案；不将回退视为 Agent 验收通过 |

异常用例先用本地模拟器和契约测试构造，不为制造失败而对正式支付环境压测。官方沙箱仅验证其支持且适合反复联调的能力。

## 八、完成后的证据包

每次完整演示保存一份独立记录：环境标签、测试时间、测试规则、用户确认摘要、内部订单与渠道订单的关联、付款和退款查询结果、失败与重试记录、最终金额核对表。导出材料默认隐藏账号、密钥、付款链接和完整身份信息。

所谓“闭环通过”，至少需要 P13 的完整购买链路、A 保留正确、B 明确退款结果、C 关单结果可核对、D 未产生新订单，以及金额和重复请求测试通过。C 未形成渠道交易时必须另行验证渠道关单用例，不能把本地关闭算作 P10 通过。B 仍在等待结果时只能记录“进入退款跟踪”。完整放行门槛见[验证策略](../04-quality/verification.md)。

用户理解测试可以邀请 5—10 名知情同意的测试者，比较他们能否说清楚：哪些项目被保留、哪笔钱真正退回、还有谁需要处理。应报告实际人数、任务、成功数和失败原因，不把小样本体验改善包装成大规模统计结论。

## 九、可压缩的实施顺序

1. **先完成本地业务基础纵切：** 建立 Vue 3/Fastify/PostgreSQL 应用、三类服务端角色、A/B/C/D 测试目录、授权、方案、暂停、订单、任务与事件恢复；本地模拟只证明内部规则。
2. **再核实并接入支付入口：** 获取经确认的测试条件，完成独立的一笔沙箱付款、关单和原单退款；本地模拟不能代替这些证据。
3. **接入完整善后与异常：** 按同一业务模型完成费用退款、多次部分退款、商户拒绝／延迟、重复退款、在途支付、通知乱序、关闭页面和进程重启。
4. **完成 Pi 闭环与证据：** Pi 自然语言选购和变更是必做；补齐确认交互、行迹导出与手机适配。官方 Agent 支付产品交接单独评估。

若时间有限，可压缩跨端和复杂图形，但不删除 Pi Agent、实际沙箱付款退款及异常恢复。任何阶段都不能用手工修改支付成功状态弥补尚未完成的官方交易联调。
