## 一、产品定位

行止是一款拟嵌入银行 App 的青年消费规划微应用，贯通轻量记账、未来 30 天资金规划、银行平台登记商品的推荐选购和计划变化后的订单调整。

用户可以先说生活目标、日期、消费上限、必须保留项和可调整项，再选择一个主借记账户。在账户尚未选择时，行止只能保存目标和需求草稿，不能输出已经验证可行的资金结论，也不能创建订单或交易。账户选定后，行止在授权范围内查看余额与收支，并关联独立的信用卡账单、贷款或分期当期还款安排。系统将已经发生的消费事实与未来现金流约束分开呈现，先给出可行性卡，再从已登记的商品目录中提供候选；用户确认后才创建订单和支付。发生临时必要支出、工资延后或消费意愿变化时，行止重新计算影响，按需给出待确认的调整方案。

首版消费者载体确定为微信小程序，采用 Taro + Vue 3；银行 App 嵌入仍是后续合作方向。小程序使用 simulation 展示完整闭环，商户／审核保留网页；M3 另保留支付宝 sandbox 连续证据，首版不接入微信支付。实施细节见[小程序方案](../03-engineering/miniapp-frontend.md)。

首版目标是用一条简洁、连续、可核验的消费者闭环证明价值。它不是完整的个人财务管家、全网商城或自动扣款代理。

## 二、用户与问题

### 2.1 目标用户

首批面向正在实习或初入职场、开始独立承担房租、通勤、生活费和还款安排的青年用户。用户可能希望安排一次周末消费，却不清楚当前余额扣除未来支出和保留金额之后还剩多少，也不知道计划发生变化时如何处理已经付款的订单。

“青年”是竞赛和试点方向，具体需求仍需通过少量访谈和任务观察验证。产品不假设所有青年有相同收入、债务或消费偏好。

### 2.2 用户问题

1. 当前余额是快照，不能直接说明未来 30 天哪些钱已有用途。
2. 记账或预算常常停留在消费之前，用户仍需自行比较商品价格、条件和取消成本。
3. 新增必要支出、收入延后或计划改变后，用户缺少保留、替换、延后、取消和退款跟踪的一体化处理。

## 三、角色和权限

| 角色 | 职责 | 权限边界 |
| --- | --- | --- |
| 消费者 | 提供需求、补充资金安排、选择商品、确认订单和调整计划 | 只能查看和操作自己授权范围内的账户摘要、计划、订单与退款 |
| 登记商户／平台管理员 | 维护已登记商品及取消规则，处理可执行商品的订单和退款 | 只能处理所属商品和订单，不能查看其他用户账户或改变用户授权 |
| 只读审核者 | 查看脱敏的运行、订单、资金口径和渠道证据 | 只能查看服务端分配范围，不能创建订单、支付、取消或退款 |
| Pi Agent | 理解语言、调用受控业务工具、解释结果 | 不拥有用户身份、确认权、支付密钥或商户权限，不能直接改写业务事实 |

前端视图切换不改变服务端权限。真实银行宿主、正式账户接口和真实商户履约属于后续合作条件；测试原型使用明确标记的测试账户、测试目录和测试规则。

### 4.1 FR-01：主账户与数据范围

首版默认使用一个主借记账户。余额是查询时的账户快照，需要显示查询时间和来源。账户之外的信用卡当期应还、贷款或分期当期还款作为独立的资金安排记录，不把选择借记卡解释为自动获取全部债务信息。

如果实际接口暂时只能提供余额或账单的一部分，界面必须显示可见范围，用户可补充缺失信息。总欠款可以作为背景信息，但不能把全部未偿金额一次性当成未来 30 天支出。

### 4.2 FR-02：轻量记账

记账服务于规划和消费回顾，不建设专业财务软件的全部能力。系统至少保存来源、发生日期、金额、类别、关联订单和纠正记录。

消费统计回答“已经花了多少”；现金流安排回答“未来哪一天要留出多少钱”。订单、支付回执、银行卡流水和退款记录可以相互关联，但不能因为它们存在多份记录就重复增加消费或现金流。信用卡消费与信用卡还款分别保存，账单中已覆盖的分期安排不能再次计入。同一主账户下的多个消费计划共享账户事实，汇总时不能把同一笔流水重复分配给多个计划。退款保留原付款事实。

### 4.3 FR-03 和 FR-04：30 天规划及未来金额

主演示中的初始可规划空间采用静态样例规则：

`当前可用余额 − 本月已知必要支出及当期还款 − 用户希望保留金额`

标准样例得到 2,000 − 900 − 500 − 400 = 200 元，但这不是正式的单一汇总算法。M1 正式规则必须按日期计算，并识别基准余额、已入账流水和已经覆盖的现金流，不能重复扣除；付款后以实际账户事实和剩余未付安排计算，若余额已反映 99 元付款，就不能再从剩余安排中扣一次 99 元。期末有正余量也不能掩盖中途日期上的缺口。

预计收入和预计退款显示在时间线上或说明区域中，只有实际到账或形成可核验账户事实后才更新相应账户或现金流事实；支付宝沙箱的渠道退款成功只更新沙箱渠道事实，不能直接更新主借记账户余额。信用额度始终不属于自有现金，不能增加当前未分配缓冲。系统应明确提示“根据当前已提供的信息”，不提供覆盖所有账户的确定性财务结论。

在进入商品检索前，系统生成可行性卡。卡片只描述当前输入和规则下的条件结论，不使用“安全保证”等绝对表述：

| 条件结论 | 必须说明 |
| --- | --- |
| 符合当前约束 | 依据哪些余额、必要安排、保留金额和日期可以继续确认 |
| 需调整 | 哪个金额、日期或项目超出约束，以及需要缩减、替换或延后什么 |
| 依赖预计收入或退款 | 依赖的资金何时可能发生，当前为什么不能当作可用余额 |
| 信息不足 | 缺少哪项账户、流水、账单、日期、商品规则或用户意图 |

可行性卡同时列出影响日期、缺口或余量、项目预算拆分、必须保留项、可调整项和简短解释。它支持用户决定下一步，不代替用户确认，也不对未来资金作保证。

### 4.4 FR-05 和 FR-06：从空状态开始选购

没有现成计划时，用户可以先说生活目标、日期、消费上限、必须保留项和可调整项，例如“周末和朋友出去玩，预算不要影响月底生活安排，晚饭必须保留，活动可以调整”。Agent 负责识别这些信息以及人数、偏好等条件；影响价格、履约或资金判断的条件缺失时先询问。Agent 可以把用户当前消息中明确表达的内容保存为非执行草稿，但不能推断缺失金额或改变保留目标。账户尚未选择时，不输出已经验证可行的资金结论，不创建订单或交易。首版使用需求草稿和月度预算项目，不建设独立的长期目标系统；商品选定和 active 目标变化由用户通过结构化界面确认，购买方案再独立确认。

检索范围限于银行平台已登记的商品或服务。登记资料至少包含商品、商户、价格、适用条件、可执行能力、数据更新时间和取消规则。展示型商品只能推荐或跳转；可执行商品才进入确认、下单和售后流程。标准主演示准备至少两个合格候选时，系统提供两套均符合当前约束、取向不同的方案，例如“省预算”和“偏体验”，每套列出项目预算拆分、必须保留项和可调整项；不硬凑三套方案，不把超出约束或没有执行接口的商品放入可直接执行的购买方案；展示型候选仍可单独推荐并标明仅能跳转。目录不足两个合格候选时，返回无足够可比较结果或现有候选，不以虚构商品补齐数量。

### 4.5 FR-07：确认、订单与支付

确认卡片必须列出商品、商户、数量、总额、适用条件、授权范围、有效期和环境来源。服务端重新读取报价与权限后创建订单；Agent 不能代替用户确认、填写收款方或扩大金额范围。

本地模拟支付用于日常开发、故障构造和微信小程序主链演示。M3 以独立 sandbox 场景新建代表性订单，通过受控外部浏览器交接支付宝收银台，并在同一运行内连续完成后续变化、退款与查询；不切换已有订单环境。付款已确认时恢复操作只查询原订单；状态未知时保留占用并先查单，不创建另一笔订单绕过未知结果。

### 4.6 FR-08 和 FR-09：变化后的调整

用户可更新一笔必要支出、工资延后等变化，修改预计收入日期，或直接改变消费意愿；已接入的账户事实变化也可以触发规则重算。系统沿用同一计划和已知订单按需重算影响，列出变动前后金额和日期，并生成待用户确认的建议。它不常驻模型等待变化，也不在没有确认时自动交易。

调整方案应区分尚未下单、已建单待付款、已付款和退款待核对等状态。未付款项目可以关单；已付款项目需要依据商户规则提交取消或退款；已经明确不可执行的商品只能提示用户自行处理。用户必须确认调整范围和可接受费用后才执行。

退款成功只增加已确认退款事实，不抹去原付款，也不自动恢复购买授权或主借记账户余额。沙箱退款证明渠道结果，不证明银行账户已经入账。

每次关键选择保存轻量决策记录：输入事实版本、规则计算结果、简短理由、方案差异、用户确认内容和实际操作结果。记录用于解释业务决定，不保存模型隐私思维链，不根据用户行为自动学习或改变规则。计划完成后提供轻量复盘，列出计划金额、实际支付、已确认退款、净额和未决事项。

## 五、核心数据口径

M1 已在 001—023 基础上增量完成至 029；其中 024—026 补资金事件与必要支出确认约束，027 支持新预算周期任务和退款恢复，028 支持未选账户或绑定预算周期的消费者 Agent 运行，029 补收口数据结构（分类展示覆盖、Agent 产物关联、订单善后预览、隔离场景登记）。旧迁移不改写，具体表和迁移职责以工程文档为准：

| 逻辑实体 | 主要内容 | 关键要求 |
| --- | --- | --- |
| 主账户 | 测试借记账户、余额快照、来源、查询时间 | 账户归属由服务端确定；余额不与信用额度混合 |
| 记账记录 | 收支、分类、来源、发生时间、关联订单 | 可纠正；与现金流承诺分开 |
| 资金安排 | 必要支出、当期账单／还款、预计收入、保留金额 | 每项有日期、金额、来源和确认状态 |
| 消费计划 | 目的、计划项、版本、规划周期、可规划空间 | 变化后生成新快照，保留历史事实 |
| 登记商品与报价 | 商品、商户、价格、条件、取消规则、可执行能力 | 报价确认前重校验，目录更新使旧报价失效 |
| 用户授权与确认 | 购买或调整范围、金额、期限、用户确认 | Agent 不能创建确认；资金权限由服务端校验 |
| 订单与支付 | 商品快照、支付尝试、环境、渠道状态、占用 | 已付款、未知和未付款分别处理；幂等号固定 |
| 取消与退款 | 原订单、费用、退款预计额、批次和渠道结果 | 预计退款与已确认退款分开，退款回原单 |
| 事件与证据 | 来源、时间、环境、关联号、脱敏行迹 | 业务事实可追溯，秘密不进入日志和导出 |
| 决策记录与复盘 | 输入事实版本、规则结果、理由、差异、确认和操作结果；计划／实付／已退／净额／未决 | 不保存模型隐私思维链，不自动学习或改写规则 |

核心金额使用整数分保存。每笔记录带环境标签：`simulation`（本地模拟）、`sandbox`（支付宝官方沙箱）或未来的 `production`。不同环境的账户、订单、支付和退款不能互相命中。

## 六、主场景与产品规则

标准演示数据的初始静态样例为：主借记账户余额 2,000 元，可调计划 400 元（已含晚餐估价 80 元），本月必要支出及当期还款 900 元，用户保留 500 元，因此当前未分配缓冲为 200 元。用户用 99 元报价替换晚餐 80 元估价后预计余量为 181 元；新增一笔 400 元必要支出后，计划形成 219 元缺口。正式计算仍按日期和账户事实执行。

在该场景中，系统应先展示计算依据和可行性卡，再推荐候选。标准目录有足够合格商品时，系统提供“省预算”和“偏体验”两套方案，分别列出项目预算拆分、必须保留项和可调整项；支付已确认后不能重复支付；新增支出后只能让用户选择保留、替换、延后或取消。若取消产生退款，退款未核验前继续保留 219 元缺口；即使支付宝沙箱返回退款成功，也只更新沙箱渠道事实，不直接写入主借记账户余额。

## 七、权限、金融和安全边界

保留旧项目已经建立的必要约束：真实用户确认、服务端重新校验金额和对象、购买与善后授权分离、支付和退款固定业务号、未知结果先核对、角色隔离、密钥不交给模型、模拟与沙箱凭据隔离。

不提供自有钱包、资金托管、自动转账、自动借贷、分期推荐、免确认扣款、跨账户资金归集或模型直接修改余额。不能把信用卡额度当成可用资金，也不能把用户同意取消写成商户或渠道已经退款。

## 八、P0、专项与非目标

P0 只要求一条可重复的主闭环：先从空状态提出生活目标和需求草稿 → 选择测试主账户并查看账目和 30 天安排 → 先取得可行性卡 → 比较登记商品的两套合格方案 → 用户确认并完成支付 → 新增必要支出 → 按需重新规划 → 用户确认调整 → 查询订单和退款事实并完成轻量复盘。

分批退款、商户拒绝／延迟、复杂贷款合同、多账户聚合、自动分类、全年预测、银行正式接口、完整商城生态、多 Agent 协作和长期目标管理保留为专项或后续方向，不作为首版 P0 放行前提。工资延后等变化由用户更新或已接入事实触发规则重算，按需生成待确认建议；不常驻模型、不自动交易。它们不削弱 P0 的授权、金额、环境、幂等和数据完整性要求。

## 九、实施阶段

实施固定为 M1 新后端、M2 微信小程序、M3 沙箱与用户证据三个大阶段；这是唯一主 DEV 顺序，每个阶段的具体产物、集中验收和暂停条件以[分阶段开发计划](../03-engineering/development-plan.md)为唯一来源，本 PRD 不另维护一套阶段清单。现有订单、确认、支付、取消和退款能力继续在主开发链路中复用，不因新方案把订单支付后移到 P2。大阶段末集中验收，不为每个小改动重复构建或全量测试。新的验收标准固定为 N01 至 N12，统一定义在[Demo 与验收](demo-and-acceptance.md)。
