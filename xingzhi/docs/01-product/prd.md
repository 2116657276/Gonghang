## 一、问题与目标

用户通过智能体安排消费后，改变计划可能同时影响已付款、待付款和尚未购买的服务。行止帮助用户表达变化、确认影响并协调善后，重点解决部分保留、停止新购买和退款事实难以统一解释的问题。

第一版必须从自然语言购买需求开始，通过自建测试商户和官方支付沙箱形成同一订单链上的购买、付款、变更、取消、退款与核验记录。单独的聊天演示、预置已付款数据或不同订单拼接不满足目标。

## 二、角色与范围

消费者提出需求和授权；Pi Agent 选择受控工具；行止业务服务管理方案与执行；测试商户提供商品、订单及退款执行；审核者只读查看脱敏证据。可以同一部署，不可用前端切换角色代替后端权限校验。

P0 为第一版放行必须满足的范围；P1 为增强项，不阻断基础闭环。S1 已在本地实现计划、授权、订单和明确标识的模拟流程；S2—S5 能力及全部 P0 综合验收仍未完成，不能据此称为首版交付。

首个完成的 MVP／Demo 必须覆盖全部 P0 基础功能；可逐阶段开发、逐步深化体验，但不能把本地底座或单笔支付演示称为首版交付。实施与交付顺序唯一见[分阶段开发计划](../03-engineering/development-plan.md)，S5 通过才形成首次完整交付。

| 需求 | 级别 | 内容与边界 |
| --- | --- | --- |
| FR-01 | P0 | 自然语言选购；查询测试商品和规则；信息不足时澄清，不虚构价格 |
| FR-02 | P0 | 展示购买方案、费用、计划总上限、范围和有效期；由真实用户确认后创建订单并占用预算；恢复购买沿用计划账本，提高上限须明确确认 |
| FR-03 | P0 | 获取官方付款入口，由用户完成渠道要求的确认；后端核验结果 |
| FR-04 | P0 | 明确暂停独立生效；阻断受控入口新购买并列出在途请求 |
| FR-05 | P0 | 部分保留与取消预览；区分已付款、待付款和未创建订单 |
| FR-06 | P0 | 确认绑定方案版本、订单和可接受费用；变更后重新检查，不沿用失效授权 |
| FR-07 | P0 | 按实际状态关单或提交取消申请，由商户处理原单退款；跟踪到可核验结果 |
| FR-08 | P0 | 重复请求、超时、回执乱序和重启后不重复业务扣款退款，不丢失待处理事项 |
| FR-09 | P0 | 展示状态来源、查询时间、实际金额与未完成事项；导出脱敏行迹 |
| FR-10 | P0 | 用户、商户和审核权限隔离；模型不能确认授权或取得支付密钥 |
| FR-11 | P0 | Pi 单 Agent、多工具；待用户或渠道结果时结束本轮，按事件恢复 |
| FR-12 | P0 | 模拟与沙箱隔离；只有官方沙箱实际证据计入交易闭环通过 |
| FR-13 | P0 | 带取消费用的部分退款、一次取消确认总额内分次退款、商户拒绝／延迟及明确失败处理；每批实际退款均绑定原单、独立固定退款号和已接受总额 |
| FR-14 | P1 | 官方 Agent 支付产品、小程序和独立合作商户适配；单独核验准入 |

不建设自有钱包、托管、分账、垫付、真实票务库存、全平台自动操作或多 Agent 集群。不把免用户确认扣款作为基础能力；真实资金另审。

## 三、用户流程与界面

购买阶段：输入需求 → 查询商品与规则 → 展示结构化购买卡片 → 用户确认 → 创建订单 → 官方付款 → 查询核验。变更阶段：暂停新购买 → 查询实际状态 → 展示影响卡片 → 用户确认 → 执行取消申请／关单 → 后台核验 → 汇总。

| 界面 | 必须显示 | 失败或等待状态 |
| --- | --- | --- |
| 用户工作台 | 对话、计划项、订单、预算、独立暂停按钮 | 模型不可用时仍能查询已知状态 |
| 确认卡片 | 订单范围、保留项、金额、费用、有效期和来源 | 过期、已确认、已撤回不得重复执行 |
| 付款与退款进度 | 待付款、在途、已确认、拒绝与待人工处理 | 不使用单一“完成”掩盖未决资金 |
| 测试商户端 | 测试规则、取消申请和退款执行记录 | 无权限或规则不满足时明确拒绝 |
| 证据视图 | 事件顺序、查询时间、脱敏关联号 | 标注模拟、沙箱和回放 |

基础配套包括测试账号登录／退出、计划列表与继续上次任务、结构化操作回退、查询权限撤回／续期、商户人工任务和受控脱敏导出。善后与查询授权分别展示、分别保存，P0 默认各 7 天；到期后的受托动作和商户已受理职责按领域规则区分。消费者能查看自己已有结果，审核者只能查看服务端分配范围。完整页面交付清单见开发计划 S4。

P0 固定为响应式网页：Vue 3/Vite 前端、Fastify 业务 API、PostgreSQL 与同代码库的独立后台执行者，均使用 TypeScript。PostgreSQL 保存授权、订单、支付、退款与任务的业务事实；本机 Redis 可在实际需要时提供非关键缓存或限流，不能保存唯一交易事实或承担任务正确性。消费者、测试商户管理员和只读审核者由服务端会话识别，前端切换视图不改变权限。Pi v0.85.1 已安装并通过本地无资金循环，历史真实 DeepSeek 只读／方案联调已通过；当前配置 `deepseek-flash` 的本地兼容性、请求体、固定场景及进程／授权连续样本已有记录，交易执行工具、事件恢复和官方支付仍须按 S4—S5 验收，且不得改变上述业务边界。

## 四、非功能要求

| 编号 | 要求 | 验证方式 |
| --- | --- | --- |
| NFR-01 | 页面关闭不影响已受理任务；进程重启可恢复 | R04、R05、R11 |
| NFR-02 | 相同业务请求至多产生一项业务操作，网络可重试 | P09、R06；检查固定业务编号 |
| NFR-03 | 状态来源可追溯，付款退款分别核对 | P01、P05、P07、P11、P13 |
| NFR-04 | 越权、密钥暴露和环境误用被阻止 | A08、A09、A11、R10 |
| NFR-05 | 暂停不依赖模型长时间推理；服务端先持久化暂停结果，再返回范围与在途清单 | A01、A02；本地目标与测量边界见运行文档 |
| NFR-06 | 模型轮次、工具调用、重试和等待均有上限；累计模型费用不超过 ¥100；Agent 入口采用每分钟 10 次、突发 2 的常规令牌桶，同一计划并发 1；未确定外部结果进入核对而非改参重试 | R12、R02、R03；具体账本、退避和密钥边界见运行文档，DeepSeek 实际价格按官方 usage 记录核对 |

## 五、完成定义

必须通过[验证策略](../04-quality/verification.md)的 P0 门槛，并提交同一可追溯业务运行的连续证据；允许因用户确认或外部结果而跨 Agent 会话恢复。本文不填写虚构性能目标、测试通过率或获奖概率。样例金额与四服务场景见[Demo](demo-and-acceptance.md)；规则与状态唯一来源为[领域设计](../02-domain/rules-and-state.md)。
