## 二、按大阶段检查

M1 集中核对迁移、种子、金额日期、流水关联去重、跨计划和权限约束及新 Agent 链；M2 集中做浏览器连续流程与必要角色检查；M3 完成新版 N 案例、沙箱连续演示、用户观察和交付构建。具体顺序见[开发计划](../03-engineering/development-plan.md)。

只对实际行为变更补最少回归检查，不建立覆盖率目标。已有代码、环境和输入条件未变的有效检查不重复。测试、类型检查、浏览器观察、模型调用和渠道结果分层记录；类型检查不能证明业务成功，模拟结果不能证明渠道或银行成功。

## 三、结果记录方式

每批记录日期、适用版本、案例、环境、结果和必要证据。状态使用未执行／通过／失败／外部条件阻塞；局部通过明确子场景。新方案所有 N 案例当前均为未执行，不因文档评审完成而更新为通过。

交易演示关联同一运行和原单号，标明账目来自测试数据，沙箱交易来自官方测试接口。只生成付款链接不算付款；退款等待不算到账；阶段性资金缺口不能被规划期末的预计收入掩盖。失败及复测只补实际发现问题的范围。

新种子加载和迁移验收不得覆盖原沙箱订单、业务退款号、未决任务、密钥或模型费用。演练用隔离环境，重置仅针对明确选择的模拟数据。

## 四、用户与交付

匿名访谈和情境任务记录用户是否理解资金范围、推荐理由、实际支出和退款等待。可记录步骤、耗时及错误，但不预填改善比例，不以少量样本推断整体青年群体。

新版必验范围通过后交付受控原型；金额、越权、误环境和假成功缺陷不得放行。未启用的复杂退款、通知和真实银行接入分别列出，不强行补齐无关专项，也不能声称这些已通过。

## 五、迁移方案的静态审核范围

本轮文档审核检查现有迁移执行器、种子覆盖逻辑以及新方案的模块衔接。已经核实迁移按文件独立事务执行、按文件名登记，旧文件改写不会重新应用；旧 seed 会按商品 code 覆盖并激活 A/B/C/D。计划因此采用增量迁移及独立新样本，历史已受理交易保留。

开工前的文档检查重点为：无账户目标草稿如何承接现有 Agent；用户原消息保存草稿、结构化商品选择与独立购买确认如何分层；余额基准及流水去重；各财务表允许的来源子集；账单分期覆盖；同账户多计划；账户撤回后的历史读取、新购买拦截和既有善后；旧入口不能绕过新准入；迁移失败如何恢复；沙箱结果如何与测试银行事实分开。

队员建议中的目标驱动、条件可行性、两套方案取舍、决策摘要和轻量复盘并入既有 N05／N06／N08／N09／N12，不另设一套验收流水线。变化触发规则重算，不自动执行交易；决策说明不保存模型私有推理。

文档审核通过只表示具备按计划开始实施的条件。SQL 的实际兼容性、新行为结果及新界面可用性必须在后续 M1—M3 获得证据；未运行内容不得预填通过。最终开工判断统一在[开发计划](../03-engineering/development-plan.md)记录。
