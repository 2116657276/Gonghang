## 一、对象与术语

计划项是购买意图，不一定有订单；商户订单是业务事实，支付尝试是渠道交互；退款申请是消费者诉求，退款执行是商户行为。购买授权和善后授权分开，Agent 会话不充当任一种授权。

变更方案包含保留、停止、关单、取消申请及费用预览；确认记录绑定方案版本和具体对象。暂停只限制行止受控购买入口，不冻结支付账户。退款“渠道确认”不自动证明银行卡可用余额变化。

## 二、领域不变量

| 规则 | 不变量 |
| --- | --- |
| BR-01 | 用户归属与角色来自服务端认证；模型传入的 userId、merchantId 不构成身份依据 |
| BR-02 | 购买确认绑定商品、数量、金额、商户、范围、有效期；服务端重算报价并检查版本 |
| BR-03 | 创建订单时原子检查计划预算、最新购买授权与暂停范围，并占用预算；付款交接重查授权但不重复占用；暂停后不准入新购买动作，在途动作继续核对 |
| BR-04 | 同一业务动作编号固定；相同幂等键不同参数拒绝，不生成新退款号绕过未知结果 |
| BR-05 | 内部金额使用整数分；同原单已成功退款加未决退款占用不得超过可退金额 |
| BR-06 | 预览不是授权；费用、对象或关键规则变化时，失效预览不得执行 |
| BR-07 | 商户审核与渠道退款独立于用户确认；退款回原交易，不接受模型提供收款账号 |
| BR-08 | 网络成功、业务受理、渠道处理成功分开；历史付款事实不能因全额退款而删除 |
| BR-09 | 退款不自动恢复购买权限；授权撤回不抹除已受理外部操作或已知交易事实 |
| BR-10 | 模型输出、商户文本和会话摘要都是输入，不能覆盖业务账本与确认记录 |
| BR-11 | 整体闭环只有全部必处理项终态且金额核对一致才完成；人工接管不是退款成功 |
| BR-12 | 模拟与沙箱对象、凭据和网关隔离；模拟结果不得回写沙箱交易事实 |
| BR-13 | 同一计划跨购买授权累计已支付与未决占用；恢复购买不重置账本，扩大总上限须明确确认；新授权不能使旧授权重新有效 |
| BR-14 | 善后与受托查询分开确认和保存，P0 默认各 7 天；到期／撤回停止新增对应受托动作，不抹除既有事实及商户自身处理职责 |
| BR-15 | P0 多次部分退款来自一次已确认取消的退款总额；每批独立固定退款号，批次成功额与未决占用合计不超过本次确认总额和原单可退额 |

## 三、状态与转换条件

| 对象 | 主要转换 | 关键条件 |
| --- | --- | --- |
| 购买授权 | 用户确认后创建有效授权；有效 → 暂停／撤销／过期 | 待确认的是方案；局部暂停另存范围；恢复创建新授权，不借新版本清空累计支出 |
| 善后／查询授权 | 用户确认后分别创建有效授权；有效 → 撤回／过期 | 默认各 7 天；续期创建新记录，查询续期不执行取消退款 |
| 方案 | 草稿 → 待确认；待确认 → 已确认／过期／拒绝；已确认 → 执行中 → 完成／待处理 | 过期或拒绝不能进入执行；执行前重查授权与快照；部分成功不能整体回滚成未执行 |
| 计划项 | 待执行 → 待确认 → 执行中 → 保留／停止／结束／待处理 | 已付款停止并不代表订单取消或资金退回 |
| 商户订单 | 已创建 → 履约中／取消处理中 → 已履约／已取消／取消拒绝 | 取消同意后仍可能等待退款，保存独立状态 |
| 支付尝试 | 待发起 → 等待付款／结果未知 → 已付款／确认未付关闭／明确失败 | 超时保持未知；关单与付款竞争时按渠道证据核查 |
| 退款执行 | 待提交 → 已提交待核对 → 渠道确认成功／明确失败／待人工 | 未知不释放退款占用；重试不改变原单与业务退款号 |
| 整体善后 | 未启动 → 处理中 → 仍有待跟踪事项／全部事项结束 | 转人工须显示责任任务，不能并入资金成功 |

这些是内部设计状态，不原样转发给渠道。适配器保留原始字段、查询时间及映射依据；相互矛盾的证据进入核对，不按“最后收到的通知”覆盖已确认事实。

## 四、金额与授权

购买方案确认时创建购买授权，绑定 plan、计划项／商品／商户范围、计划总购买上限、有效期和确认记录。授权的确认内容不可改写；暂停、撤销、到期等生命周期状态单独更新并保留事件和版本。P0 购买授权默认从确认时起 24 小时。创建订单限于确认的计划项和数量；重复调用不能为同一已确认计划项多建订单。

变更确认卡片分别展示善后执行与后续受托查询的订单范围、用途和截止时间；一次明确确认分别建立善后授权与查询授权，P0 默认从确认时起各 7 天。善后授权绑定保留／取消对象、关单或取消动作、用户接受的费用与退款总额；查询授权只允许跟踪这些订单及关联退款。用户可只续期查询；这不重新提交取消或退款。善后续期通过新的变更方案，只列尚未受理部分并重新校验规则。续期保留旧授权和原业务操作关联，不重复已受理动作。

到期或撤回后，尚未受理的对应受托动作停止，页面提供重新确认或人工处理入口。商户已受理的取消、已提交渠道的动作及商户自身对账按其职责继续；每个后台动作保存执行主体和用途，不能把用户受托查询换个名称继续执行。购买付款核验由商户交易职责承担；消费者读取自己的既有业务快照不等于新增渠道查询，查询撤回不剥夺其查看已知结果的权利。

暂停仅限制选定计划项或全计划的购买准入，不撤销善后／查询授权；整体暂停覆盖所有当前购买入口。恢复购买必须通过新的购买方案确认取得新授权，并明确恢复范围，范围外继续暂停；旧授权保持失效。若同一计划有多个有效购买授权，所有准入仍锁定同一计划预算并检查该计划的最新暂停范围。

累计已支付保留同一计划、同一环境内跨授权的所有已确认付款；已确认退款按唯一退款业务编号累计；当前净支出为前者减后者。预计退款只作预览。计划总购买上限默认 3000 元，剩余授权空间为总上限减累计已支付减支付占用；退款不自动回补。恢复购买默认沿用原总上限，需要提高时必须展示原上限、新上限、历史已支付与占用并明确确认；不是额外发放一笔 3000 元额度，也不能通过授权版本或复制订单隐藏原计划账本。新建独立计划不迁走旧订单或旧占用。

创建订单时原子占用预算并记录待发送任务；生成或再次读取付款交接不重复占用。明确未付关闭或确认未受理失败后释放；付款确认后将占用转为已支付。结果未知时继续占用。尚未创建订单的纯计划项不占用。若仅存在本地订单且可证明从未向渠道发出请求，可在本地关闭并释放；已经发出或不能证明未发出时必须核查渠道，不能直接释放。

退款按一次取消确认的总额处理。住宿 B 样例：基础全退 880 元；费用变体确认退 800 元、保留费用 80 元；分次变体在同一 800 元确认下分两批各退 400 元。每个批次独立固定业务退款号，重试保持原单、金额和退款号。创建取消退款安排时保留确认总额，防止并行取消重复占用同一权益；每批提交前原子占用其可退金额，明确失败才释放该批占用，成功转为已确认退款。明确失败的批次如需重新提交，先按原号核实渠道可重试条件；未知批次不能以新号替代。已经受理的同一取消申请不因新幂等键而再次建立退款安排。

退款分批是商户执行方式，不是 Agent 任意指定退款金额。成功批次不回滚，尚未成功部分继续跟踪；总额、费用或取消对象改变时重新预览并确认，不能覆盖旧确认。金额校验同时约束原单可退额和本次确认额度；不得以浮点数参与金额比较。

## 五、竞争与补偿

数据库事务不能撤销已被渠道受理的付款。暂停先更新授权并记录事件；已经发送的动作列入核对清单。关单遇到已付款，应重新生成适用的取消方案，而不是沿用仅限未付款关单的授权自动退款。

多订单部分成功后保留结果，只对尚未执行部分重新规划。发生费用变化时确认新方案；已退款订单不得为了“恢复原计划”自动重购。撤回后续查询权限时停止新增受托查询，保留已知记录和官方查询入口；商户自身对账职责不等同于消费者委托权限。

变更方案同时引用计划项和已存在订单。D 这类无订单计划项以计划项标识确认停止，不为它创建虚假订单或退款授权；善后／查询授权的订单范围只包含实际存在且需要处理或跟踪的订单。保留 A 不产生取消任务。确认已保存但执行入口尚未受理时，界面恢复后显示“已确认、待执行”，重查有效性后继续原方案；不因缺少 Agent 会话自动丢弃或重复确认。
