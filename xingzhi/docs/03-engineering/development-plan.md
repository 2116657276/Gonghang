## 一、执行原则与完成定义

按用户最新要求，先完成后端，再统一重构前端，最后完成综合交付。当前不修改 `apps/web` 的页面、组件、样式、路由或本地类型；后端业务、共享契约和服务端导出属于当前开发范围。已经实现的页面保留原状，不逐功能同步改造。前端重构必须建立在后端实现及统一验收结果上，不能以开始联调为由提前穿插页面开发。

小阶段只划分工作范围，不设置逐项测试、构建、审批或多角色流水线。类型检查、行为验证、模型评测和浏览器验收按大阶段集中安排；金额、授权、幂等或数据完整性已有明确缺陷时，可先做最小复现与修复核对。已有检查在相关代码与环境未变时直接复用；失败后只复测受影响部分。默认在最终候选版本构建一次，构建路径变更或构建失败才增加必要构建。

优先复用现有业务入口、适配器、任务与测试设施。禁止没有当前需求或实际问题依据的通用抽象、重复校验、重试、缓存、兼容层、依赖升级和目录重构；不新增测试框架、覆盖率门槛、CI、监控平台、自动备份平台或多 Agent 框架。资金、权限、外部输入与数据完整性的必要约束继续保留。

首个完整 MVP／Demo 必须包含全部 P0：从自然语言选购、用户独立确认、官方沙箱付款，到同一计划的部分保留、暂停、未付关单、取消退款、结果核验与脱敏导出；费用／分批退款、商户拒绝／延迟、权限隔离及必要恢复均不能推迟到首版之后。36 项是验收案例，不是必须新建的测试数量。P1 官方 Agent 支付、小程序、独立商户适配，以及真实资金、真实旅行履约、钱包、分账、公开部署和规模化优化不进入本轮。

常规开发已获授权，沿用既定规则直接执行。只有缺失信息会改变结果、需要扩大范围或新增外部操作授权时才询问；问题只阻塞依赖它的支线，其他后端工作继续。已有模型授权与人民币 100 元共享费用上限继续有效，不重复索取；官方付款、关单和退款按实际交易授权执行，不能由开发文档推定授权。

## 三、第一阶段：完成后端并统一验收

以下小阶段按顺序推进。外部条件未齐时跳过依赖该条件的联调，继续其他后端工作；不能把有阻塞的第一阶段标记完成，也不提前进入前端重构。

| 小阶段 | 实施内容 | 完成产物 |
| --- | --- | --- |
| 1.1 金额与授权 | 按 BR-13 区分累计支付、累计退款、净支出、未决占用和剩余购买空间；退款不回补购买空间，重新确认不清零历史。核对建单、付款交接、暂停范围、授权撤回／到期／续期及服务端导出的同一口径 | 共用业务入口、快照和共享契约一致；修正已有金额回归案例 |
| 1.2 Agent 执行与解释 | 合并处理确认与订单关联、执行后旧快照、未付关单与已付取消、模拟与沙箱、自动跟进与显式复核的混淆。复用工具返回和运行指令；明确意图直接生成草稿，歧义才澄清 | 写操作受独立确认与服务端准入约束；已知事实、金额及责任解释准确 |
| 1.3 善后与渠道 | 核对取消规则、费用／分批退款、拒绝／延迟、固定业务号、未知结果核验、人工任务及权限；按真实缺口修复现有适配器和 worker，不另建执行框架。一次汇总官方账号、设备和交易授权条件 | 服务端交易与善后闭环；具备条件时取得官方付款、原单退款／查询和未付关单证据 |
| 1.4 恢复与验收准备 | 核对 API／worker 中断、旧领取回写、Agent 中断接管及独立库备份恢复；恢复后先核对外部事实，不能重放资金写入。将历史证据映射到既有 36 项的后端子场景，标明可复用、待复测和缺失 | 可执行的集中验收场景及后端缺口清单，直接维护在验证记录 |

**统一验收：** 合并执行受影响的既有后端／契约检查及类型检查；集中核对本地 A/B/C/D 链、授权和金额、商户善后、实际进程及数据恢复。真实模型集中覆盖明确变更、部分保留、歧义、规则变化和恶意商品文本等既定缺口；新模型验证并入本批次，不逐提示词付费试跑。官方渠道在资源与授权齐备时集中联调，过程中有效证据直接复用，不在结束时再跑一遍。此阶段不做前端检查或交付构建。

金额依据 Demo 的标准样例核对：基础最终净支出 420 元、剩余购买授权空间 1700 元，暂停时不可新增购买；费用变体净支出 500 元，退款仍不回补购买空间。测试夹具使用其他报价时按相同公式核算，不强改夹具金额凑标准数字。

默认采用本机返回页主动查单，不为演示新建域名、云服务或隧道。未启用通知时，既定重复、乱序、验签子场景仍以标明层级的契约证据覆盖；实际通知场景明确记录未执行。渠道未形成待付款交易时不能以本地关闭冒充官方关单。官方条件未齐时可先给出本地后端验收结果及具体阻塞，第一阶段整体保持待完成；若需带阻塞进入前端，须由用户另行调整顺序。

## 四、第二阶段：统一重构前端并联调

进入条件是第一阶段后端实现与统一验收完成。此时再使用稳定的服务端契约统一整理页面、状态与操作，不逐个后端功能穿插页面修改，也不预设引入新的组件库或状态框架。

| 小阶段 | 实施内容 | 完成产物 |
| --- | --- | --- |
| 2.1 消费者主流程 | 统一对话与结构化入口、计划与预算、购买／变更确认、独立暂停、付款进度、退款批次、撤回／续期、停止跟进及失败回退；金额和操作依据持久事实展示 | 连贯的选购到善后流程，明确加载、等待、失败和下一步 |
| 2.2 商户与审核 | 统一规则预设、取消队列、固定退款批次、拒绝／延迟、人工任务领取与责任；整理审核范围、脱敏行迹、导出和下载过期反馈 | 三角色入口完整、权限反馈明确，展示术语一致 |
| 2.3 交互与联调收口 | 统一登录退出、刷新与计划恢复、确认焦点、键盘操作及窄屏布局；集中处理真实接口下的失效入口、旧响应和阻断操作的问题 | 桌面及一个代表性窄屏可完成主流程；额外尺寸仅在发现布局问题时补查 |

**统一验收：** 一次前端类型检查与集中浏览器联调，覆盖本地连续主线、三角色、恢复和必要失败状态。官方收银台按实际设备条件记录，不从响应式布局推断兼容。复用第一阶段的服务端证据，只对联调暴露且修复的服务端路径定向复测。此阶段不默认构建，不重跑全部后端检查。

## 六、暂停点与下次执行顺序

2026-09-13 用户要求开发先到此结束。本次仅维护文档，不继续开发、模型调用、浏览器测试或支付操作，不修改当前 `PAYMENT_MODE=simulation`。本地后端及当前模型已有证据见验证记录第十七至十九节；应用配置已按用户截图核对，商户编号已修正，只读官方查单及响应验签通过，但尚无官方付款成功证据。

下次恢复后先进行支付宝沙箱浏览器自动化测试，复用现有付款交接、官方收银台和后端主动查单。首批对象沿用运行文档中的 A 单 0.01 元付款后全退、B 单 0.01 元待付关单；仅对测试进程启用沙箱模式，不提前改变默认模式。通过判据是浏览器付款流程可完成，且后端核实原单付款、原号退款查询、待付关单和最终金额；仅登录成功、打开收银台或只读连通不能判为通过。无法自动完成的交互及未通过项如实记录，不自动扩建测试平台。

用户已明确后续模式切换要求：上述测试确认通过后，将本机 `.env` 的 `PAYMENT_MODE` 从 `simulation` 改为 `sandbox`，使 API 与 worker 加载同一配置。保留旧模拟订单的环境和历史事实，后续新订单走支付宝沙箱；不把旧模拟记录改标为官方交易。切换后只核对模式生效及必要的真实入口，不重复已有验收或全量构建。测试失败或条件缺失时保持 simulation，处理实际问题后仅复测受影响部分。

默认模式切换不等于第一阶段或完整 MVP 自动放行；余下官方特殊场景和综合验收继续按既有范围补齐。前端仍须等后端阶段整体验收完成后统一重构。
