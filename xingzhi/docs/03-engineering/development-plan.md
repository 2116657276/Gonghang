## 一、执行原则与完成定义

当前后端阶段已收口。本轮由后端负责人维护 `apps/server`、`packages/contracts`、数据库迁移／种子、worker、模型／支付适配、后端检查及 API／数据／运行文档；本次不修改 `apps/web`。前端开发者从第二阶段接手页面、组件、样式、路由、客户端请求和浏览器交互，依据稳定契约与服务端快照开展工作，不复制业务规则、不接触数据库或支付密钥。字段、错误语义或状态变化先由后端更新 API 契约和共享类型，再由双方联调；综合交付仍须通过完整 P0 验收。

小阶段只划分工作范围，不设置逐项测试、构建、审批或多角色流水线。类型检查、行为验证、模型评测和浏览器验收按大阶段集中安排；金额、授权、幂等或数据完整性已有明确缺陷时，可先做最小复现与修复核对。已有检查在相关代码与环境未变时直接复用；失败后只复测受影响部分。默认在最终候选版本构建一次，构建路径变更或构建失败才增加必要构建。

优先复用现有业务入口、适配器、任务与测试设施。禁止没有当前需求或实际问题依据的通用抽象、重复校验、重试、缓存、兼容层、依赖升级和目录重构；不新增测试框架、覆盖率门槛、CI、监控平台、自动备份平台或多 Agent 框架。资金、权限、外部输入与数据完整性的必要约束继续保留。

首个完整 MVP／Demo 必须包含全部 P0：从自然语言选购、用户独立确认、官方沙箱付款，到同一计划的部分保留、暂停、未付关单、取消退款、结果核验与脱敏导出；费用／分批退款、商户拒绝／延迟、权限隔离及必要恢复均不能推迟到首版之后。36 项是验收案例，不是必须新建的测试数量。P1 官方 Agent 支付、小程序、独立商户适配，以及真实资金、真实旅行履约、钱包、分账、公开部署和规模化优化不进入本轮。

常规开发已获授权，沿用既定规则直接执行。只有缺失信息会改变结果、需要扩大范围或新增外部操作授权时才询问；问题只阻塞依赖它的支线，其他后端工作继续。已有模型授权与人民币 100 元共享费用上限继续有效，不重复索取；官方付款、关单和退款按实际交易授权执行，不能由开发文档推定授权。

## 三、第一阶段：完成后端并统一验收

以下小阶段记录第一阶段后端的完成范围。第一阶段本轮已收口；外部条件未齐时只阻塞依赖该条件的专项验收，不影响按契约准备前端协作。

| 小阶段 | 实施内容 | 完成产物 |
| --- | --- | --- |
| 1.1 金额与授权 | 按 BR-13 区分累计支付、累计退款、净支出、未决占用和剩余购买空间；退款不回补购买空间，重新确认不清零历史。核对建单、付款交接、暂停范围、授权撤回／到期／续期及服务端导出的同一口径 | 共用业务入口、快照和共享契约一致；修正已有金额回归案例 |
| 1.2 Agent 执行与解释 | 合并处理确认与订单关联、执行后旧快照、未付关单与已付取消、模拟与沙箱、自动跟进与显式复核的混淆。复用工具返回和运行指令；明确意图直接生成草稿，歧义才澄清 | 写操作受独立确认与服务端准入约束；已知事实、金额及责任解释准确 |
| 1.3 善后与渠道 | 核对取消规则、费用／分批退款、拒绝／延迟、固定业务号、未知结果核验、人工任务及权限；按真实缺口修复现有适配器和 worker，不另建执行框架。一次汇总官方账号、设备和交易授权条件 | 服务端交易与善后闭环；具备条件时取得官方付款、原单退款／查询和未付关单证据 |
| 1.4 恢复与验收准备 | 核对 API／worker 中断、旧领取回写、Agent 中断接管及独立库备份恢复；恢复后先核对外部事实，不能重放资金写入。将历史证据映射到既有 36 项的后端子场景，标明可复用、待复测和缺失 | 可执行的集中验收场景及后端缺口清单，直接维护在验证记录 |

**统一验收：** 本阶段已合并执行受影响的后端／契约检查及类型检查，集中核对本地 A/B/C/D 链、授权和金额、商户善后、实际进程及数据恢复；当前结果为 55 项定向测试通过。真实模型、官方渠道和恢复证据按验证记录分层保留。前端检查与交付构建放在第二、三阶段，不用本阶段结果替代完整跨端验收。

金额依据 Demo 的标准样例核对：基础最终净支出 420 元、剩余购买授权空间 1700 元，暂停时不可新增购买；费用变体净支出 500 元，退款仍不回补购买空间。测试夹具使用其他报价时按相同公式核算，不强改夹具金额凑标准数字。

默认采用本机返回页主动查单，不为演示新建域名、云服务或隧道。未启用通知时，既定重复、乱序、验签子场景仍以标明层级的契约证据覆盖；实际通知场景明确记录未执行。渠道未形成待付款交易时不能以本地关闭冒充官方关单。官方特殊条件未齐时，后端继续保留具体阻塞，前端可以基于已验收契约开展不依赖该条件的页面工作。

## 四、第二阶段：统一重构前端并联调

第一阶段后端实现与本轮统一验收已经完成，第二阶段现可开始。前端开发者使用稳定的服务端契约统一整理页面、状态与操作；不逐个复制后端规则，也不预设引入新的组件库或状态框架。前端发现契约缺口时，先登记接口或数据问题，由后端负责人评估并保持向后兼容。

**统一验收：** 一次前端类型检查与集中浏览器联调，覆盖本地连续主线、三角色、恢复和必要失败状态。官方收银台按实际设备条件记录，不从响应式布局推断兼容。复用第一阶段的服务端证据，只对联调暴露且修复的服务端路径定向复测。此阶段不默认构建，不重跑全部后端检查。

## 六、当前执行位置与下次顺序

2026-09-14 已从暂停点恢复并完成支付宝沙箱浏览器自动化测试。专用计划中的 A 单完成 0.01 元付款，后端按原单确认 `TRADE_SUCCESS`，商户按固定退款号退款后查询到 `REFUND_SUCCESS`／0.01 元；B 单在官方收银台形成 `WAIT_BUYER_PAY`，后端按原单关单并查询到 `TRADE_CLOSED`。最终累计支付 0.01 元、累计退款 0.01 元、净支出 0、未决占用 0，详细证据见验证记录第二十节。

本轮已补齐模拟后端的直接缺口：迁移 012 将付款、关单和退款结果拆为独立配置，建单时固化三项结果；PENDING／UNKNOWN 不释放金额，付款与关单保留原操作供显式复核，退款未决继续形成商户复核责任。商户原规则接口可选更新三项结果，规则版本继续阻止旧预览执行。后端统一验收最终为 55 项通过、0 失败，服务端类型检查通过；本轮后端阶段据此收口。

当前不再整体暂停：后端进入维护和官方特殊场景补证支线，前端开发者可按交接规则开始第二阶段。录制 Demo 时再切换 sandbox，随后完成跨端与交付验收；不把尚未执行的前端、官方特殊场景或完整 36 项 P0 标记为通过。
