## 一、交付目标与文档分工

首个可交付版本必须能从自然语言选购开始，经用户确认和官方沙箱付款，在同一组测试订单上完成计划变更、部分保留、暂停、未付关单、取消退款、结果核验和行迹导出。全额退款、费用退款、分次退款、商户拒绝／延迟、权限隔离、重复请求和重启恢复均属于首版基础能力。允许界面、解释质量和运行效率逐步深化，不把这些基础功能改为后续选做。

### 1.6 模型 429 退避（2026-09-10）

本轮由开发代理完成 S4 不依赖官方交易的退避切片。API-24 使用 Pi 的请求适配入口，只对明确 HTTP 429 最多重试三次，支持 Retry-After 秒数和日期，否则等待 1／2／4 秒加不足一秒抖动。每次重试重新校验持久运行状态、8 次调用上限和共享人民币预算；每次请求保留 30 秒超时，等待计入 120 秒总时限。响应丢失、网络错误和部分流不重试。缺少 usage 的旧调用预占保留，成功响应只结算本次调用。运行结束和下一次模型调用前等待费用结算落库。

新增 5 项定向检查，该 429 切片共 36 项自动检查通过，服务端类型检查通过。只使用本机隔离数据库与受控 HTTP 响应，未调用外部模型或支付。结果与可复跑位置见[验证记录第十一节](../04-quality/verification.md)。这不代表同样编号数量的 36 项 P0 放行验收已通过；后续仍为交易工具、事件恢复、官方交易及综合验收。

停止前，工作区已写入共用业务服务、T05／T06／T07／T09 工具、事件排队与恢复、迁移 `009_agent_execution.sql` 和页面状态衔接的初步代码。涉及 `domain/business-actions.ts`、`agent-actions.ts`、`agent-events.ts`、`agent-recovery.ts`，以及既有路由、Agent 运行、worker 和确认页面。上述内容尚未完成行为验证；009 未由本任务执行到开发库。期间一次服务端类型检查报告了共用方案类型不一致，后续虽调整了类型声明，但没有重新核对最终工作区，不能记为类型检查通过。1.6 的 36 项自动检查只适用于此前 429 切片。

已形成的实现方向是：HTTP 和 Agent 共用业务准入；用户确认继续独立；付款交接不向模型返回签名链接；明确暂停从用户原始消息核定范围；有效确认与业务新事实分别触发执行恢复和只读解释。规则细节见 [Agent 运行设计第七节](agent-runtime.md)，持久化与竞争问题见[数据与事件第五节](data-and-events.md)，接口映射见 [API 契约第八节](api-contract.md)。这些新增章节明确区分既定约束、拟采用设计与待收口问题。

恢复开发时按下列顺序继续，不从 S1 重建，也不为了增加检查次数扩大范围：

1. 先收口共用业务服务，处理确认后的报价变化、付款交接的授权复查、局部暂停范围，以及多入口一致锁序。新预览应能使用最新报价，不能只拒绝旧报价却无法生成可用的新确认。
2. 再收口写工具，保证同一业务对象跨调用／跨恢复复用，不能只依赖工具调用号；T07 的同轮重复调用也不能重复推进版本。
3. 然后确定事件的一次性语义和中断接管方式，解决已终态对象的订阅、同步商户决定、队列取消和持续等待的展示问题。当前“按尝试创建新运行”的初步代码与旧文档“同事件只创建一个恢复运行”存在口径差异，须先按数据文档收敛，不能直接启用。
4. 最后完成页面与后台的衔接。确认前说明助手会继续执行的范围，确认后展示实际动作、订单和人工责任；恢复失败时保留结构化操作入口。

必要验证限定为受影响服务的类型检查，以及确认后改价／越权、重复执行／中断接管、局部暂停／伪造指令三组定向行为。其余已有证据按适用范围复用，不默认再跑全项目构建、所有浏览器尺寸或完整验收。真实渠道和真实模型测试另受既有授权及资源条件约束。

### 1.8 恢复开发：交易工具与事件跟进（2026-09-11）

本轮由主模型负责共用业务、权限与恢复判断，Luna 子代理负责范围明确的测试、页面和文档修改。沿用现有模块完成 T05／T06／T07／T09 与 HTTP 的共用业务入口；重新预览读取最新目录报价，旧确认在报价或规则变化后拒绝建单，局部暂停不阻断范围外的有效购买授权。同轮重复暂停即使使用不同工具调用号，也只推进一次计划版本。

事件恢复采用稳定队列事项与有界执行尝试：一个触发事实对应一个 `agent_wakeups`，中断或过期最多启动两次关联运行，旧尝试保持失败且不能再执行写工具；已受理业务仍按原订单、确认和操作复用。确认事件只允许继续对应确认；交易结果事件仅开放只读工具。观察在提交变更前建立，保存业务事实基线；已终态对象不持续等待，相同事实不反复触发推理。取消助手跟进会结束该分支的排队与推理，保留已受理订单和商户责任。

确认接口返回实际是否已排队的 `agentFollowupQueued`，页面据此提示助手继续或使用结构化按钮。助手面板区分推理失败、跟进失败与交易等待，支持停止整个关联分支；刷新只读取已有结果。迁移 `009_agent_execution.sql`、`010_agent_watch_facts.sql` 已应用行止本机 `xingzhi_dev`，没有修改其他项目数据库。

本轮定向证据统一记录在[验证记录第十三节](../04-quality/verification.md)。截至 2026-09-11，当前工作区 `pnpm test:targeted` 45 项通过，`pnpm typecheck` 与 `pnpm build` 通过；历史 31／36 项检查保持原适用范围，不能与当前测试总数混用，也不把本轮局部行为验证加成完整 P0 放行结论。后续继续补齐 T10 显式复核的受控 Pi 链、变更执行与商户善后的受控连续链、真实模型执行评测以及 S2 官方交易证据；真实付款仍需要用户完成官方收银台操作。

## 四、S1：本地业务基础

## 五、S2：官方沙箱支付能力

### 5.1 实施任务

1. 先在本机实现禁用外部调用的统一支付适配器、环境校验与受控付款交接页面；缺少沙箱配置时明确拒绝发送，不能退回到模拟成功。复核官方 SDK 与实际网页支付、通知、查询、关单、退款、退款查询契约。锁定使用版本、网关和验签方式，更新证据登记；不要直接照搬示例中的内存订单或退款判定。
2. 取得 Q-06／Q-08 后才启用沙箱调用。沙箱数据与模拟数据使用独立数据库或等效独立存储空间及凭据；正式交易通道保持未启用。固定域名不是本机主动查单演示的前置条件；`notify_url` 可留空。若进行异步通知验收，必须使用渠道可访问的 HTTPS 地址，可使用经用户授权的临时隧道，或后续云服务器地址。
3. API-06 生成受控付款交接，用户进入官方界面完成必要确认；付款返回页调用 API-06R 主动查单并等待服务端核验。再次获取交接不新建支付业务号，也不重复占用预算。
4. API-06R 主动调用 `alipay.trade.query`，完成订单号、金额、卖家和交易状态核对后落库；配置 `notify_url` 时再由 API-26 接收通知，保留验签所需原始格式并可靠去重。两条路径都保留来源和观察时间。
5. 实现未付关单和原单退款；退款请求号固定，退款成功必须满足适配器明确判据。未知请求先查原单；关单遇到已付款进入重新评估，不沿用未付关单授权自动退款。
6. 经商户权限入口验证一笔付款、同原单全额退款，并另建一笔可查得待付款的交易验证关单；全退、费用和分批变体使用独立运行，不能在已全退订单上继续退款。

### 5.2 交付与验收

本机准备交付适配器、付款页交接、配置缺失提示及主动查单入口；取得前置条件后补齐单笔付款／退款及未付关单证据。配置并授权通知地址后，再补回调验签、设备与通知可达性记录。重点执行 P01、P02、P05、P07、P09—P12，以及 R02、R03、R10；通知异常和竞争条件可以用经标记的适配器契约测试验证，渠道成功仍必须有官方证据。

| S3-03 费用与分批 | 全退／费用／分批使用独立取消场景；分批从一次确认总额拆出固定批次，校验原单额度和确认额度；同一申请不因重复点击再建安排 |
| S3-04 授权到期 | 用户受托动作与商户已受理职责分开；到期／撤回停止新增对应受托操作，允许查看已知事实与重新确认，不自动扩权 |
| S3-05 明确拒绝与失败 | 显示原因、已退／未退金额、责任与下一步；商户拒绝可作为处理终态，但不是退款成功；延迟和未知继续列入未决事项 |
| S3-06 人工任务 | 超时、未知或可安全重试耗尽后持久化责任任务；商户可领取、查原单、按原请求重试和记录结果，不可手工填“已退款” |
| S3-07 恢复与去重 | 调用前后崩溃、重复通知、退款先到付款后到、付款／关单竞争、两 worker 领取；恢复检查领取版本及渠道事实 |

商户端实现 API-20—API-23，用户端展示各订单结果、退款批次、整体善后和人工责任；API-25 合并显式查询任务并检查用途。自动规则决定、延迟人工处理与退款批次复用同一业务约束，故障注入只用于模拟或隔离的契约场景。

### 6.2 交付与验收

通过结构化表单，在同一次运行中从选购付款开始走完 A/B/C/D 善后；金额符合 Demo 基础表。另行完成费用、分批、拒绝和延迟场景，分批展示第一笔成功、第二笔待处理及最终两笔成功，不提前扣除未确认退款。

重点执行 P06、P08、P09、A03—A07、A10、R01—R08；复核 S1/S2 受影响用例。每个失败或等待状态能找到责任和下一动作。此阶段可以展示完整结构化操作版，仍因交易执行、完整恢复和最终验收未完成而标为开发中。

## 七、S4：Pi 与全功能交互

### 7.1 Agent 主流程

恢复开发后，当前单 Agent 已接入 T01／T02／T03／T10 只读工具、T04／T08 方案工具及 T05／T06／T07／T09 受控执行工具；T10 在普通用户消息中可按明确请求进入 API-25 复核，事件恢复仍只读。自然语言购买先查询目录，再生成确认卡片；自然语言变更先识别明确暂停意图并执行暂停，再生成影响方案。含糊取消要澄清，商品描述不能成为用户确认。金额、版本和权限在业务服务重查，模型不访问数据库、商户退款接口或任意网络地址。模型调用受 ¥100 累计预算、每分钟 10 次／突发 2 的服务端令牌桶、同计划单运行和每轮技术上限约束。

用户确认由专属 UI 调用 API-04／API-11，模型没有确认工具。确认及渠道业务事件可恢复新一轮 Agent，但事件重复不重复运行或写入；等待用户或渠道时结束本轮。页面离开、运行取消或模型达到上限后，已受理业务任务仍由 worker 处理。会话恢复使用最新业务快照，不按聊天记录重放写工具。T10 读取已知事实；沙箱付款主动查单调用 API-06R，其他既有交易复核在有效查询授权下调用 API-25。

模型不可用时，目录、结构化购买／变更方案、确认、暂停、订单查询和已授权任务仍可操作，提示自然语言能力受限。回退是首版功能的一部分，但不能代替 Pi 验收。

Agent 已完成两个历史可验证切片：T01／T02／T03／T10 的只读快照、无资金烟测，以及 T04／T08 的持久化方案与专属确认 UI。恢复开发后 T05／T06／T07／T09 已接入共用业务服务，并以受控数据库与确定性 Pi 流完成确认后建单、模拟付款、只读事实恢复、重复执行、局部暂停、跨范围拒绝和中断接管的局部验证；T10 显式复核仍缺一条从普通用户消息到 Pi 工具的受控链。任何写工具继续受服务端越权、失效确认、错误环境和幂等约束；不为 Agent 复制一套 SQL 或商户退款逻辑。

### 7.3 交付与验收

交付 Pi 工具、运行与恢复、全部角色页面、降级操作和脱敏导出。执行 P13 连续主流程、A01、A03、A04、A09、A11、R04、R11、R12；记录实际模型、工具、版本、调用次数和费用。此时 FR-01—FR-13 应全部达到实现待验收，仍须完成 S5 才能放行。

## 八、S5：综合验收与首次交付

1. 按验证策略核对全部 36 项用例，每项记录通过／失败／阻塞及证据；既有有效记录可复用，发生相关修改的用例才重跑。新增规则作为已有案例的子场景检查，不因子场景批量生成测试文件。
2. 从空计划完成一次 Pi 驱动的官方沙箱连续运行：选购、确认、付款、变更、善后、最终核验。A 保留、B 明确退款、C 渠道关单、D 无订单，预算和净支出正确；费用和分批变体有独立证据。
3. 检查登录隔离、服务重启、页面恢复、通知去重、模型回退、授权撤回／续期、人工责任、手机布局和导出；确保没有无响应按钮或以占位数据冒充已实现的 P0 能力。
4. 检查环境示例无秘密、运行说明可按步骤启动、数据库迁移及种子可用；在独立测试库演练一次备份恢复。首次构建交付包时执行对应构建检查，普通文档改动或无关变更不反复全量编译。
5. 整理完整验收证据、4—6 分钟演示脚本、已知限制、未决事项和操作说明。只有全部 P0 门槛满足时更新阶段状态及项目表述，不因答辩需要把阻塞写成通过。

交付物包括可运行应用、项目配置与锁文件、迁移及种子、启动与故障处理说明、脱敏验收记录、连续交易证据和可读行迹导出。存在待核对资金、未通过权限控制、缺失 Pi 或缺失官方沙箱能力时，只能交付“开发中版本＋明确阻塞”，不能称为本计划定义的首个完整 MVP。

## 九、S6：首版之后逐步深化

首版完成后按实际反馈选取任务，不同时铺开。每次深化仍需明确输入、改动范围、定向验收和剩余问题。

| 深化方向 | 输入与任务 | 交付／验收 |
| --- | --- | --- |
| 交互与解释 | 基于真实使用问题，改进状态措辞、卡片、恢复入口和移动布局 | 用户能理解已退、待退、保留和责任；原闭环保持通过 |
| Agent 效果 | 基于失败案例改进澄清、上下文和提示词，控制调用成本 | 固定同一案例与模型条件比较，记录实际改善及退化，不预填指标 |
| 现有商户规则 | 在既有范围内丰富取消条件和展示，保持确认总额、版本与权限约束 | 新规则有清楚实例和金额验证；新的业务能力先确认再扩展 |
| 稳定性与部署 | 根据实际故障、访问量及部署目标调节参数、观测和备份 | 针对观察到的问题验证；公开部署或真实用户数据先关闭相应条件 |

FR-14 的官方 Agent 支付产品、小程序和独立商户适配属于 P1，另行立项；真实资金、真实旅行履约、钱包、分账等不因“深化”自动进入开发范围。
