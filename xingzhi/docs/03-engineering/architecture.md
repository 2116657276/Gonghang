# 行止系统架构与迁移边界

更新日期：2026-09-15。状态：目标设计；原交易模块已有实现，新增账户、记账和规划尚未实现。

## 一、总体结构

复用 Vue 3/Vite 响应式网页、Fastify 业务服务、PostgreSQL、独立 worker 和 Pi 单 Agent。网页展示银行微应用原型，不能宣称真实嵌入银行 App。沿用现有 TypeScript 和锁定依赖，不增微服务、消息队列、第二个 Agent 编排层或通用银行平台。

服务端计算金额与状态，PostgreSQL 保存业务事实，worker 处理已受理的渠道任务。Pi 解释需求、查询受控工具，并可按用户当前消息明确表达的内容保存非执行目标草稿；商品选定、active 目标变化和购买分别由用户通过结构化界面确认，再由业务层执行。模型和前端都不能写入支付成功或银行余额事实。

## 三、数据流与边界

账户及还款来源→用户确认必要安排→服务端规划快照→候选及报价→用户确认→订单与 worker→来源可追溯的支付／退款结果→新的规划快照。银行事实、测试账目和渠道事实各自保存来源；展示整合不等于混写事实。

现金流按账户可见范围合并相关计划，购买权限仍按具体计划检查。规划只读计算不占用真实银行卡余额，消费确认也不形成银行冻结。执行前重查最新资金安排及确认依据，处理变化时重新预览，不依靠模型自行推断授权。

新银行数据首版为受控测试资料，不调用个人网银抓取或自动登录。将来接银行接口需有具体权限和来源契约，不能因已有支付适配器就假定已支持银行读数。

## 四、工程迁移

按[数据设计](data-and-events.md)增量迁移，保留交易链和历史业务编号，不把 SQL 重构等同于清库。默认种子替换为新场景；原固定样本保留为隔离回归资料。消费者界面先等待后端契约稳定，按[开发计划](development-plan.md)推进。

必要并发、金额和权限约束由既有事务与唯一约束落实；小规模目录直接查询与规则筛选，不引入向量库、智能推荐训练或统一事件总线。恢复先核对既有业务事实，不重新发送可能已执行的资金动作。

## 五、队员建议的最小落点

生活目标使用 `plans`／`plan_items` 扩展少量日期与可调整属性；可行性来自资金计算服务；两套方案比较复用目录和只读计算，选定后复用 `proposals`／`confirmations`。决策摘要、变化差异和复盘使用现有快照、事件与导出，不新增独立目标中心、资金池、偏好学习服务或多 Agent。

微应用入口可先记录目标，再引导补齐账户与资金资料。账户不足时只允许草稿和解释，不输出已验证可行结论或放行交易。新 API、字段及旧工具耦合以接口和数据设计为准，必要改造在 M1 一起收口。
