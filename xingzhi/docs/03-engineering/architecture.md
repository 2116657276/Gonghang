# 行止系统架构与迁移边界

> 本文维护现行系统边界与原交易底座复用说明；M2 客户端细节见[微信小程序前端实施方案](miniapp-frontend.md)。新消费者月度模型、需求草稿及交易路径以 [A/B 后端总方案](../../行止_AB后端开发总方案_现状接口数据库任务.md)为准；新规划不双写旧 cashflow 表，新 Agent 不继承旧执行工具。

更新日期：2026-09-17。状态：原交易模块继续保留；001—029、A00—A06 与 B00—B07 的核心实现及 M1 补充收口（含 HTTP 集中验收）已进入当前基线，微信小程序和新流程支付宝 sandbox 连续演示仍待完成。

## 一、总体结构

M2 消费者采用 Taro 4.x + Vue 3 + TypeScript 微信小程序，拟新增 apps/miniapp；现有 Vue 3/Vite 网页保留商户、审核与历史交易善后。Fastify、PostgreSQL、独立 worker 和 Pi 单 Agent 继续复用，不增微服务、消息队列或通用银行平台。小程序是受控原型载体，银行 App 宿主仍属未来合作条件，不能宣称已经嵌入。小程序会话接入属于 M2.1 待实现增量，沿用原会话存储与权限，详见[API 契约 1.3](api-contract.md#13-m2-小程序会话接入待实现)。

服务端计算金额与状态，PostgreSQL 保存业务事实，worker 处理已受理的渠道任务。Pi 解释需求、查询受控工具，并可按用户当前消息明确表达的内容保存非执行目标草稿；商品选定、active 目标变化和购买分别由用户通过结构化界面确认，再由业务层执行。模型和前端都不能写入支付成功或银行余额事实。

## 三、数据流与边界

账户及还款来源→用户确认必要安排→服务端规划快照→候选及报价→用户确认→订单与 worker→来源可追溯的支付／退款结果→新的规划快照。银行事实、测试账目和渠道事实各自保存来源；展示整合不等于混写事实。

现金流按账户可见范围合并相关计划，购买权限仍按具体计划检查。规划只读计算不占用真实银行卡余额，消费确认也不形成银行冻结。执行前重查最新资金安排及确认依据，处理变化时重新预览，不依靠模型自行推断授权。

新银行数据首版为受控测试资料，不调用个人网银抓取或自动登录。将来接银行接口需有具体权限和来源契约，不能因已有支付适配器就假定已支持银行读数。

## 四、工程迁移

按[数据设计](data-and-events.md)增量迁移，保留交易链和历史业务编号，不把 SQL 重构等同于清库。通用 `db:seed` 仍保留旧 A/B/C/D 目录和测试账号；A00 资金样例与 B00 新目录使用独立入口，原固定样本保留为隔离回归资料。M1 收口与构建／提交登记已完成，消费者小程序按[开发计划](development-plan.md)的 M2.1—M2.4 推进。

必要并发、金额和权限约束由既有事务与唯一约束落实；小规模目录直接查询与规则筛选，不引入向量库、智能推荐训练或统一事件总线。恢复先核对既有业务事实，不重新发送可能已执行的资金动作。

## 五、队员建议的最小落点

新消费者目标先保存为 `planning_drafts`，用户确认后写入自然月 `budget_periods/budget_items`；可行性来自资金计算服务。两套候选分别取得评估，选定后沿 `purchase_intents` 和本人确认创建订单；旧 `plans/plan_items/proposals` 不承接新消费者购买。决策摘要、变化差异和复盘使用现有快照、事件与导出，不新增独立目标中心、资金池、偏好学习服务或多 Agent。

微应用入口可先记录目标，再引导补齐账户与资金资料。账户不足时只允许草稿和解释，不输出已验证可行结论或放行交易。现行 DTO 以共享契约和 A/B 总方案为准，M2 不恢复旧 Agent 执行工具；渠道交接与小程序运行差异由小程序方案维护。
