# 行止微信小程序前端实施方案

更新日期：2026-09-17。状态：方案已确定，Taro 应用、小程序会话接入和真机验收尚未实施。本文是 M2 前端实现边界的唯一来源；阶段顺序与完成条件见[开发计划](development-plan.md)，业务字段见[共享契约](../../packages/contracts/src/consumer-backend.ts)及[A/B 后端总方案](../../行止_AB后端开发总方案_现状接口数据库任务.md)，N01—N12 判据仍由[Demo 与验收](../01-product/demo-and-acceptance.md)维护。

## 一、平台、交付与复用范围

消费者采用 Taro 4.x + Vue 3 + TypeScript，主要运行和验收端为微信小程序。初始化时选定相互兼容的 Taro、Vue、构建插件与 Node 版本，写入现有锁文件和运行说明，不在文档中猜测最新补丁号。现有 Vue 技术栈继续使用；不同时迁移到 React，不新增后端框架、数据库或 Agent 编排层。

拟新增 `xingzhi/apps/miniapp`，只承接新消费者流程。`apps/web` 保留商户、审核和历史交易读取／善后，消费者新购买不得绕回旧路径。`apps/server`、worker、PostgreSQL 与 `packages/contracts` 继续复用。H5 只作为必要时的辅助调试或渠道交接页面，不列为第二套完整消费者产品，也不能替代真机验收。

| 演示内容 | 首版处理 | 不代表什么 |
| --- | --- | --- |
| 微信小程序完整消费者链 | 调用真实业务 API，在 simulation 下完成规划、确认、模拟付款、调整与退款；界面常驻“演示环境”，关键动作标明模拟 | 不代表微信支付接入、真实银行数据或银行 App 上线 |
| 支付宝沙箱新消费者链 | M3 独立建立 sandbox 场景和订单，保留同一运行的付款、变化确认、原单取消退款与查询；必要时在外部浏览器交接收银台 | 不把 simulation 订单改环境，不把不同运行片段拼成同一条链 |
| 微信支付 | 本轮不接入；如赛事明确要求，再单独确定渠道、商户条件与验收 | Taro 不会把支付宝参数转换为微信支付参数 |

小程序内不假定能够直接打开支付宝收银台。M2.3 需确认现有 `payment-handoffs` 的沙箱输出及外部浏览器承接方式，必要时只补一个受控交接页；页面仍须验证本人会话与订单归属，不在二维码、日志或分享链接中暴露会话令牌。未验证前 N12 保持未执行或阻塞，不用模拟结果替代。具体连续证据归[Demo](../01-product/demo-and-acceptance.md)维护。

## 二、页面与用户流程

一级入口固定为“规划、账目、订单”，使用小程序页面路由和原生 tabBar；账户选择、项目编辑、候选比较、购买确认及调整确认在流程内进入。没有账户或周期时仍可表达目标，但只形成需求草稿。已有周期时，“规划”优先展示当前结论、资金依据和下一步动作，不以空聊天框覆盖已有事实。

| 页面或区域 | 内容与交互 | 主要接口来源 |
| --- | --- | --- |
| 登录／会话 | 测试账号登录、退出、失效后重新登录；不新增微信身份绑定 | API 契约 1.3 的拟新增小程序会话接入 |
| 规划首页 | 目标输入、当前周期、必要／可调项目、可行性、未知资料、突发支出入口 | 预算周期列表／详情、Agent 运行列表／详情、规划草稿 |
| 账户与预算准备 | 选测试主账户、显示来源和时间、选择自然月、逐项确认预算、明确确认必要支出后激活 | finance/accounts、budget-periods、items、activations、savings-target |
| 候选比较 | 同一需求的有效报价、规则、资金影响；各候选分别评估，用户选定 | offers、quote、finance/assessments |
| 购买确认 | 商品、金额、日期、规则、版本、有效期、环境及动作范围 | purchase-intents 创建／确认／放弃；列表／详情待 API 契约 1.4 补齐、payment-handoffs |
| 账目 | 已发生收支与分类纠正；未来还款另列；预计收入、待退款及信用额度分开 | finance/accounts、流水分类覆盖接口 |
| 订单及详情 | 订单列表、已受理操作、付款／退款／到账各层状态、原单善后入口 | 已有订单详情／操作查询／善后；消费者列表及操作引用待 API 契约 1.4 补齐 |
| 变化与复盘 | 新增必要支出、前后差异、可选调整、本人确认、未决事项与复盘 | emergencies/assess、adjustments、budget-periods/:id/review、预算事件 |

表中是页面目标与接口族导航，标记为待补的读取接口按[API 契约 1.4](api-contract.md#14-m2-交易读取与恢复补充待实现)在 M2.3 先实施，不是当前可调用接口；准确路径、方法和请求体以当前共享契约及 A/B 总方案第 5、11 节为准。账目首版复用已有账户读取中的 ledger/obligations，不因为页面拆分另建后端列表接口。

优先提取四类复用卡片：可行性卡、候选比较卡、购买／调整确认卡、变化前后对照卡。基础按钮、输入、空状态和状态标识按实际重复抽取；不预建完整设计系统，不为少量金额趋势引入大型图表库。采用 Taro 基础组件，按小程序重新处理布局、样式作用域、弹层和输入事件，不直接复制网页 DOM。输入框、键盘遮挡、底部安全区、长文本和金额换行在真机核对。

## 三、代码和状态组织

应用内以 `pages` 承载路由，`components` 承载复用卡片，`composables` 承载实际复用的流程逻辑，`services` 承载请求与业务接口调用。只有会话、当前账户／周期等确有跨页需求的信息共享；页面编辑值留在页面内，初期使用 Vue 响应式能力，不预先引入另一套状态库。

共享 DTO 优先 `import type`，需运行时校验才引入对应 schema，避免把整套旧契约或服务端依赖带进主包。首个小程序编译即验证 workspace TypeScript 引用、模块解析及产物体积；只在实际包体接近平台限制时做按页面分包或依赖调整，不先搭复杂分包体系。

服务端保存余额、评估、意图、订单和操作事实。前端只格式化整数分和日期，不重算可购买空间、不乐观增加余额、不推断支付成功。日期遵循业务 `Asia/Shanghai` 与 `YYYY-MM-DD` 语义，不按手机本地时区重新解释预算日。

| 状态或错误 | 页面处理 |
| --- | --- |
| `allowed` 且依据未过期 | 可进入待确认流程；最终仍由服务端事务复核 |
| `needs_adjustment`／`blocked` | 展示原因、影响日期和可调整项，不放行购买 |
| `unknown`／缺失快照 | 明确资料不足；`shortfallMinor=0` 在 unknown 响应中只是不可量化，不显示“无缺口” |
| `VERSION_CONFLICT`／`QUOTE_STALE` | 保留用户编辑内容，重新读取和评估，展示变化并重新确认，不自动改价提交 |
| `FINANCE_SCOPE_REVOKED` | 停止新规划／购买，显示撤回与历史快照；原订单读取和善后继续 |
| HTTP 202／`PROVIDER_RESULT_UNKNOWN`／请求超时 | 显示受理或核对中，保留原订单／操作关联，不直接标失败或重复付款 |
| `UNAUTHENTICATED` | 清理当前会话与用户展示缓存，重新登录后查询原操作；不自动重放交易 |

可行性卡的展示文案按 Demo 四类结论组织，但不能把“依赖预计收入或退款”映射为可执行 allowed。所有资金卡展示来源和时间，订单渠道状态与测试账户到账状态分栏。

## 四、请求、会话与幂等

请求层使用 `Taro.request`，配置实际 API 基址，按 HTTP 状态码判断业务成功，不把网络 API 的 success 回调视为交易成功。统一消费新接口 `{data,meta}` 与 `{error:{code,message,details?},correlationId}`；旧会话／操作读取、Agent 前置拒绝等按实际形状处理：error 为字符串时读取顶层 message，为对象时读取 code/message，归一为页面错误。Agent 未配置当前返回单层 MODEL_NOT_CONFIGURED／503，展示结构化填写入口并停止自动调用；不强行把所有响应断言为新 DTO。204 无正文单独处理。

当前后端只有 Cookie 会话，登录和多处写路由要求 `Origin === WEB_ORIGIN`；这不是已经适配的小程序接口。M2.1 按[API 契约 1.3](api-contract.md#13-m2-小程序会话接入待实现)增加最小的消费者令牌传输，复用 sessions 的失效、撤销和权限判定；网页 Cookie 的 Origin 防护保持。不能通过伪造网页 Origin、取消全部来源校验或在客户端填写 ownerId 来接通小程序。该变更只解决客户端会话，不增加微信登录、开户或身份绑定。

同一次提交在发送前生成并保存稳定的 `Idempotency-Key`，同路径、同参数的重试复用原键；明确变更内容、重新评估并重新确认后才视为新动作。前端禁用重复提交按钮仅改善交互，最终去重仍由服务端负责。只保存必要的提交键、关联 ID 和恢复所需最小参数，并绑定当前用户；不缓存密码、支付链接或模型密钥。恢复前重新核对用户身份与服务端状态，用户切换或退出时清理前一用户本地信息。

保存失败或超时且尚无返回 ID 时，保留原请求依据，使用同键同参数查询式重试以取得原结果，不生成新键建第二单。已有意图、订单或 operationId 时优先读取详情。版本冲突、报价失效或用户取消后不得后台自动重放。接口接入不新增通用无限重试或离线交易队列。

## 五、Agent、生命周期与恢复

Agent 通过现有独立消费者运行入口启动；首版不新增 SSE、WebSocket 或逐字流式协议。仅在运行或业务操作未结束且页面可见时按当前节奏轮询相关状态；页面隐藏或卸载停止轮询，重新显示时先读取当前事实。切换账户／周期后丢弃旧上下文迟到响应，避免其他周期数据覆盖当前页。

运行详情中的 `artifacts` 是草稿入口，通过草稿详情构建卡片，不能从模型自然语言提取交易依据。模型最终解释失败但已保存草稿时，仍提供草稿读取及结构化补全；取消模型运行不撤销已受理交易。无账户运行可恢复，缺失字段由用户补齐并逐项确认，不因一次聊天提交直接写 active 目标或创建订单。

冷启动、页面重新显示和登录恢复后，先读本人周期、运行、意图、订单和操作状态，不重启同一模型运行或新建交易。退款等待页区分申请、受理、渠道确认、账户到账；渠道成功不直接变成余额增加。对已经终结的对象停止轮询。

## 六、开工资料与验证落点

按[开发计划 M2](development-plan.md#三m2微信小程序与接口联调)逐步实施，不同时铺开全部页面。现有 `pnpm dev` 只启动网页、服务端和 worker；小程序命令、AppID 和构建输出应在应用实际创建后补入[运行说明](../../README.md)，本文件不把尚不存在的命令写成可执行入口。

M2.1 首先核对 AppID／开发权限、微信开发者工具、至少一台演示手机和可供手机访问的后端地址；体验版需落实 HTTPS、服务器域名和体验成员配置。手机 localhost 不指向开发电脑，网页 Vite 代理也不会自动服务小程序。域名或设备缺失时可继续本地结构与接口开发，真机出口保持未验证，不以关闭域名检查作为交付证据。不因文档定稿自动购买域名、发布服务或上传体验版。

每次需要新基准时使用新的隔离场景标识，连续业务链沿同一场景；细则见[开发计划第五节](development-plan.md#五验证节奏与恢复入口)。现有场景已创建 active 周期，适合金额与交易联调，不能单独证明“新建 draft→逐项确认→激活”通过；M2.2 为该路径准备独立的无当月周期测试账户，现有入口不支持这一准备模式，因此在 M2.2 开头为既有 consumer-scenario 入口增加 account-only 模式（待实现，当前命令尚不可用），只创建独立消费者、测试账户、有效快照、还款和匹配目录，不创建周期／预算项目；默认模式保持原 active 样例，输出账号、accountId 和准备模式，复用同键不得覆盖或切换模式。用户从 UI 建周期、添加必要／可调项目并确认激活；不清除原周期，也不以隐藏页面数据假装数据库为空。

N01—N11 在微信真机 simulation 连续验收，并在对应编号补记登录失效、重复点击、提交超时、版本冲突、账户撤回、切后台和冷启动恢复。N12 保留独立 sandbox 连续证据及用户观察要求。记录实际代码版本、Taro／微信基础库版本、手机系统、场景、来源与结果；开发工具或 H5 结果单独标明。受影响类型检查和小程序构建按阶段执行；会话权限改动做定向后端回归，其余未变的 M1 证据复用。
