## 一、事实分层

会话保存用户与模型交流；PostgreSQL 保存计划、授权、订单和操作；渠道证据保存查询与通知依据。三者关联但互不替代。P0 使用 PostgreSQL、SQL 迁移和参数化查询；009—011 已应用本机 `xingzhi_dev`，交易工具、事件恢复、退款批次关联、人工任务按订单展示和页面状态字段已接入，局部行为验证与类型检查结果见[验证策略第十三、十四节](../04-quality/verification.md)。下表继续作为实体约束，不要求逐项建立包或服务。

| --- | --- | --- |
| User / Session / ReviewScope | 测试账号、密码摘要、角色、会话摘要及期限、审核计划范围 | 角色由服务端配置；会话退出失效；密码摘要使用专用密码算法，不记录明文 |

| ManualTask / EvidenceExport | 原操作、原因、责任角色、下一动作、复核时间；导出范围、生成时间、过期时间 | 人工接管不改资金事实；导出只读且脱敏 |
| ChannelEvidence | 原始状态、证据类型、关联号、发生及收到时间、核验结果 | 秘密字段不进入日志与导出；访问受限 |
| Event / AgentRun / AgentUsage | 事件号、对象序号、关联运行、触发事件、动作、版本、来源；父运行、逻辑恢复事项、attempts、观察与队列状态；服务商、模型、请求／响应 token、usage、人民币费率版本、人民币预算估算、预算前后余额、限流与错误 | 业务事件追加；同 `(parent_run_id,event_key)` 只保留一个逻辑恢复事项，每事项最多两次有界执行尝试；旧运行失败后不能写工具；AgentRun 不决定资金状态；每次模型调用形成可追溯 usage，预算账本按本地累计上限 ¥100 原子扣减或拒绝，不能以重启清空 |

所有交易实体均带环境和创建／更新时间。环境参与唯一约束，防止模拟数据命中沙箱对象。核心金额使用整数分且非负，费用与报价、实付与退款分别保存。

## 二、事务与任务

确认接口原子保存确认、对应授权与事件；业务执行入口原子保存订单／取消事项与后续任务。创建订单时锁定计划预算、重查授权与暂停范围、写订单占用；退款准入锁定原支付及取消事项，校验原单可退额与本次确认剩余额度并写批次占用。对外请求在提交之后发出。订单和待执行任务在同一事务保存，避免只写订单没写任务。付款确认在同一事务将订单占用转为已支付，重复通知或查单不得重复转入。

执行者领取任务有到期时间与领取版本。旧执行者回写须检查领取版本；重复调用仍由固定业务编号约束。崩溃发生在外部调用之后时，接管者先查询原操作；不能认为本地未保存结果就等于渠道未执行。

### 2.1 事务责任与完成协议

以下为完成协议。2026-09-08 已将模拟业务写入、领取检查和 `completeJob` 合并为同一事务；渠道执行采用准备／外部调用／结果事务，回写再验领取版本。已通过故障注入定向检查，官方实测与完整恢复仍待验证。

| 时点 | 同一短事务内完成 | 事务外行为 |
| --- | --- | --- |
| 操作准入 | 业务归属、授权／暂停／版本、环境检查；订单或批次、占用、固定业务号、操作、所需任务及事件一起提交 | 返回既有操作标识；尚不宣布渠道成功 |
| 领取与发送准备 | 锁任务并生成领取版本；检查操作与环境；保存本次尝试及可能发送的标记 | 提交后调用渠道，避免在持锁事务内等待网络 |
| 应用结果 | 锁对应业务对象和任务；检查领取版本；归并证据；一起更新付款／退款、占用、操作、任务和事件 | 提交后通知页面；若响应丢失，重复请求读取已提交事实 |
| 等待与人工接管 | 保留未知占用；保存 nextRunAt 或唯一人工任务、原因和责任 | 本轮执行结束；不保持数据库锁或模型循环 |

模拟任务没有外部网络步骤，应在一个事务内完成领取版本验证、业务结果和任务／事件更新。渠道任务无法保证网络恰好执行一次；使用固定业务编号、结果查询、唯一约束和状态归并，使重复通信不重复记账。旧 worker 的租约失效后不得直接写业务结果；晚到的有效渠道观察可由当前持有者或受控核验入口按原号重新归并，不能为了拒绝旧执行者而丢失已发生的交易。

多对象写入采用一致锁序：涉及计划预算时先锁计划，再按固定标识顺序锁订单，随后锁取消申请／退款批次，最后检查关联操作及任务；单独领取任务的事务在调用业务前结束。实际修改时核对所有竞争入口是否同序，不新增全局锁。版本检查必须发生在会修改业务事实的事务内。

### 2.2 崩溃窗口与恢复判定

| 中断位置 | 恢复依据 | 禁止行为 |
| --- | --- | --- |
| 准入事务提交前 | 无完整操作即没有受理；按原幂等键重新准入 | 留下孤立订单或占用 |
| 准入已提交、尚未发送 | 读取原操作与任务；确认没有发送风险后执行 | 再建订单或再占用预算 |
| 已标记可能发送、未保存结果 | 原支付／退款业务号查询；不能确定则保持未知 | 把本地无成功结果当作渠道未执行 |
| 结果提交后、响应或事件消费前 | 从已提交快照与事件恢复；消费按事件号去重 | 再次累计金额或将成功改成失败 |
| 领取过期、旧执行者返回 | 当前领取版本控制业务回写；按原号核对晚到事实 | 只检查任务表版本，允许旧执行者先写订单 |

### 2.3 现有表与设计实体的对应

逻辑实体不是逐表完成清单：`MerchantOrder` 对应 `orders`，`PaymentAttempt` 对应 `payment_attempts`，`RefundOperation` 当前主要由 `refund_batches` 与 `operations` 表达，`BusinessOperation / Job` 对应 `operations / jobs`，通知证据由 `payment_notifications` 承载。`AgentRun`、`AgentUsage`、方案关联、交易工具关联、确认事件消费和退款批次／订单人工任务关联已由 006—011 迁移及对应领域服务落地；仍需以第十三、十四节的局部结果和剩余验证边界为准，不把局部通过扩大为完整放行能力。

订单汇总金额与批次明细不是两份可独立修改的账本。批次成功额在同一事务归并至订单；净支出由历史付款减已确认退款计算，原付款不能因退款终态被覆盖。页面快照、Agent 与导出应复用同一金额计算，不分别从状态文本推算。发生汇总和明细不一致时保留原记录并转核对，禁止用人工成功标记抹平差额。

## 三、事件与去重

建议事件类型为 PurchaseConfirmed、OrderCreated、PaymentObserved、PurchasesPaused、ChangeConfirmed、CancellationDecided、RefundObserved、ReconciliationRequired 和 OperationResolved。每项事件包含 eventId、aggregateId、aggregateVersion、occurredAt、receivedAt、correlationId、环境与脱敏负载。

事件投递可能重复与乱序；消费者按事件标识去重，业务对象按合法转换核验。原始通知通过签名与字段检查后关联处理记录，重复通知不能重复记账。补发旧付款事实不允许把已退款业务状态降回仅已付款。

## 四、恢复、保存与删除

启动后扫描非终态操作，按 nextRunAt 恢复核查；会话按 planId 与 runId 重建，不批量重放历史写工具。界面通过业务快照加事件游标恢复，不依赖内存聊天流。

P0 本地测试数据的保留、备份与导出期限以[运行文档](../04-quality/operations.md)为准。只删除明确选择且满足清理条件的测试数据；删除会话不自动删除交易记录，未决操作不得随会话清理。不在 Markdown 中记录真实账号、密钥或完整回执。

### 5.1 事务边界与启用顺序

确认、授权、业务事件和必要的恢复排队记录应在同一短事务保存，避免确认提交后进程退出却没有恢复依据。交易工具同事务保存调用关联、业务结果和操作；提交前失败整体回滚，提交后响应丢失读取原结果。模型推理及等待始终在事务外，领取事务先提交再推理。队列等待不计作模型调用，也不提前为尚未发送的等待项占用模型费用。

当前付款交接是本地签名准备，不等同于已发出渠道请求；实际外部动作仍须遵守发送前持久化、事务外请求和结果核验协议。事件生产者、应用与 worker 已按 009—011 的迁移顺序启用；数据库异常不能被吞掉以绕过恢复记录，否则会失去确认与恢复的原子关系。

### 5.2 一个逻辑恢复事项与有界中断尝试

口径是“同一事件一个逻辑恢复事项，每事项最多两次执行尝试”，不是把每次尝试都当成新的业务事项，也不改变业务幂等。稳定键为 `(parent_run_id,event_key)`，attempts 单独计数，尝试切换不改变队列事项。

进程中断或运行过期时，恢复创建关联子运行并递增 attempts，最多两次；旧 run 保留为 FAILED，旧执行者不能写工具，活跃订单观察转交新尝试。普通模型失败、取消、预算不足不自动触发下一次尝试；是否有新事实和是否仍有未受理动作由服务端在新尝试启动前重新核对。

运行超时不能证明业务未受理。先看原订单与操作，再决定是否还有剩余动作；任何尝试都不能绕过固定业务号、工具幂等或确认范围。

### 5.3 订阅建立时读取当前事实

| 窗口 | 风险 | 收口方向 |
| --- | --- | --- |
| 提交变更时同步产生商户决定，随后才建立订阅 | 事件已经发生，可能没有下一事件可供结束等待 | 提交变更前先建立观察并保存 `last_fact`；提交后读取最新事实，捕获同步决定 |
| 重复工具返回已经付款、关闭或完成善后的原对象 | 新订阅挂到终态对象，长期等待不存在的消息 | 建立订阅前判断该用途是否已结束，直接返回原事实 |
| 交易完成，但解释运行失败、取消或进程退出 | 摘要失败被误当交易失败，或者页面仍持续等待 | 分别展示交易和解释状态；订阅依据业务事实结束，结构化页面始终可读 |

购买观察与善后观察不能共用粗糙的终态判断。付款完成可结束购买观察；退款分批、延迟人工和拒绝各有后续责任。商户自动批准不等于退款执行，原取消申请操作成功也不代表退款成功。

### 5.4 有意义的新事实与锁序

同事件号重复投递复用消费记录；不同事件号携带同一已知事实时，也不应仅因查询时间或查询操作号变化调用模型。观察保存 `last_fact`，事实键包括订单状态、付款状态、已核验退款累计额、取消决定、退款批次和人工责任／操作状态，排除时间戳、查询号和秘密字段。观察创建时识别付款完成、关单、取消拒绝、退款终态等用途终态并关闭观察；还覆盖分批退款、拒绝／延迟、未知恢复和人工责任变化，不只比较付款状态。

Agent 写工具先锁计划，再锁运行和业务对象；确认与直接执行接口同样先锁计划再锁方案。幂等锁、队列领取和取消均在同一业务服务边界内复核，局部行为结果与未验证范围见第十三节。

取消推理依据具体运行及关联恢复事项生效：取消目标及后代仍处于待运行／等待状态的运行，关闭该分支队列和观察，订单与商户责任继续存在。不能仅查看最早父运行的状态而忽略当前子运行的取消；授权失效停止新增对应受托动作，既有事实读取与商户自身职责继续按领域规则处理。
