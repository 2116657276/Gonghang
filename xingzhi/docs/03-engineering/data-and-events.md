## 一、术语和事实边界

`plans` 是已有的消费计划，表示用户想购买的一组计划项，并承担购买授权、订单预算和变更善后。`cashflow_plans` 是拟新增的 30 天资金规划，表示在一个主资金账户的余额基准上，对收入、必要支出、还款、保留金额和消费计划进行预测。两者不能合并：前者约束“是否允许执行已确认购买”，后者解释“这次消费会怎样影响近期资金”。

财务来源的总集合为以下三类，但每张表只允许使用与其事实性质相符的子集；订单执行事实与人工说明仍保留在原交易表，不作为新财务 source 枚举：

| 来源 | 含义 | 能否直接改变银行资金事实 |
| --- | --- | --- |
| `bank_api` | 银行授权接口返回的账户快照、流水或还款信息 | 只能由受信适配器写入，当前 Demo 未接入 |
| `demo` | 本地固定测试账户和测试数据 | 仅用于演示，不能写成真实银行结果 |
| `user_input` | 用户补充的预计收入、必要支出或近期应还 | 只用于规划行或用户补充的还款安排，不能伪装成账户、快照或已发生流水 |

任何金额都使用整数分，时间保存 UTC；规划同时保存展示用时区。账户快照必须同时保留提供方事实时间 `asOf` 和本地收到时间 `capturedAt`。余额的基准是 `asOf`，不能用页面读取时间或最后一次 API 调用时间冒充余额时点。

| 数据对象 | 允许来源 |
| --- | --- |
| 账户目录 | `bank_api`、`demo` |
| 账户快照 | `bank_api`、`demo` |
| 已发生流水 | `bank_api`、`demo` |
| 当期账单／还款安排 | `bank_api`、`demo`、`user_input` |
| 用户预计收入和必要支出规划行 | `user_input` |

## 二、当前可以直接复用的表

当前代码树存在迁移 001—029。M1 没有删除或重写既有迁移，也没有清空历史沙箱订单。001—015 提供早期资金规划、计划关联和目录扩展，016—026 增加消费者月度预算、报价／意图、资金事件约束、需求草稿和必要支出确认；027 支持新预算周期的 operation/refund/manual task 范围，028 支持独立消费者 Agent 运行范围，029 增加分类展示覆盖、Agent 产物、订单善后预览和隔离场景登记。现有表与新方向的职责如下。

| 现有表 | 当前职责 | 新方向复用方式 |
| --- | --- | --- |
| `users`、`sessions` | 角色、密码摘要、会话有效期和撤销 | 继续作为身份来源；账户、流水和规划均按 `owner_id` 隔离，不在新表保存密码 |
| `catalog_items` | 商户登记商品、价格、商品类型、取消规则及三种模拟结果 | 继续作为银行平台登记目录；M1 只增加筛选和展示所需属性，不另建推荐数据库 |
| `plans`、`plan_items` | 消费计划、计划项快照、计划版本、暂停范围和计划级购买上限 | 继续作为消费执行计划；选中的目录商品仍复制为计划项快照 |
| `proposals`、`confirmations`、`authorizations` | 购买／变更草稿、用户确认、购买／善后／查询授权 | 保留原确认先于执行的边界；资金规划不能替代用户确认或扩大授权 |
| `orders`、`payment_attempts` | 订单、支付状态、支付业务号、环境、渠道及模拟结果 | 作为消费执行事实；订单金额只记一次，模拟支付仍标明 `simulation` |
| `cancellation_requests`、`refund_batches` | 取消决定、费用、退款总额和分批退款事实 | 支持计划变化后的取消与退款；预计退款先进入规划估算，批次成功后才形成已确认资金变化 |
| `operations`、`jobs` | 异步业务操作、租约、任务恢复和操作结果 | 保留固定业务号、未知状态、显式复核和 worker 恢复；新财务读取不创建交易操作 |
| `idempotency_records` | 按主体、路由和幂等键保存请求及响应 | 新增写接口继续复用，重复同参数返回原结果，参数变化返回冲突 |
| `events`、`review_scopes` | 计划事件游标及审核范围 | 交易和计划变化继续写事件；财务来源通过快照、流水和规划行保存，不建设独立事件总线 |
| `payment_notifications` | 支付宝沙箱通知原文、验签结果和去重 | 继续与订单环境隔离，不能被账户流水的 Demo 记录替代 |
| `manual_tasks`、`evidence_exports` | 商户人工责任和脱敏证据导出 | 退款未决仍由商户负责；审核者只看被分配计划的脱敏规划摘要 |
| `model_budget`、`model_usage`、`agent_runs` 及 009—011 的 Agent 关联表 | 模型费用、Pi 运行、工具调用、运行恢复和订单观察 | Agent 读取新规划快照，仍不能确认授权、修改财务事实或取得银行密钥 |

现有交易表中的关键字段必须保留：`orders.environment`／`provider`、`payment_attempts.business_number`、`operations.state`／`result`、确认和授权关联、`orders.reserved_minor`、`orders.refunded_minor`，以及 012 中付款／关单／退款的独立模拟结果。新规划不复制一份订单金额账本。

## 三、M1 最小迁移设计

以下保留迁移 013—015 的早期 30 日规划数据结构，并补充 016—028 已落地的消费者月度预算、报价、资金事件、需求草稿、任务恢复和 Agent 运行约束。历史迁移保持不动；表结构只能说明数据边界，不能单独证明真实银行、支付宝沙箱或前端已经接入。

### 3.1 `finance_accounts`：已授权账户目录

该表只记录用户允许微应用使用的账户引用和展示信息，不保存银行登录密码、支付密码、完整卡号、私钥或沙箱账号。

| 字段 | 约束与用途 |
| --- | --- |
| `id` | UUID 主键，内部引用 |
| `owner_id` | 外键到 `users`；服务端归属判断唯一依据 |
| `provider` | `icbc` 或 `demo`；未来接入其他提供方需单独评估 |
| `account_type` | `debit`、`credit`、`loan`；分期作为还款安排，可关联贷款或信用账户 |
| `provider_account_ref` | 提供方的非敏感不透明引用或 Demo 固定标识；不存完整账号，不为测试 ID 额外计算摘要 |
| `masked_identifier`、`display_name`、`currency` | 仅供用户确认账户范围，货币首版固定 `CNY` |
| `source` | `bank_api` 或 `demo`，标识账户来自银行适配器或固定测试配置；普通用户不能自行登记账户 |
| `status` | `linked` 或 `revoked`；撤销后不能进入新规划 |
| `authorized_at`、`revoked_at`、`created_at`、`updated_at` | 授权和资料时间 |

同一用户可以有多个已登记账户，但 M1 的一个 `cashflow_plan` 只选择一个 `primary_account_id`。选择主账户不是取得全部资产的承诺；未登记的现金、其他银行和未授权负债要由用户补充并标注来源。

### 3.2 `finance_account_snapshots`：余额和负债快照

账户余额会变化，不能只在 `finance_accounts` 上覆盖一个数。快照表保留可回溯的基准。

| 字段 | 约束与用途 |
| --- | --- |
| `id`、`account_id` | UUID 主键及账户外键 |
| `available_balance_minor` | 借记账户的可用余额；信用和贷款账户可为空 |
| `current_balance_minor` | 提供方报告的当前余额，可为空 |
| `outstanding_minor` | 信用卡／贷款当前未偿金额，可为空 |
| `credit_limit_minor` | 信用账户额度，只作展示和条件说明，不能加入可用资金 |
| `as_of` | 提供方余额事实时间；规划余额基准必须取此字段 |
| `covered_through_at`、`covered_through_ref` | 快照已经覆盖的流水截止时间或提供方游标；用于区分快照内流水与需要增量补入的流水 |
| `captured_at` | 服务端收到并保存的时间 |
| `fact_status` | `observed`、`estimated` 或 `unknown` |
| `source`、`provider_snapshot_ref` | 来源和去重引用；不保存原始凭据 |

账户类型与数值的对应关系由服务端校验：可执行资金基准只能来自仍已授权借记账户的 observed 快照，且有可用余额和覆盖截止标记；不完整的借记快照仍可保存，不能作为可执行基准；信用账户可有未偿金额和额度；贷款账户主要提供未偿金额。缺失值保持 `null`，不以 0 代替未知。

读取规划时选择作为基准的最新有效快照，按 `as_of` 和提供方覆盖游标判断；晚到的旧快照不能覆盖较新的事实。快照已覆盖到 `covered_through_at` 的流水只用于展示和消费统计，不再从余额基线重复加减；只有截止点之后且尚未被新快照覆盖的已确认流水，才按 `dedupe_key` 增量计入一次。`captured_at` 只用于说明延迟，不参与余额计算。没有覆盖截止标记的快照不能安全地与增量流水相加，应显示为基准不完整并等待核对。

### 3.3 `finance_ledger_entries`：轻量流水

该表服务于“看清已经发生什么”，不是建设银行核心账务系统。每条记录保存一个由银行适配器、固定种子或受控 Demo 服务提供的账户收支事实，不保存用户预计事项。

| 字段 | 约束与用途 |
| --- | --- |
| `id`、`owner_id`、`account_id` | 归属与账户外键 |
| `source`、`source_ref` | 仅允许 `bank_api` 或 `demo`；来源引用由受信适配器、固定种子或受控 Demo 服务生成并校验 |
| `direction`、`amount_minor` | `inflow`／`outflow`，金额为正整数分 |
| `occurred_at`、`posted_at` | 发生时间和入账时间；未入账流水允许 `posted_at` 为空 |
| `status` | `pending`、`posted`、`reversed` |
| `category`、`merchant_name`、`note` | 轻量分类和展示文本；分类可被用户纠正 |
| `order_id` | 可选地关联行止订单；同订单不再另造一条消费事实 |
| `dedupe_key` | 必填；同账户、来源和外部引用唯一 |
| `created_at`、`updated_at` | 本地保存时间 |

银行流水和行止订单是两种不同来源。首版没有普通用户或 Agent 新增已入账流水的入口；用户报告“新增 400 元必要支出”时，只写入 `cashflow_plan_items` 并使用 `source=user_input`。模拟支付只更新订单及操作，不自动生成一条“银行已扣款”流水。固定种子或受控 Demo 联动可以产生 `source=demo` 的测试流水；支付或退款联动必须依据已经核验的测试订单号生成稳定去重键，关联原订单及对应规划安排，并停止重复扣除原安排。只有银行适配器可以写入 `source=bank_api` 的流水。

支付宝沙箱回执仍是 `environment=sandbox` 的渠道事实，不属于财务 source。演示测试账户扣款或退款到账时，应另外生成明确标注为 `source=demo` 的流水，不能改写成 `bank_api`。真实银行流水到达后，服务端通过 `order_id` 或受控匹配与订单关联，展示层按关联键只计一次。

### 3.4 `finance_obligations`：账单、贷款和分期的近期应还安排

规划需要的是未来某个日期要从还款账户流出的金额，不是把全部贷款本金或信用额度塞进余额。每一笔当期账单或分期应还可以保存为一行。

| 字段 | 约束与用途 |
| --- | --- |
| `id`、`owner_id` | 归属 |
| `liability_account_id` | 外键到信用卡或贷款账户，表示欠款来源 |
| `repayment_account_id` | 外键到实际还款账户，首版通常为主借记账户 |
| `obligation_type` | `credit_bill`、`loan_repayment`、`installment` |
| `label`、`period_label`、`sequence_no`、`sequence_total` | 展示账期或分期序号，可为空 |
| `due_on`、`amount_due_minor`、`outstanding_minor` | 到期日、当期应还和仍未还金额，均为非负整数分 |
| `status` | `upcoming`、`paid`、`overdue`、`unknown`、`cancelled` |
| `settled_ledger_entry_id` | 关联已入账还款流水的内部引用，可为空 |
| `included_in_obligation_id` | 可选地指向已包含本期金额的信用卡账单；被账单覆盖的分期子项只展示，不再单独扣除 |
| `source`、`source_ref`、`created_at`、`updated_at` | 来源、去重和时间 |

同一来源和账期只保留一个去重键。若还款流水已经关联到该安排，规划只保留已结清状态，不再把该流水和未偿应还额各扣一次。信用卡消费流水可以用于消费分类，但信用卡当期账单只在还款日作为主账户未来现金流扣除；贷款只扣观察期内到期的当期还款，不扣剩余本金。若提供方说明分期金额已经包含在某一账单中，分期行填写 `included_in_obligation_id`，只在账单行计入现金流。

### 3.5 `cashflow_plans`：一个主账户的一份有效 30 天规划

该表保存规划的账户范围和版本，采用快照基准，不把每次读取结果覆盖成不可解释的余额。

| 字段 | 约束与用途 |
| --- | --- |
| `id`、`owner_id` | UUID 及消费者归属 |
| `primary_account_id` | 外键到 `finance_accounts`；必须属于用户且状态为 `linked` |
| `basis_snapshot_id` | 外键到 `finance_account_snapshots`；记录本次规划采用的余额基准 |
| `horizon_start`、`horizon_end` | 首版由服务端生成 30 天窗口，结束日不得早于开始日 |
| `timezone` | 规划日期和展示时区，首版默认 `Asia/Shanghai`；数据库瞬时时间仍为带时区的 UTC 时间戳 |
| `reserve_target_minor` | 用户设定的保留金额，不由模型擅自改变 |
| `status`、`version` | `active` 或 `archived`；更新使用版本检查 |
| `created_at`、`updated_at` | 时间 |

M1 对同一用户选定的主账户只允许一份 `active` 规划；重新读取或修改通过同一规划版本更新，旧规划归档后不再参与预算。同一主账户下的多个消费计划共享这份规划和版本，不能各自复制一份余额视角。用户切换主账户时才建立另一账户的规划视角，不建设滚动预测引擎。

### 3.6 `cashflow_plan_items`：用户补充的规划行

规划行是预测或解释输入，不是资金占用账本。它保存用户手动补充的预计收入、必要支出和自定义每日消费项目，不复制流水、还款安排、订单或退款批次，也不新建独立目标系统。生活目标仍由现有 `plans`／`plan_items` 表达。

| 字段 | 约束与用途 |
| --- | --- |
| `id`、`owner_id`、`cashflow_plan_id` | 规划归属；资金规划与行属于同一消费者 |
| `line_type` | `income`、`essential_expense` 或 `planned_spend`；后者表示用户自定义的每日消费 |
| `label`、`category_code`、`amount_minor`、`due_on` | 名称、类别、用户预计金额（正整数分）和预计日期；不是商户成交价 |
| `source` | 首版为 `user_input`；禁止客户端提交外部订单、流水或还款标识 |
| `fact_status` | `estimated`、`confirmed` 或 `cancelled`；流水和渠道事实不写入此表 |
| `related_plan_id`、`selected_plan_item_id` | 可选关联消费目标及用户后来选中的登记商品快照；未选商家时可保持为空 |
| `settled_ledger_entry_id` | 可选关联已兑现的账户流水，由受控服务核对归属后写入 |
| `created_at`、`updated_at` | 时间 |

同一用户输入在同一规划中只能有一条有效规划行，后续写接口须复用幂等和版本检查。自定义项目未匹配商家时按用户估价参加规划，但不能建单；关联 `selected_plan_item_id` 后改按 `plan_items.price_minor` 的真实商品快照计算，不能将估价和报价相加。形成已兑现流水关联后，原安排不再重复扣除，原行及估价仍保留供复盘；刷新规划不会生成流水副本。

现有 `plans` 表已增加可空的 `cashflow_plan_id` 外键和 `cashflow_state`。旧计划标记为 `legacy` 并保持 `cashflow_plan_id = NULL`；新用户从空状态创建的目标草稿须显式写 `draft`，暂时没有资金规划时只能编辑目标和输入，后续服务必须阻止确认购买或建单。完成账户选择后由服务端把该草稿关联到 active `cashflow_plan` 并改为 `active`。一个资金规划可以被同一主账户下的多个消费计划共享。`plans.target_budget_minor` 是可空的用户目标预算，`purchase_limit_minor` 仍为购买授权上限；`plan_items.required`、`adjustable` 和 `planned_on` 分别记录必要性、可调整性和项目日期。上述字段不复制订单金额，也不形成第二个支付授权。

### 3.7 目标预算与草稿准入

新产品不再另建 goal、目标或长期资金池表。现有 `plans` 继续表达一项生活目标：`purpose` 作为标题，`target_budget_minor` 作为可空的目标预算，`purchase_limit_minor` 保留为购买授权上限，另增加可选的 `target_date`；`version` 继续作为并发确认版本。现有 `plan_items` 继续表达已选消费，新增 `required`（必须保留）、`adjustable`（允许调整）和 `planned_on`（项目日期）；前两项分别默认 `false` 和 `true`，兼容历史计划。

空状态自然语言入口可以先创建 `cashflow_state = 'draft'`、`cashflow_plan_id = NULL` 的目标草稿。Agent 只能保存用户当前消息中明确表达的目标名称、日期、初始目标预算和需求条件，不能推断缺失金额或改变保留目标；这种非执行草稿不需要逐字段二次确认。没有账户规划时不能生成购买授权、建单或付款交接。选择主账户后，服务端在版本检查下关联 active `cashflow_plan`；计划进入 active 后，目标预算、必须项、可调整项和商品集合的变化均由用户通过结构化界面确认，Agent 只能提出建议。历史 `cashflow_state = 'legacy'` 的 NULL 计划不可改绑新规划，原已受理订单和善后仍按原授权完成。

## 四、金额、时间和去重规则

### 4.1 规划计算

规划基准是选定主账户快照 `available_balance_minor` 在 `asOf` 时的可用余额；快照 `covered_through_at` 之前的流水已包含在基线内。对窗口内每一天按日期计算：

```text
确认余额轨迹 = 快照基准可用余额
            + 覆盖截止点之后、尚未纳入快照的已确认收入
            - 覆盖截止点之后、尚未纳入快照的已确认支出

规划基础情景 = 确认余额轨迹
            - 日期内仍未兑现的必要支出和当期还款
            - 未付款或已付款但尚未反映到账户的已承诺消费安排
```

实际实现时将“预计收入”和“待退款”作为独立的待定栏，不进入“当前可安排金额”。预计收入只有在后续形成 `posted` 流水并被新快照覆盖或按唯一来源增量接入后，才进入确认余额轨迹；用户可以主动查看包含预计收入的条件情景，但必须标出“收入未到账”。退款批次即使渠道状态成功，也只有关联主账户的 `posted` 入账流水后才进入确认余额轨迹。页面至少展示基准时间、快照覆盖截止点、已知资金、预计收入、待还款、保留目标、已承诺消费和最低预计余额。发生新快照覆盖时，重建基线并只接入覆盖点之后的增量流水，不能把旧基线和新全量流水相加。

`reserve_target_minor` 不是自动冻结金额，也不能改变银行账户余额；系统将它从可安排金额中扣除用于判断。资金不足时只给出降价、延后、停止或调整计划等选择，不自动引导贷款或分期。

### 4.2 消费、现金流和订单只计一次

订单、支付尝试、银行流水和规划行具有不同用途：订单说明行止安排，支付说明渠道结果，流水说明账户事实，规划行说明未来安排。它们通过 `order_id`、来源引用和规划关联连接，不能把每张表的金额简单相加。

1. 行止订单成功付款后，订单是消费执行事实。模拟环境不代表真实账户扣款；真实银行流水到达后与订单关联，消费统计只保留一个消费事实。已确认付款已经反映在余额快照或关联流水中的订单，规划只保留尚未付款的未来安排，不能再次扣订单全额；没有账户关联的沙箱已付款订单不自动扣主账户余额，但保留为“待账户核对的已付款安排”，继续影响规划空间，避免付款成功反而释放可花额度。
2. `orders.reserved_minor` 是现有购买授权账本的待决占用。订单和候选金额由关联消费计划动态派生，不在 `cashflow_plan_items` 再增加一份预测或硬占用。
3. 订单退款在 `refund_batches` 中按批次保存。待退款和渠道已成功退款都只展示为待定情景，不能直接增加主账户可用资金；只有关联主账户、状态为 `posted` 的银行／Demo 流水，才增加确认现金流。
4. 同一订单的已付款和后续退款不覆盖原付款记录。没有银行流水关联的沙箱订单保持独立渠道事实，不能凭模型猜测已经改变主账户余额；Demo 主链可在已核验支付或退款事件后，由受控业务服务生成一次 source=demo 的关联流水；以订单或退款批次业务引用去重。同一事务更新关联后，用该流水替代原待核对消费安排，而非叠加扣减。渠道未明时不生成成功流水，真实 bank_api 结果绝不由此服务伪造。净消费可以展示为累计已付减累计已确认退款，但购买授权空间仍按现有规则累计，不因退款自动恢复。

### 4.3 账单、信用额度和分期不重复

信用额度不是可花余额，不能加入可安排资金。信用卡消费流水可以出现在消费分类中，当期账单在其到期日从还款账户扣除；若信用卡消费已进入该账单，就不能再把消费金额作为主借记账户的现金流扣一次。账单覆盖的分期行通过 `included_in_obligation_id` 记录覆盖关系，同一账单的子项只展示，不再单独加总。实际还款流水关联到 `finance_obligations` 后，将该期应还标为已结清。

贷款和分期只在窗口内扣当期 `outstanding_minor`；剩余本金保留为负债背景。未知还款状态不当作已支付，继续显示待核对。一个来源相同、账期相同的账单只能有一条有效安排。

### 4.4 跨消费计划的资金约束

同一主账户的一个 active `cashflow_plan` 可以关联多个现有 `plans`，所有关联计划读取同一规划版本。创建订单或确认新消费时，服务端在同一事务中锁定 active 资金规划，汇总关联消费计划中已经支付、待付／未知订单和当前拟执行金额，再分别检查：

- 原有 `plans.purchase_limit_minor`、购买授权和暂停范围；
- 主账户基准下扣除必要支出与保留目标后的近期可安排金额；
- 同一 active 规划下其他消费计划已经承诺的金额。

通过后才进入现有的订单预算占用流程。规划本身不冻结账户，不以预计收入或待退款覆盖当前购买授权。M1 上线后，`cashflow_state = 'legacy'` 且 `cashflow_plan_id IS NULL` 的旧计划只允许完成迁移前已经受理的订单、关单、退款和核验；`cashflow_state = 'draft'` 的新空状态计划可以编辑目标和输入，但在关联 active 资金规划前不能确认购买、建单或取得付款交接。所有新确认和建单都必须经过 active 资金规划的现金流准入，旧路径不得绕过。M1 不建设跨银行总账、自动扣款或全账户净资产模型。

## 五、事件、恢复和删除

已有 `events` 继续记录计划、确认、订单、暂停、变更、取消、退款和核验事件；事件按 `plan_id` 游标读取，业务结果仍以订单、支付尝试、退款批次和操作表为准。账户快照、流水和规划行通过自身的来源、版本和时间保存，不为每次只读刷新制造事件。

当资金规划与某个消费计划关联时，规划创建、用户补充、规划更新和规划归档可以写入现有计划事件的脱敏 `data`。没有消费计划的账户资料变化只更新财务表，不伪造一个订单事件。候选比较和可行性卡只读派生，不单独建表；一次真正选定的可执行草稿仍由现有 `proposals` 保存，未选候选不进入执行表。决策摘要可在 `proposals` 快照、`events` 和 `evidence_exports` 中保存事实版本、规则结果、资金影响日期、用户确认和执行结果，不保存模型思维链。M1 不新增独立消息总线。

进程恢复仍只恢复已受理的交易操作和 Agent 运行；读取账户或重新计算规划不会重放支付、退款或模型写工具。恢复时以订单、操作、支付和退款的已提交事实为准，不能用预计规划行覆盖渠道事实。

账户撤回通过 `POST /api/finance/accounts/:id/revocations` 把本人账户从 `linked` 改为 `revoked` 并记录时间；同一动作按幂等键复用结果，账户已经撤回时不重复推进版本。撤回不删除历史订单、流水和已确认退款；禁止刷新新账户事实、创建或重新关联资金规划，以及既有规划上的新报价、商品选定后的购买预览、购买确认、建单和首次付款交接。已有规划保留当时采用的快照、来源和未决事项，并显示为不可继续执行；已受理交易的关单、取消、退款、查询和恢复仍按原授权完成。测试数据清理沿用运行文档的条件，历史沙箱事实和审计证据不因重写 Demo 种子而抹除。

| `M1-CF-MAIN` | 一个借记主账户余额 ¥2,600，余额基准含 `asOf`；一个信用账户当期应还 ¥120；一个分期当期应还 ¥80；必要生活支出合计 ¥1,300；保留目标 ¥500；另有 ¥1,200 预计收入但尚未到账；标准主链只使用这一份消费计划 | 演示账户范围、账目、还款和“当前能安排多少” |
| `M1-CF-CROSS-PLAN` | 独立于标准主链的变体：同一主账户规划关联两个消费计划，分别保留不同目标和优先级，使用专门的余额与支出数据 | 验证多个 `plans` 共享同一规划版本与账户约束；不把它并入标准主链的金额结论 |
| `M1-CF-CHANGE` | 主流程先确认约 ¥480 的周末消费，随后用户补充一笔 ¥400 必要支出 | 演示保留、替换、停止、关单／退款和规划重新计算；新增支出来源为 `user_input` |
| `M1-CF-REFUND` | 一个已付款且可退款订单、一个渠道退款批次，以及退款到账前后的独立账户流水对照 | 区分预计退款、渠道已成功退款、银行已入账退款和订单原始付款，不把待退款计入当前余额 |
| `M1-CATALOG` | 至少三项同类餐饮、三项室内活动，价格、位置、取消规则和 `purchase_mode` 有差异，其中至少一项仅展示不可代下单 | 验证多候选筛选、推荐解释和登记商品边界 |

金额只是可复现的演示输入，不是金融建议。主流程应以固定时钟或明确的 `asOf` 运行，避免因系统日期变化改变预算结果。新夹具与旧回归夹具可以共存；不为迁移方便而重置数据库，也不删除已经产生的沙箱支付、退款和关单证据。

## 八、实施时必须同时落实的约束

账户、流水、还款和资金规划按 owner_id 关联；规划基准快照必须属于所选主账户。一个主账户只能有一份 active 规划，关联消费计划不能跨用户。旧计划标记 legacy 并保持无资金关联；新目标显式 draft，关联有效规划后才进入 active。上述归属及关联完整性优先使用外键和必要唯一约束；账户授权是否有效、快照是否足以执行由共用业务服务在交易入口核验。

财务来源总集合为 demo、bank_api、user_input，交易环境保持 simulation、sandbox，不增加同名财务来源。账户、快照和已发生流水只允许 demo 或 bank_api；还款安排可包含 user_input，用户规划行仅使用 user_input。普通用户首版只可纠正流水分类；未来收入及临时支出保存为用户规划安排，不伪装成银行已入账。测试样本与交易关联保留 demo 来源，沙箱渠道事实不能改写为 bank_api。

目标预算 target_budget_minor 允许 null，购买授权 purchase_limit_minor 保持独立。候选写入计划项的接口、目录 ID 与计划项 ID、展示商品限制和快照字段见接口契约；目录类型、共享类型、报价和执行门禁在同一小阶段落地后才加载可交易餐饮目录。
