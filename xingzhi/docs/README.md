行止定位为面向智能体消费的计划变更与交易善后协同服务。第一版必须从用户选购开始，在同一组订单上形成付款、计划变更、部分保留、关单、取消申请、商户退款与结果核验。官方沙箱为当前验证基线，纯模拟不能代替交易验收；真实资金另审。

后续开发直接从[开发计划](03-engineering/development-plan.md)进入：先完成后端并统一验收，再统一重构前端，最后综合交付。当前前端冻结；小阶段连续实施，不逐项测试、构建或审批。全部 P0 通过才算首次完整交付。

本地安装、启动与测试账号见[本地运行说明](../README.md)。实际检查结果和历史适用范围统一见[验证记录](04-quality/verification.md)，不以自动测试数量代替 36 项 P0 放行。

本文档体系采用常见产品工程规范：单一事实来源、稳定编号、架构决策、接口契约、需求追踪、测试证据与交付门槛。它不是任何企业内部模板，也不构成合规认证。

## 三、开始分阶段开发

常规开发按开发计划继续，不要求用户逐阶段重复指定或批准；依赖动作前核实尚未具备的条件，在大阶段集中验收。沙箱账号／设备及支付权限在 S2 前核实；通知地址仅在选择异步通知路径时核实；继续实施 S4 时复用已核对的 Pi、DeepSeek 密钥和人民币预算配置，并在真实调用前继续关注 `deepseek-flash` 的官方价格和服务状态。不能把未知条件填成已通过。按已有规则解决常规实现问题；只有影响结果的缺失信息、范围变更或新增外部授权才询问，继续不受影响的工作。支付联调与真实资金仍须分别取得相应授权。
