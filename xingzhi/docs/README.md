行止定位为面向智能体消费的计划变更与交易善后协同服务。第一版必须从用户选购开始，在同一组订单上形成付款、计划变更、部分保留、关单、取消申请、商户退款与结果核验。官方沙箱为当前验证基线，纯模拟不能代替交易验收；真实资金另审。

后续开发直接从[行止分阶段开发计划](03-engineering/development-plan.md)进入。首个完成的 MVP／Demo 包含全部 P0 基础功能，S1—S4 是中间里程碑，S5 通过才算首次完整交付；之后逐步深化体验和稳定性。

本地安装、启动、测试账号和 S1 范围见[行止 S1 本地运行说明](../README.md)。其中模拟结果只验证内部业务流程，不能代替官方沙箱交易证据。2026-09-08 的环境分派、任务完成事务及渠道复核记录，以及 2026-09-10 的 429 退避记录，分别见[开发计划](03-engineering/development-plan.md)和[验证记录](04-quality/verification.md)。此前 36 项是 429 切片的自动检查数量；截至 2026-09-11，当前工作区定向测试 45 项全部通过，但仍不等同于完整官方验收。

本文档体系采用常见产品工程规范：单一事实来源、稳定编号、架构决策、接口契约、需求追踪、测试证据与交付门槛。它不是任何企业内部模板，也不构成合规认证。

## 三、开始分阶段开发

用户指定开发阶段后，按开发计划核实 S0 中该阶段的前置条件，再完成阶段任务和定向验收。沙箱账号／设备及支付权限在 S2 前核实；通知地址仅在选择异步通知路径时核实；继续实施 S4 时复用已核对的 Pi、DeepSeek 密钥和人民币预算配置。不能把未知条件填成已通过。开发时发现新的实质性冲突或拿不准的问题，须中断并询问用户。支付联调与真实资金仍须分别取得相应授权。
