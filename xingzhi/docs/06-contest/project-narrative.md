## 一、项目概述

行止是一款拟嵌入银行 App 的青年消费规划微应用。它把轻量记账、近期资金规划、银行平台已登记商品的推荐选购，以及计划改变后的调整连接起来，帮助用户在看清近期资金安排的前提下完成消费，并在收入、支出或个人计划变化后及时处理。

用户可以先说生活目标、日期、消费上限、必须保留项和可调整项；即使尚未选择账户，行止也只能保存需求草稿，不能输出已经验证可行的资金结论，不能创建订单或发起交易。用户选择一个主借记账户后，才在明确授权和数据可见范围内读取余额与收支，另外关联信用卡账单、贷款或分期的当期还款安排。用户也可以补充平台暂时无法读取的必要支出、预计收入和保留金额。行止先整理账目并计算未来 30 天的资金影响，再从银行平台预先登记的商品或服务中提供候选，说明价格、适用条件和对计划的影响。用户确认后，系统才创建订单并进入支付流程。计划发生变化时，系统重新计算影响，提出保留、替换、延后或取消方案，并按已有授权处理相应订单，直到结果可核验。

行止的核心不是把四个常见功能并排堆在一起，而是让四类信息形成一条可解释的反馈链：记账提供已经发生的事实，规划说明未来 30 天的约束，商品选择把规划落实为行动，变化调整把新的生活情况反馈回订单和资金安排。

## 二、目标用户与核心问题

首批用户定位为正在实习或初入职场、开始独立承担生活支出的青年。他们可能有固定房租、通勤和生活费，也可能有信用卡账单或分期还款，同时希望安排聚餐、短途活动或其他个人消费。

这类用户遇到的不是“完全不知道自己有多少钱”，而是余额、未来支出和当前消费之间缺少连接：

1. 当前余额不能直接说明哪些钱已经有用途。房租、还款、生活费和用户希望保留的应急金额，可能分布在不同记录里。
2. 做完预算后，用户仍要自己比较商品价格、适用条件和取消成本，预算往往停留在消费之前。
3. 临时出现必要支出、收入延后或个人计划改变时，用户不知道该保留哪一项、取消哪一项，也不清楚退款何时能够形成可用资金。

这些判断属于需要通过访谈和任务观察验证的需求假设。项目不把“青年”当成同一种人，也不预先宣称能够改善所有人的财务状况。

## 三、产品定位与银行价值

项目定位为：

**依托银行场景，贯通收支事实、近期规划和消费执行的青年 AI 助手。**

银行在产品中承担的是可信的账户与支付服务入口，以及已登记商品、服务和权益的承载平台。行止根据用户授权读取主账户可见信息，结合用户主动补充的数据，帮助用户理解消费影响；它不把选择一张卡表述成掌握用户全部资产、贷款或外部平台账单，也不把测试环境中的商户目录表述成已经接入工行真实商品生态。

对于银行，项目要验证的价值假设是：如果消费决策能够结合账户收支、近期还款和银行平台内的商品资源，用户是否更容易完成合理的消费安排，并在计划变化时继续使用银行的服务入口。这个价值需要以用户完成任务、理解金额和愿意继续使用等证据验证，不能直接写成已经提升活跃度、留存或存款。

## 四、产品主线

行止围绕一个近期消费计划工作，主线顺序如下：

1. 用户先说生活目标、日期、消费上限、必须保留项和可调整项；尚未选账户时只建立需求草稿，不输出已验证可行结论，也不创建交易。
2. 用户选择主借记账户，查看当前余额、收支记录和数据更新时间，并确认行止能够看到的范围；再补充或确认未来 30 天的必要支出、当期账单／还款、预计收入和希望保留的金额。
3. 系统把已经发生的消费统计与未来现金流安排分开呈现，先生成可行性卡，说明当前约束、影响日期、缺口和需要补充的信息，再决定是否进入商品检索。
4. 在资金信息足够后，用户用自然语言提出或确认需求；行止从银行平台已登记的目录中检索候选，比较价格、条件、适配度和取消成本。
5. 用户确认具体商品、金额、订单范围和购买授权后，系统创建订单并进入模拟支付；录制 Demo 时，在同一运行中将主线切换为支付宝官方沙箱，连续完成付款、变化确认、原单取消退款与查询。
6. 用户更新新增必要支出、工资延后等变化，或已接入的账户事实发生变化后，行止按日期重新计算同一计划影响，按需生成待确认建议，不常驻模型，也不自动交易。
7. 用户再次确认调整方案，系统按订单当前状态执行未付款关单、取消申请或退款，并把已确认事实、待核对事项和预计变化返回规划视图。

每一步都保留来源与状态。预计收入和预计退款可以作为情景信息展示，但在实际到账并形成可核验账户事实前不计入当前可用资金；信用额度始终不属于自有现金，也不计入可规划空间。同一运行中的支付宝沙箱退款确认成功，只证明原单的渠道退款结果，不等于主借记账户余额已经增加。首版使用需求草稿和月度预算项目，不建立独立的长期目标系统。

可行性卡的结论只描述当前信息下的条件，不使用“安全保证”等绝对表述：

| 条件结论 | 说明 |
| --- | --- |
| 符合当前约束 | 在已知余额、必要安排、保留金额、日期和商品条件下可以继续进入确认 |
| 需调整 | 当前金额、日期或项目范围不满足约束，需要替换、缩减或调整计划 |
| 依赖预计收入或退款 | 只有相关资金按期形成账户事实后才成立，当前不能当作可用余额 |
| 信息不足 | 账户、账目、日期、商品规则或用户意图缺少关键条件，需要补充后再判断 |

卡片必须同时给出影响日期、当前余量或缺口、项目预算拆分、必须保留项、可调整项和简短解释。结论只支持下一步决策，不代替用户确认，也不代表银行对未来资金作保证。

## 五、账户、记账与规划边界

“一张银行卡”在首版中指一个主借记账户入口。它用于展示当前可用余额和与本应用有关的账户流水，不代表行止自动取得用户全部资产负债信息。

| 数据 | 在行止中的用途 | 口径限制 |
| --- | --- | --- |
| 主借记账户当前可用余额 | 作为 30 天规划的起点 | 是当前快照，需标注查询时间，不保证未来仍不变 |
| 已入账收支记录 | 轻量记账、分类和订单关联 | 已确认消费与现金流事实分开；同一笔交易不能重复统计 |
| 信用卡当期应还及日期 | 作为对应日期的必要现金流 | 消费与后续还款分别记录；总欠款不全部扣入本期 |
| 贷款或分期当期应还及日期 | 作为近期必要安排 | 首版只纳入已知的当期还款，不宣称读取全部贷款合同 |
| 预计收入及日期 | 展示未来情景 | 未到账前不能加入当前可用余额 |
| 预计退款及日期 | 展示调整后的可能回款 | 未经渠道核验不能减少当前净支出 |
| 信用卡额度或可借额度 | 提供背景信息 | 始终不能并入自有现金或可规划资金，也不能自动触发借贷建议 |
| 用户补充的现金、其他账户和必要支出 | 补足当前授权范围之外的信息 | 标记为用户输入，并注明更新时间和不确定性 |

“当前未分配缓冲”在主演示中先用静态样例“当前可用余额－本月必要支出及当期还款－用户保留金额－已安排的可调计划”计算，2,000－900－500－400 得到 200 元。正式实现必须按日期计算资金安排，并识别基准余额或已覆盖流水，已经包含在当前账户事实中的现金流不能再次扣除。付款后应以实际账户事实为准，再加上尚未支付的必要安排；如果当前余额已经反映 99 元付款，就不能在剩余安排中再次扣除这 99 元。预计收入和退款另列情景，只有实际账户事实形成后才更新余额或现金流，期末有正余量也不能掩盖中途日期上的缺口。

同一主账户下的多个消费计划共享账户事实和必要支出，汇总时不能把同一笔流水或账单中的分期重复计入。信用额度始终不进入自有现金或可规划资金。

消费统计回答“已经花了多少、花在什么类别”，现金流安排回答“未来哪一天需要留出多少钱”。订单付款、银行卡流水和退款事实建立关联，但不能把订单、支付回执和流水简单相加。退款成功后保留原始付款记录，再增加已确认退款记录；不能用退款覆盖历史消费，也不能把预计退款当作到账。

## 六、商品目录与推荐边界

行止只推荐银行平台预先登记的商品或服务。登记信息至少包括商品名称、商户、价格、适用条件、履约说明和取消规则，并标明数据更新时间。目录中的商品按能力分为两类：

- 展示型商品支持检索、比较和跳转，不能承诺行止代下单、代付款或代取消。
- 可执行商品具有订单、支付和必要售后接口，行止只有在用户确认并满足授权条件后才能执行对应动作。

首版使用少量自建测试目录。标准主演示目录应准备至少两个合格的同类候选，让价格、时间、条件或取消成本形成可解释差异，并围绕两种不同取向组织方案，例如“省预算”和“偏体验”。每套方案都要列出项目预算拆分、必须保留项和可调整项；不硬凑三套方案，也不生成不符合约束或没有执行接口的候选。如果当前登记目录不足两个合格候选，行止必须如实提示无足够可比较结果或只展示现有候选，不能虚构商品、价格或推荐理由。推荐理由应能回到用户需求和计划约束，例如预算适配、时间合适或退款条件更清楚；不建设全网搜索、复杂推荐模型或推广排序系统。若未来出现商户推广，推广信息需要与基于用户条件的推荐理由分开显示。

## 七、核心演示场景

主演示面向一个有近期固定支出的青年用户，使用测试借记账户和登记商品。以下金额是虚构的演示数据：

| 资金安排 | 金额 |
| --- | ---: |
| 当前主借记账户可用余额 | 2,000 元 |
| 本月已知必要支出及当期还款 | 900 元 |
| 用户希望保留的金额 | 500 元 |
| 本月可调计划（含晚餐估价 80 元） | 400 元 |
| 当前未分配缓冲 | 200 元 |
| 用户选定的消费计划 | 99 元 |
| 消费计划完成后的预计余量 | 181 元 |

用户说：“周末想和朋友出去玩，两个人，帮我找一个不影响月底生活安排的方案。”行止先展示计算依据，再从已登记商品中给出候选。用户比较并用 99 元报价替换已计入计划的晚餐 80 元估价，完成订单和模拟支付。

随后用户补充：“临时多了一笔 400 元的必要支出。”在其他条件不变的情况下，原计划的 181 元余量变为 219 元缺口。工资延后等变化由用户更新或已接入的账户事实触发规则重算，行止按需生成待确认建议，不常驻模型，也不自动交易。行止应说明变化来源，并让用户选择保留重点项目、替换更便宜的商品、延后未付款项目，或取消可退订单。用户确认后才执行调整。

如果订单已经付款，恢复页面或重复点击不能再次创建支付或扣款；应先读取原订单和支付事实。取消产生的退款在沙箱中只证明渠道退款结果，不能直接改写银行余额。若退款仍待核对，行止应继续显示缺口及预计回款，不得宣称必要支出已经得到解决。

这条链同时展示记账、规划、商品选择、支付和变化调整，且每个金额和状态都能回到业务记录。

每次关键决策保存一份轻量记录：输入事实版本、规则计算结果、简短理由、候选或计划差异、用户确认内容和实际操作结果。记录用于解释当时为什么给出方案，不保存模型隐私思维链，也不依据用户行为自动学习或改变规则。计划完成后提供轻量复盘，列出计划金额、实际支付、已确认退款、净额和未决事项；预计退款不写入已退金额。

## 八、Demo 范围与实现路线

首版 P0 只做一条简洁、可重复的消费者闭环，使用测试账户、测试收支／还款数据、银行登记测试商品和本地模拟支付。日常开发继续使用模拟支付；集中录制 Demo 时，在同一运行中用支付宝官方沙箱连续完成付款、变化确认、原单取消退款与查询，并明确环境标签。未付款关单需要展示时另行补充，不用历史子链替代这条连续链。

历史后端曾有 55 项定向检查通过，也曾取得支付宝沙箱付款、原单退款和待付款关单等核心子链记录。这些是旧项目底座的历史证据，说明已有订单、支付、取消、退款和恢复能力可以复用；历史子链不能替代新方案要求的同一运行连续链，也不代表新方案中的账户规划、轻量记账、空状态需求、多候选比较和统一消费者流程已经通过，不能直接作为新 P0 验收结果。

实施固定为三个大阶段，且是唯一主 DEV 顺序；现有订单、确认、支付、取消和退款能力继续在主开发链路中复用，不因新方案后移到 P2：

| 阶段 | 重点 | 集中验收 |
| --- | --- | --- |
| M1 新后端 | 账户／账目事实、当期还款、月度与 30 天派生规划、登记商品、受限 Agent、购买和变化调整；001—028、A00—A06、B00—B07 已完成 | simulation 原领域检查已有证据；M1 补充收口和 HTTP 连续验收待完成 |
| M2 统一前端 | 从空状态输入需求，到规划、候选、确认、支付和变化调整的一体化消费者工作区 | 页面能完成一条主线，状态与后端事实一致 |
| M3 沙箱与用户证据 | 在同一运行中完成付款、变化确认、原单取消退款与查询，集中整理交易证据、用户访谈与任务观察；未付款关单需展示时另行补充 | 沙箱来源清楚，用户能理解资金影响，材料区分已实现与待合作 |

分批退款、商户拒绝或延迟、复杂贷款信息、多账户聚合等保留为专项验证或后续扩展，不作为首版 P0 放行前提。资金、用户确认、服务端授权、支付金额与退款原单的必要约束不因范围收窄而降低。

## 九、竞赛定位与竞争力

项目可围绕工行杯官方赛事介绍中的数字金融、青年群体服务等方向组织材料，具体赛道名称和当届申报要求在提交前以官方文件为准。[工行杯官方赛事介绍](https://www.gonghangbei.com/dsjs.html)

“记账”“余额提醒”“AI 推荐商品”分别看都容易被已有产品覆盖。行止需要把竞争力放在它们之间的连续关系上：用户先根据账户事实规划消费，再在银行登记目录中作选择，计划变化后系统继续帮助用户处理订单和退款，并将实际结果反馈回资金安排。这样既承接银行账户、支付和生活服务场景，也保留现有后端在授权、取消、退款和核验上的积累。

项目不能把拟议中的银行接口、真实商品履约、全量账户读取或正式支付写成已经实现。当前最可信的交付方式是受控原型：用明确标记的测试数据证明业务逻辑，用一条支付宝沙箱链证明渠道适配，再用少量目标用户任务观察证明这条流程确实能被理解和完成。

冲击国二、国三的关键不是堆叠功能，而是让评审看到一个完整、可信、可解释的银行消费场景：为什么推荐、这笔消费会影响什么、用户有哪些选择、用户确认后发生了什么、退款是否已经形成可用资金。用户需求证据、金额与订单一致性、银行价值假设和真实接入边界，都应在提交材料中清楚区分。

## 十、待验证事项

后续需要用少量访谈和体验任务验证：目标用户是否确实因为未来支出与还款安排而难以决定当前消费；他们能否理解“当前余额、可规划空间、预计收入和预计退款”的区别；他们是否愿意在自己确认后让行止执行可调整订单；商品目录规模和信息更新由谁维护；银行实际可提供哪些账户、账单和还款接口。

在这些问题得到证据前，项目使用“拟接入”“测试目录”“根据当前已提供的信息”等表述。不得把测试数据、支付宝沙箱结果或历史后端检查写成工行正式接入、真实账户联动或实际商品履约。
