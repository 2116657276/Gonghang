## 一、项目介绍

行止是一项面向智能体消费的计划变更与交易善后协同服务。用户可以通过自然语言提出购买需求，在确认商品和费用后完成付款；当目的改变时，系统协助区分需要保留、取消和停止的事项，展示退订成本，按授权提交处理请求，并持续核验订单和退款结果。

项目设计为由自定义 Pi 单 Agent 调用多个业务工具，首版连接自建测试商户，以官方支付沙箱验证完整交易闭环。商户商品和旅行履约为测试场景，付款确认仍遵守渠道要求，退款由商户按规则执行。后端已完成交易执行工具、事件恢复、T10 复核、变更善后连续链、1.3／1.4 恢复准备和当前模型固定场景的本地受控核对，并取得首批官方付款／原单退款／待付关单核心链记录；费用／分批退款、外部中断、多场景模型稳定性、前端跨端联调和完整验收仍待完成，当前实现与检查结果以开发计划为准。

首个 MVP／Demo 按[开发计划](../03-engineering/development-plan.md)完成全部 P0 基础能力后交付，包含费用退款、确认总额内分次退款、拒绝／延迟、权限隔离、恢复与行迹导出；内部开发阶段不作为完整产品成果宣传，后续基于实测深化体验。

## 二、核心演示

用户先安排一次出行并完成部分服务付款，随后说明“出差取消，但仍去探亲”。系统保留去程、申请退住宿、关闭未付款景点订单、停止接送和其他新购买，分别展示已处理事项、费用和仍待核对的退款。

重点不在于重复展示一个支付按钮，而是让用户意图变化与不同交易状态形成可确认、可执行、可追踪的处理方案。保留项不能误取消，停止推理不能被当作撤销付款，退款申请不能被显示成退款成功。

## 三、自主贡献与复用边界

| 内容 | 归属与证明 |
| --- | --- |
| 模型推理、Pi 工具循环 | 复用基础能力，保留来源和许可；不宣称自研大模型或通用框架 |
| 购买／善后分离、部分变更规则 | 项目应用设计；用明确案例和异常测试证明正确性 |
| 商户工具、授权执行、状态核对 | 自行建设的业务层；以连续交易证据证明实现 |
| 付款与退款通道 | 官方测试接口；不宣称行止掌握清算、全平台退款或资金托管 |
| 行迹证据与界面解释 | 项目体验设计；用户测试验证理解度，不凭设计宣称效果 |

## 四、允许和禁止的表述

现阶段说“计划实现”“设计要求”“待验证”；通过沙箱后才能说明具体已验证能力并附环境。不可写“已接入工商银行”“真实机票酒店全覆盖”“免确认自动扣款”“停止后绝不再付款”“一键保证到账”或“法律认可不可篡改凭证”。

不把同主题获奖记录换算成本项目获奖概率。赛事届次、赛道正式名称、资格和知识产权条款在提交前核对；旧计划书中的相关内容不是本轮确认依据。

## 五、提交前补齐

补齐匿名用户需求证据、Pi 与第三方许可、完整沙箱验收、异常恢复、实际交互效果、团队信息及当届规则。未经验证的性能数字、合作资源和生产能力不得填入正式计划书。
