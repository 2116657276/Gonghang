# 行止：验收与演示

> 本文合并微信手动验收指南和 Demo 录制脚本。它是执行清单，不改变 [04-development.md](04-development.md) 的阶段状态，也不把历史记录改写成当前通过。

## 1. 验收目标与环境分层

验收叙事先证明“看懂收支—安排资金—应对变化”；商品、订单和退款按选定的交易专项单独验收。所有结果必须注明运行环境：

| 环境 | 用途 | 不能替代 |
| --- | --- | --- |
| H5 | 本地消费者和管理端联调，检查请求、页面和跨角色事实 | 不能替代微信开发者工具或真机行为 |
| 微信开发者工具 | 小程序构建、页面、网络配置和模拟设备检查 | 不能证明真实手机的安全区、系统浏览器、网络和字体行为 |
| 真机 | 至少一台手机的最小消费者主线和底部操作面板 | 不能用 H5 截图替代 |
| Simulation | 本地付款、关单、退款和 Worker 恢复的业务链证据 | 不能写成银行或支付宝渠道事实 |
| 支付宝 Sandbox | 独立订单的渠道付款、主动查单、取消退款和退款查单 | 不能写成工行生产到账 |

一次外部验收只使用新建的隔离场景。失败时保存第一条错误、页面截图/录屏和业务编号；不删除数据、不手工改订单状态、不重复 Seed 同一个场景。

第 2—8 节保留原交易专项的准备与操作；纯财务主线使用第 9 节，不强制创建购买、退款或商户审核场景。财务空状态使用既有种子的 account-only 模式，历史流水观察可使用 complete 场景；每次使用新的唯一场景键，不修改历史证据。共用的 API 地址、微信工具导入和隐私要求仍适用。

## 2. 交易专项前置准备

1. 使用仓库根目录的启动脚本准备本地环境。常规 Simulation 使用 `PAYMENT_MODE=simulation`；密钥、测试密码和渠道配置只保存在本机 `.env`，不写入文档、截图、导出或聊天记录。
2. 为自动售后和商户人工处理各建一个唯一场景。场景键使用当天上海日期和未使用后缀，例如：

   ```zsh
   pnpm --filter @xingzhi/server db:seed:consumer-scenario weapp-auto-YYYYMMDD-01 YYYY-MM-DD complete automatic
   pnpm --filter @xingzhi/server db:seed:consumer-scenario weapp-manual-YYYYMMDD-01 YYYY-MM-DD complete merchant-review
   ```

   命令中的日期和场景键必须替换为实际值。保存命令输出中的消费者、预算周期、测试商户、审核者、商品、报价和场景标识，不保存密码。
3. 等待服务端、Worker、H5、管理端和微信监听构建按运行说明启动；检查 `http://localhost:8877/api/health` 和 `xingzhi/apps/miniapp/dist/weapp/app.json`。本文件记录的是验收步骤，不代表本次整理已执行这些操作。
4. 在微信开发者工具导入 `xingzhi/apps/miniapp`，不是直接把 `dist/weapp` 当作项目目录。项目配置的 `miniprogramRoot` 指向 `dist/weapp/`。
5. 本机开发者工具可以使用 `http://127.0.0.1:8877` 或 `http://localhost:8877`；真机不能使用这两个地址，必须使用手机可访问的 HTTPS 地址并配置微信合法域名。登录后在“我的 → 应用设置 → 演示环境”核对编入产物的 API 地址。
6. 管理端地址通常为 `http://localhost:5174`。商户和审核者账号使用场景输出或本机已配置账号；不要把账号密码写入记录。

## 3. Simulation 消费场景专项（保留）

用自动售后场景的消费者账号，按以下顺序操作。页面显示的周期、意图、订单、支付操作和退款标识都应记录；页面没有展示的标识，可以从管理端或审核导出补录，但不能自行编造。

| 步骤 | 操作 | 应看到的事实 |
| --- | --- | --- |
| 1 | 登录并打开首页、计划、账目、AI/草稿、我的 | 账户属于当前消费者；当前现金、未来收入、信用额度和待到账退款分层显示 |
| 2 | 查看预算周期和资金影响 | 标准场景能解释 2,000 元确认现金、900 元必要安排、500 元保留目标、400 元可调安排和 200 元初始空间；实际值不同以场景输出为准 |
| 3 | 从预算项目进入登记商品和报价 | 用户估价 80 元由正式报价 99 元替换，只增加 19 元占用，不重复扣除 80+99 |
| 4 | 建立购买意图 | 页面列出商品、报价、有效期、资金/预算/报价版本；此时还没有订单和支付 |
| 5 | 确认建立订单并快速重复点击/返回 | 只有一笔有效订单；页面明确建单不等于支付 |
| 6 | 进入付款交接并完成本地 Simulation | Worker 处理后订单状态恢复为已支付或对应记录；环境显示本地模拟，退出重进仍是同一订单 |
| 7 | 新增 400 元必要支出并查看影响 | 代表性场景从 181 元余量变为 219 元缺口；系统只提出调整方案，不静默改正式预算或订单 |
| 8 | 选择方案并在确认框明确确认 | 调整结果、计划变化、订单善后和退款状态分开显示；未选方案不执行 |
| 9 | 从订单详情发起取消/退款 | 先展示费用和预计退款，再要求本人确认；“已受理”不写成“已到账” |
| 10 | 等待 Worker 后重新进入订单、退款和周期复盘 | 订单取消、渠道处理、已核验退款和现金影响使用同一服务端事实；重复刷新不产生第二次业务动作 |
| 11 | 关闭并重开小程序，重新登录并打开订单列表 | 原意图、订单、支付、退款和操作时间线可通过本人业务事实恢复 |

如果商品、预算初值或账户状态与场景记录不一致，先停止并核对账号和场景，不改数据库把页面凑成样例数字。

## 4. 变化与人工处理分支

使用商户审核场景的消费者账号重复主线第 1—6 步，再从订单详情提交取消退款。

1. 消费者端应显示“等待商户处理”或等价的处理中状态，不能提前显示退款完成。
2. 场景对应商户登录管理端，确认新订单列表、详情、商品、金额、脱敏消费者信息、本人确认版本、支付状态和业务编号与消费者端一致。
3. 商户批准取消，并按用户已确认范围创建固定退款批次。重复点击、刷新或重试不能创建第二个有效批次，也不能由商户直接写入到账金额。
4. Worker 处理后回到消费者订单页，主动刷新或重新进入页面，确认订单取消、渠道处理和已到账退款分层展示。
5. 场景对应审核者登录管理端，只能看到明确分配的预算周期；沿同一订单编号核对资金版本、预算版本、用户确认、支付、商户操作、退款批次和时间线。
6. 分别生成 JSON 和 HTML 脱敏证据。页面与导出中的订单号、金额、状态和时间线应一致；不能包含密码、支付密钥、完整账户号、原始付款凭据或模型私有推理。

## 5. 微信开发者工具与真机

### 5.1 开发者工具财务主线

按根目录[开发接力指南](../../开发接力指南.md)准备隔离数据库、启动 API/Worker 和微信监听编译，并将 `xingzhi/apps/miniapp` 导入开发者工具。完整财务验收不要求购买、付款、退款、Sandbox 或商户审核；这些属于独立交易专项。

逐页核对：

- 登录后首页、账户和账目属于同一 Demo 用户与所选账户；当前余额、posted 流水、预计收入、未来义务和退款待到账各自语义清楚；
- 查看当前月与已有历史月统计，核对摘要和流水筛选；无数据时记录真实空态，不补造数据；
- 查看自然月规划及未来 30 日派生视图；修改预计收入日期或新增必要支出时，先比较变更前后，再由用户明确确认，检查结果与资金事实一致；
- 进入 AI 发起只读解释，确认资金金额和未知原因与服务端事实一致；查看规划草稿的用户输入、模型建议、待补充字段及只读影响预览，草稿不会自动变为正式计划或订单；
- 在存在适用数据时，核对同账户、同月 posted 非订单支出与未承诺计划的人工关联、实际覆盖和剩余金额；刷新或重新进入后事实保持一致。订单、退款待到账或未来义务不用于凑成普通流水关联场景；
- 首页、计划、账目、AI/草稿和我的五个标签页可打开；约 360px 宽、360×640 短屏及大字号下，金额、状态、按钮和底部面板不溢出或被遮挡；冷启动无持续白屏或明显卡死；断网恢复、重新登录/返回及数据刷新后状态可恢复。

记录开发者工具版本、基础库版本、构建/提交、场景、API 地址、每步结果和第一条错误。微信构建成功只证明产物生成，不等于开发者工具财务主线通过。若白屏，检查监听编译输出、`dist/weapp/app.json`、项目导入路径、API 健康状态和开发者工具缓存；不要把 H5 目录当作小程序产物目录。

### 5.2 开发者工具交易专项补充

仅当交付范围包含交易时，才在上述财务主线之外执行本小节。付款交接、处理进度和商户处理后返回订单详情时应读取最新服务端事实，晚到旧请求不能覆盖新状态；建单、取消或退款的快速重复操作不能产生重复业务结果。对应的完整 Simulation、商户审核和 Sandbox 流程见第 3、4、6 节。

### 5.3 真机

至少一台真机重复：

`登录 → 报价 → 建单 → 模拟付款 → 返回刷新 → 订单恢复`

并再次打开一个底部操作面板。真机必须使用手机可访问的 HTTPS API 和已配置的合法域名；`127.0.0.1` 在手机上指向手机自身。记录机型、系统、微信版本、基础库/构建信息、API 地址和第一条错误。

### 5.4 H5 与微信的支付平台差异

- H5 获取支付宝 Sandbox 收银台后，浏览器尝试用新标签页打开；如果弹窗被阻止，复制同一地址并在新标签页打开，原行止页面保留用于主动查单。
- 微信小程序不能直接跳转支付宝网页，只复制同一收银台地址到系统剪贴板；用户在系统浏览器打开并完成操作后，回到小程序付款交接页点击“我已完成操作，主动查单”。
- 两者都不能因为打开收银台就标记付款成功；最终以服务端保存的主动查单或已配置通知结果为准。

## 6. 支付宝 Sandbox 单独验收

Sandbox 不复用已付款、已退款、已撤回或报价过期的历史订单。先准备 Sandbox 所需应用/卖家/网关配置，再建立一个全新场景和订单。

沿同一订单完成：

1. 付款交接，保留原订单号和收银台有效期；
2. 用户在官方 Sandbox 收银台完成付款；
3. 回到原行止页面主动查单，保存渠道状态、业务号和服务端结果；
4. 沿原订单提交取消退款，不创建替代订单；
5. 读取/等待退款批次并主动查退款结果，保存原退款号、金额、状态和时间；
6. 在审核证据中核对同一订单的付款、取消、退款和环境标识。

Sandbox 渠道成功不等于工行账户已入账，也不等于真实银行退款。若配置未就绪或查询被限频，按页面/接口返回记录阻断原因，不反复创建新订单绕过问题。

## 7. 演示叙事与录制条件

### 7.1 含交易的扩展演示叙事（保留）

建议主视频控制在 5—7 分钟：

| 顺序 | 画面 | 讲解重点 |
| --- | --- | --- |
| 1 | 微信首页、账目和预算 | 行止先解释已发生收支和当前约束；当前 Demo 使用明确标注的测试账户 |
| 2 | 资金影响与需求入口 | 用户知道当前能安排多少，再说生活目标、日期、上限和必须项 |
| 3 | 候选和正式报价 | 80 元估算被 99 元报价替换，只增加 19 元；商品不是自动下单 |
| 4 | 用户确认、建单、付款 | 确认建单不等于支付；支付环境和结果来源显式显示 |
| 5 | 新增必要支出 | 181 元余量变为 219 元缺口，系统给方案，用户选择后才调整 |
| 6 | 订单取消与退款 | 区分申请受理、渠道成功、退款查单和账户到账 |
| 7 | 商户和审核工作台 | 沿同一订单编号展示处理、时间线、范围和脱敏证据 |
| 8 | 返回/重登恢复 | 回到原订单和原事实，说明“规划—消费—变化—善后”的闭环 |

进入支付宝 Sandbox 的内容只有在 Sandbox 实测通过后才录制；没有通过的真实模型、通知、银行或设备能力不进入结论。

### 7.2 含交易与 Sandbox 的录制条件

以下条件适用于包含 Sandbox 与跨角色交易的完整扩展演示。纯财务主线按第九节单独验收和录制，不能由其通过推导本专项通过：

- 当前 Git 提交、数据库场景名和构建信息已记录，录制中不临时改代码或数据库；
- 微信开发者工具主线通过，至少一台真机完成最小主线；
- 全新 Sandbox 订单完成付款、主动查单、取消退款和退款查单；
- 商户和审核者只能看到各自有权访问的订单/预算周期，页面与证据导出一致；
- 小程序“演示环境”页显示预期 API 地址、支付模式和 Worker 状态；
- 屏幕、浏览器自动填充、终端和导出文件没有密码、私钥、完整账户号、付款凭据或无关个人信息；
- 关键业务编号已记录在屏幕外的本地便笺中，视频不依赖临时等待编译、Seed、模型或渠道轮询。
