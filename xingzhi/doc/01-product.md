# 行止：产品目标与功能范围

> 本文说明产品为什么存在、当前代码能够支持什么，以及哪些能力不能被当前版本宣称。产品状态和后续顺序见 [04-development.md](04-development.md)，验收步骤见 [05-acceptance-and-demo.md](05-acceptance-and-demo.md)。

## 1. 产品目标

行止依托银行场景，帮助青年用户理解已经发生的收支，整理账目，安排近期资金，并在收入、支出或计划发生变化后及时调整安排。

它要解决的不是“替用户自动消费”，而是把用户平时分散在余额、流水、账单、预算和消费计划中的信息放到同一个可解释的决策过程里：先看懂现在发生了什么，再判断近期能安排什么，最后在情况变化时知道应该保留、替换、延后还是取消什么。

首批目标用户是正在实习或初入职场、开始独立承担房租、通勤、生活费和还款安排的青年。具体需求和实际效果仍需通过后续用户观察验证，不能仅凭竞赛样例推导普遍结论。

行止当前用于竞赛演示和本地联调。仓库内的 Demo 账户、登记商品、Simulation 支付和支付宝 Sandbox 路径都必须标明来源与环境；这不等于已经接入工行真实账户、真实商户履约或生产支付。

## 2. 核心体验的轻重关系

当前产品表达按以下顺序组织：

1. **理解收支与账目。** 读取授权范围内的账户快照和已入账流水，显示来源、时间、状态和分类；发现分类不合适时允许用户纠正展示分类。
2. **安排近期资金。** 以自然月预算周期保存必要支出、当期应还、预计收入、保留目标和可调安排，并派生日期级或未来 30 日的影响视图。
3. **应对变化。** 用户新增必要支出、收入延后、改变消费意愿或已接入事实变化后，系统重新评估缺口与余量，给出需要用户确认的调整方案。
4. **用 AI 理解需求。** 用户可以先说生活目标、日期、上限、必须项和可调整项；AI 负责提取信息、解释事实和保存非执行草稿，不代替用户作出购买、支付、退款或预算变更确认。
5. **记录消费场景。** 商品推荐、报价、购买、支付和退款是当前已有的消费场景能力，用来验证“安排资金后如何消费、变化后如何善后”，不是产品定位的中心，也不应掩盖账目和规划的核心价值。

## 3. 当前功能范围

### 3.1 消费者端

消费者端位于 `xingzhi/apps/miniapp`，使用 Taro + Vue 3 + TypeScript，同一套业务源码构建 H5 和微信小程序。当前页面与服务端路径覆盖以下能力：

| 模块 | 当前可以做什么 | 当前边界 |
| --- | --- | --- |
| 账户与资金事实 | 查看当前消费者可见的账户、余额快照、数据时间、账户状态和资金来源；撤回或重新授权 Demo 账户 | 不宣称真实银行同步；不把信用额度、预计收入或待到账退款当作当前现金 |
| 账目 | 查看已发生流水，按日期和状态浏览，纠正展示分类，关联行止订单；也可由用户确认将本人同月已入账的非订单支出覆盖到未承诺的预算项目 | 当前没有通用“手工新增一笔已发生流水”的入口；计划关联不改写流水，用户补充的必要支出、预计收入和预算项目仍是规划输入，不是银行流水 |
| 预算与近期规划 | 创建或读取自然月预算周期，保存必要支出、当期安排、保留目标和可调项目，查看资金依据与影响 | 未来 30 日是从当前月度事实派生的视图；不承诺完整年度预测、专业财务报表或所有账户的统一资产负债表 |
| 需求与 AI 草稿 | 从空状态提出生活目标，补充日期、金额、优先级和要求，保存规划草稿并在之后查看或接受；可基于本人所选上海自然月的已入账收支汇总提问 | 模型仅读取获准的月度汇总，不读取全部逐笔流水；草稿不等于预算激活、商品选择或订单，模型未配置或输出失败时不能写成自然语言演示已通过 |
| 商品与报价 | 查询银行平台预先登记的商品，查看商品条件、价格、有效期和取消规则，取得正式报价并进行资金评估 | 只使用登记目录；展示型商品只能推荐或跳转，可执行商品才进入确认和交易；不做全网商城 |
| 购买与订单 | 用户确认商品、报价、金额和授权后建立购买意图、订单，查看支付交接、订单时间线和恢复状态 | 建单不等于支付；服务端会重新检查报价、资金、预算和授权版本；不能由 AI 或页面自动扩大金额范围 |
| 变化与售后 | 评估新增必要支出，已有项目金额/日期编辑、取消入口，以及新增必要支出后的保留、取消可调项或申请取消订单方案；用户确认后沿原订单处理 | 预计退款、渠道退款成功和账户已到账是不同事实；不因预计退款立即增加当前现金 |

### 3.2 商户、审核与服务端

- 商户/审核网页位于 `xingzhi/apps/web`。网页保留旧计划历史入口，同时接入新消费者订单的商户列表、详情、取消决策、固定退款批次、人工任务、原操作复核，以及审核者的预算周期范围和脱敏证据导出。
- 服务端位于 `xingzhi/apps/server`，使用 Fastify + PostgreSQL；Worker 负责支付、退款等异步操作的处理与恢复。共享请求、响应和界面类型位于 `xingzhi/packages/contracts`。
- 商户只能处理建单时固化到本人商品的消费者订单，不能凭 `provider` 猜测归属，也不能查看消费者完整账户资金或改写用户确认的金额。
- 审核者只能查看服务端显式分配的预算周期和脱敏证据，不能创建订单、支付、取消或退款。页面上保留旧计划历史入口，不代表旧计划是新消费者主模型。

### 3.3 AI 的职责

当前消费者 AI 运行层的定位是“理解、读取、解释、保存草稿”。新消费者运行使用受控工具读取预算依据和本人所选月份的已入账流水汇总、搜索登记商品和保存规划草稿；月度账目工具不向模型提供逐笔流水。它不能确认商品、激活预算、建立订单、付款、取消或退款，也不能取得银行或支付密钥。

旧计划 Agent 路径仍存在于服务端，用于历史计划兼容；它与新消费者 Agent 入口分开，不能把旧路径的能力直接写成当前消费者 AI 能力。

## 4. 事实来源与产品边界

| 内容 | 当前含义 | 不能据此宣称 |
| --- | --- | --- |
| `demo` 账户、流水和预算 | 受控测试数据，用于本地和竞赛演示 | 已接入真实银行或覆盖用户全部资产 |
| `bank_api` 事实 | 代码为未来受信适配器保留来源边界；当前项目没有可供本次交付宣称的真实银行接入 | 银行余额、流水、账单已经实时同步 |
| `user_input` | 用户补充的预计收入、必要支出、日期、估价或变化，用于规划和条件说明 | 用户输入已经发生、已经入账或已经被银行核验 |
| `simulation` | 本地支付、关单和退款的业务链证据 | 真实渠道付款或银行卡到账 |
| `sandbox` | 支付宝官方沙箱渠道事实，和微信小程序运行环境分开 | 工行生产账户、真实银行余额或正式商户履约 |
| 模型输出 | 对用户需求和事实的解释、草稿或待确认建议 | 自动交易、自动借贷、自动扣款或模型直接修改业务事实 |

## 5. 演示主线与保留的消费样例

下一步财务主线依次展示账户与流水、月度统计、近期规划、收入日期或必要支出变化、调整前后对比、AI 解释与计划实际复盘；这一主线不要求购买或退款。具体冻结条件见[验收文档第九节](05-acceptance-and-demo.md#9-f1f3-财务体验集中验收与主线录制)。

以下消费样例作为已有交易能力的独立扩展保留。当前受控样例使用 2,000 元确认现金、900 元必要支出、500 元保留目标和 400 元可调安排，初始可支配空间为 200 元；80 元用户估价被 99 元正式报价替换后，示例余量为 181 元；新增 400 元必要支出后形成 219 元缺口。

这些数字是可复核的 Demo 场景，不是所有用户和所有月份的固定算法结论。正式计算仍按当前账户事实、日期、周期版本、流水覆盖范围和用户确认执行。演示随后展示用户选择调整方案、订单取消/退款及商户和审核者沿同一订单编号核对证据。

## 6. 非目标与未确认事项

当前不把以下内容写成已实现或本轮新增要求：真实银行账户与银行 App 宿主接入、生产支付和退款、全网商品检索、自动分类、任意手工流水录入、多账户完整资产聚合、长期目标/年度预测、自动借贷、自动交易、自动退款决策、多 Agent 协作和已验证的用户效果提升。

这些能力可以作为后续合作或产品化方向继续评估，但不能改变当前的用户确认、权限、金额、幂等、环境隔离和恢复约束。

### 7.1 本轮纳入与后置的优化

纳入：账户/月度上下文一致性、金额解释统一、真实流水摘要与查询、未来安排时间线、普通项目金额/日期变更前后对比、AI 结构化草稿卡、计划与实际复盘。已有项目编辑和分类纠正直接复用，不重做。
